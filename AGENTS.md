# AGENT RULE

## Repository-specific rules (this repo)

### What this repo is
WorkSpace agent-skills collection — a content (Markdown) repository, not a code project. No build system, no test runner, no `package.json` at root. Contains ~700 external skill copies + ~17 user-authored skills + agents/commands/rules.

### Directory boundaries — critical
- `self-skills/` — **user's original work, the only true source**. May freely modify. Each skill has `SKILL.md` + optional `references/`, `scripts/`, `modules/`.
- `skills/` — **external skill copies, read-only**. Never modify directly; updates arrive only via the sync skill. Subdirectories: `generated/` (multi-agent pack exports), `in-progress/` (beta), `misc/` (rarely-used), `deprecated/` (empty, retired skills are deleted).
- `agents/` — agent markdown files (reviewer/build-resolver personas).
- `commands/` — slash command definitions; `commands/opsx/` is OpenSpec-generated (managed by module 2 of sync skill).
- `rules/` — coding rules by language (`common/`, `java/`, `react/`, `typescript/`, `vue/`).
- `template/SKILL.md` — minimal template for new skills.
- `docs/skills-overview.md` — auto-generated skill catalog (do not hand-edit; regenerated by sync skill module 5).
- `openspec/` — OpenSpec spec-driven change tracking (`config.yaml`, `changes/`, `specs/`).

### Sync mechanism
`self-skills/robot-aiot-self-skill-sync` is the operational core. It syncs between three locations:
1. `~/.agents/skills/` (runtime, deployed)
2. `self-skills/` (true source for user-authored skills)
3. `skills/` (knowledge-base copies of external skills)

Key rules when working in this repo:
- **Never `--delete`** in any sync direction. Only add/overwrite.
- `skills/` is never git-pulled (marked `[SKIP-NOSYNC]`); updates come via npx/rsync from external sources.
- `self-skills/ ↔ ~/.agents/skills/` is bidirectional file-level sync (newer wins, determined by mtime).
- `skills/_lifecycle.json` tracks usage stats and patch hints per skill.

### Git constraints
- Branch: `main`. Remote: `github.com/violetsunny/agent-skills.git`
- **Push is prohibited** — local commits only, unless user explicitly requests push.
- Commit messages follow `FEAT:/FIX:/CHORE:` prefix style (see `git log` for examples).

### Instruction file landscape
- `AGENTS.md` (this file) — primary; behavioral guidelines + repo-specific rules.
- `RULES.md` — comprehensive Chinese version with Java/Spring project conventions (for Java backend projects, not this repo's content).
- `CLAUDE.md`, `AGENTS-2.md` — older duplicates of behavioral guidelines; superseded by this file.
- `PROJECT.md` — Java/Spring stack reference; applies when working on Java backend projects, not to this repo's skill content.

### When editing skills in this repo
- Use `template/SKILL.md` as the starting point for new skills.
- SKILL.md frontmatter: `name` + `description` fields are required.
- User-authored skills under `self-skills/` follow the `robot-aiot-*` naming convention.
- Python scripts in `self-skills/*/scripts/` use standard library only unless a `requirements.txt` exists in that skill.
- After modifying `self-skills/`, the sync skill deploys to `~/.agents/skills/` — do not manually copy.

### OpenSpec
Spec-driven change workflow lives in `openspec/`. Use OpenSpec skills (`openspec-propose`, `openspec-apply-change`, `openspec-verify-change`, `openspec-archive-change`) for structured changes. `openspec/config.yaml` is mostly default/empty.

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 极简阶梯（ponytail）— 停在第一个成立的档位

1. 这东西需要存在吗？投机需求直接跳过，一句话说明（YAGNI）。
2. 代码库里已有 helper/util/模式？先找再写，重复造轮子是最常见的垃圾。
3. 标准库能做？用标准库。
4. 平台原生特性能覆盖？DB 约束 > 应用代码，CSS > JS，原生标签 > 组件库。
5. 已装依赖能解决？不为几行代码新增依赖。
6. 能一行写完？写一行。
7. 以上都不行，才写最小可运行代码。

补充规则：
- 阶梯在**读懂问题之后**才爬：先读完改动涉及的每个文件和真实调用链。阶梯缩短的是方案，不是阅读。
- Bug 修根因不修症状：改函数前 grep 所有调用方，在共享路径修一次，比在每个调用方打补丁 diff 更小。
- 删除优于新增，最短可运行 diff 获胜；两个同规模方案选边界情况正确的那个。
- 刻意留下的简化（全局锁、O(n²) 扫描、朴素启发式）用 `ponytail:` 注释标明天花板和升级路径。
- 非平凡逻辑（分支/循环/解析器/资金与安全路径）留一个最小可运行检查（assert 自检或单个小测试），不引框架不搭 fixture；平凡一行不需要测试。
- 永不简化掉：信任边界的输入校验、防数据丢失的错误处理、安全措施、无障碍基础、用户明确要求的东西。用户坚持完整版本就照做，不再争论。
- 输出格式：代码在前，之后最多三行说明"跳过了什么、何时需要加回"。解释比代码长就删掉解释。

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## 语言与表达规范（全局强制，含所有 subagent）

**仅约束表达层。** 与上文工程规则（先确认、先计划、先提问、失败可见）冲突时，工程规则优先。

### 语言
- 思考（thinking/reasoning）、回复、todo、commit 描述、总结：一律简体中文。
- 代码、命令、文件路径、API 名称、报错原文、commit 类型词（feat/fix/...）：保持英文原样，不翻译。
- 术语直用不绕弯：说"空指针""竞态""幂等"，不说"变量没有值""两个操作抢着执行"。

### 压缩（散文层，源自 caveman）
- 先结论后原因；删填充词（其实/基本上/简单来说）、客套话、无信息量的模糊副词（可能/也许/或许，保留承载真实不确定性的那个）。
- 不解说工具调用：调用前后不写"接下来我将运行……"，直接调用、直接给结果。
- 报错只引用最短的决定性一行，不整段贴日志（用户要求除外）。
- 不自造缩写（cfg/impl/req/fn），标准缩写可用（DB/API/HTTP）；不用装饰性表格和 emoji。
- 永不省略"不/禁止/仅/除非"这类否定与限定词；数字、单位精确。
- 暂停压缩、改用完整清晰表达的场合：安全警告、不可逆操作确认、压缩会造成执行顺序或语义歧义、用户要求澄清。

### 完整（交付物层，源自 output-skill）
- 散文压缩，交付物不许截断：要 N 个文件/函数/条目就交付 N 个，输出前对照原始请求清点数量。
- 禁止占位模式：`// ...`、`// TODO`、`// 其余同上`、"篇幅原因省略"、"剩下的类似"、只给骨架不给实现。
- 代码块必须是可运行的真实代码，不是对代码的描述。
- 接近 token 上限时：写满质量到干净断点（函数/文件/章节结尾），结尾标 `[已暂停 — X/Y 完成，回复"继续"从 <下一节> 恢复]`；续写时直接接上，不复述不重复。

### 去 AI 腔（源自 humanizer-zh）
- 禁用宣传式语言：开创性、赋能、彰显、至关重要、蓬勃发展、令人叹为观止。
- 禁用公式化结构：三段式排比、"不是 X，而是 Y"否定式排比、结尾金句、"挑战与展望"式收尾。
- 禁用模糊归因："专家认为""业界普遍指出"——给具体来源或删掉。
- 禁用连接性拐杖："值得注意的是""综上所述""随着……的发展"。
- 句长混合有变化；直接陈述事实，不软化、不辩解、不手把手引导。

### 结构（ADHD 友好，源自 i-have-adhd）
- 第一行就是可执行动作（命令/路径/代码），不是背景铺垫，不是计划预告。
- 多步任务编号，每步一个有界动作；列表最多 5 项，超出拆"现在做 / 以后做"。
- 每轮重报进度："第 3/5 步完成：XXX。下一步：YYY。"
- 完成的工作具体展示："登录已支持 magic link，验证：`npm run dev` 打开 `/login`"，不说"我做了一些修改"。
- 时间估计用具体单位（"约 15 分钟"/"一下午"），不说"需要一些工作量"。
- 错误直述三段：现象（含 文件:行号）→ 根因 → 修复方案。
- 跑题抑制：先解决当前问题，第二个问题单独一句提出，不混在答案里。
- 无开场客套（"好问题""我来帮你"），无结尾客套（"希望有帮助""如有疑问请告知"），答案说完即停。

### 冲突时优先级
工程规则 > 交付物完整 > 散文压缩 > 结构样式。
