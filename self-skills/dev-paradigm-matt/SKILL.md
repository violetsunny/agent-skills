# Dev Paradigm

这是一个开发分层路由 skill，不是七阶段强制流水线。

目标只有两个：

1. 先判断任务当前处于哪一层
2. 再把工作路由到最合适的 matt-skills 组合

不要为了“走完整流程”而引入无意义步骤。任务小就走短路径，任务大才补齐规格、票据、架构和治理。

## 执行前依赖检查

本 skill 按需把工作路由到其他 skill，依赖检查发生在**路由时**：路由到某个目标 skill 前，先确认它已安装在运行时 `~/.agents/skills/`：

```bash
# 路由前把 s 替换为实际目标 skill 名，例如 s='to-spec'
s='<路由目标 skill>'
[ -d "$HOME/.agents/skills/$s" ] || printf '[DEP-MISSING] %s\n' "$s"
```

路由目标（按需依赖，以 matt-skills 系列为主）：`setup-matt-pocock-skills`、`triage`、`grill-me`、`to-spec`、`to-tickets`、`domain-modeling`、`codebase-design`、`implement`、`tdd`、`diagnosing-bugs`、`code-review`、`java-code-review`、`zh-code-reviewer`、`improve-codebase-architecture`、`spring-boot-patterns`、`wayfinder`、`handoff`、`retro`。

- 目标存在 → 略过，正常路由
- 出现 `[DEP-MISSING]` → 不私自安装，提示用户手动安装该 skill，或经用户确认改走其他可用路径

## 总图

```text
前置准备（每仓一次）
→ 需求层
→ 规格设计层
→ 开发实现层
→ 质量校验层
→ 收尾与长期维护
```

## 1. 前置准备

不要靠感觉判断“像不像初始化过”，先按下面标准检查。

### 初始化检查标准

满足以下条件，才算这个仓库已经完成 `setup-matt-pocock-skills` 初始化：

1. 仓库根目录存在 `CLAUDE.md` 或 `AGENTS.md`
2. 该文件中已有 `## Agent skills` 区块
3. 存在 `docs/agents/issue-tracker.md`
4. 存在 `docs/agents/domain.md`

补充规则：

1. 如果仓库安装了 `triage` skill，还应存在 `docs/agents/triage-labels.md`
2. 只看到 `CONTEXT.md`、`docs/adr/`、零散 ADR、issue 文档，不能等价视为已完成初始化
3. 只要上述 4 项条件缺任一项，就按“未初始化”处理——包括“文件都在、只缺 `## Agent skills` 区块”的情况；禁止以“其余齐全”为由跳过 setup

### 未初始化时

如果未满足上述标准，先执行一次：

1. `setup-matt-pocock-skills`

执行时采用以下默认选择，无需再逐项询问用户：

1. 目标文件：追加到 `AGENTS.md`（仓库没有 `AGENTS.md` 时，按 setup skill 自身规则处理）
2. Issue tracker：Local markdown（`.scratch/`）
3. Triage labels：默认五标签（若安装了 `triage`）
4. Domain docs：single-context

预期出口：

1. `CLAUDE.md` 或 `AGENTS.md` 中写入 `## Agent skills`
2. `docs/agents/issue-tracker.md`
3. `docs/agents/domain.md`
4. 若安装了 `triage`，再补 `docs/agents/triage-labels.md`

只有在检查失败或用户明确要求重建初始化时才需要这一步，不要每次开发都重复跑。

## 2. 需求层

先按检查项判断需求是否清楚，不要凭感觉。

### 任务规模检查标准

同时满足以下条件，可按“小需求”处理：

1. 改动目标单一
2. 影响范围集中在单模块、单接口、单页面或少量相邻文件
3. 不需要跨人协作或跨天拆分跟踪
4. 不会明显引入新的领域概念、系统边界或长期架构约束

满足以下任一项，就按“中大型需求”处理：

1. 影响多个模块、服务、页面、流程或角色
2. 需要多人协作、跨天推进或 issue tracker 持续跟踪
3. 需要先明确领域边界、职责拆分、接口契约或长期演进方式
4. 需求本身会拆成多个子任务，且实现顺序互相影响

### 需求清晰检查标准

同时满足以下 4 项，才算“需求已清晰”：

1. 能说清要改什么对象或流程
2. 能说清期望结果或外部可见行为
3. 能说清至少一个验收方式、成功标准或失败表现
4. 当前不存在会直接影响实现方向的未决分歧

只要上述任一项缺失，就按“需求模糊”处理。

### 需求模糊

按下面标准选路：

1. 满足以下条件时，用 `grill-me`：单一目标、影响范围集中、主要缺的是几处关键澄清、不需要沉淀正式文档
2. 满足以下任一条件时，用 `grill-with-docs`：跨模块、跨角色、跨天推进、需要形成书面结论、需求分支较多

满足以下任一条件时，补 `domain-modeling`：

1. 同一概念被多个名字混用
2. 多个对象之间职责或边界说不清
3. 需求讨论已经卡在术语定义而不是实现细节

出口：

1. 需求清晰
2. 核心术语统一
3. 边界、非目标、约束已显式化

### 需求已清晰

直接进入规格设计层，不重复访谈。

## 3. 规格设计层

这一层的重点不是写文档本身，而是决定是否需要正式规格、票据和架构边界。

### 进入本层的检查标准

满足以下任一项，就进入规格设计层，而不是直接写代码：

1. 任务需要跨模块协调，且实现顺序会互相影响
2. 任务会跨天推进，靠聊天上下文难以稳定传递
3. 任务需要多人协作或进入 issue tracker 持续跟踪
4. 当前已经能说清需求，但还不能直接列出稳定的实现边界、拆分顺序或验收项

如果上述条件均不满足，且改动边界已经明确，可直接进入开发实现层。

### 需要正式规格

满足以下任一项，按“需要正式规格”处理：

1. 需求已清晰，但实现前仍需沉淀正式验收项或非目标
2. 任务需要拆成多个可独立跟踪的子项
3. 任务状态、优先级、阻塞依赖需要被显式管理
4. 用户明确要求产出 Spec、tickets 或 issue tracker 条目

按顺序：

1. `to-spec`
2. `to-tickets`
3. `triage`

适用场景：

1. 中大型功能
2. 多人协作
3. 跨天推进
4. 需要进入 issue tracker

出口：

1. 正式 Spec
2. 带阻塞依赖的任务清单
3. 优先级与状态明确

### 需要架构设计

满足以下任一项，说明重点已经不是票据管理，而是边界设计：

1. 改动会新增模块、服务、流程主干或关键抽象
2. 现有代码能实现，但模块职责、依赖方向或扩展边界明显不稳
3. 接手的是陌生系统，短时间内还无法判断从哪里切入最安全
4. 争议点集中在系统边界、职责拆分、长期演进，而不是单个需求细节

按场景分流：

1. 新模块或大规模重构：`codebase-design`
2. 接手陌生老项目或工作量超大：`wayfinder`
3. 需要补齐领域边界：`domain-modeling`
4. 如果实现重点是 Spring Boot 的 controller / service / repository / JPA / REST 异常处理等常见后端模式，补 `spring-boot-patterns`

如果用户只是想把当前对话直接转成规格而不想继续访谈，优先 `to-spec`，不要重复 `grill`。

### 不需要正式规格

同时满足以下条件，可跳过正式规格，直接进入开发实现层：

1. 改动范围集中
2. 边界、非目标和验收方式已经明确
3. 不需要多人并行拆分，也不需要 issue tracker 持续跟踪

出口：

1. 已决定走 Spec/tickets 路径，或
2. 已确认可直接实现，且不会因为缺少文档而改变实现方向

## 4. 开发实现层

先判断是验证想法，还是正式生产代码。

### 进入本层的检查标准

满足以下 3 项，才算可以进入开发实现层：

1. 需求边界已清晰，且当前不存在会改变实现方向的未决问题
2. 已决定是否需要 Spec / tickets / 架构设计
3. 当前目标已经可以落到代码、配置、脚本或迁移等可执行改动上

任一项不满足，就回到需求层或规格设计层，而不是硬写代码。

### 快速验证 / POC

满足以下任一项时，用 `prototype` 而不是直接产出生产代码：

1. 目标是验证可行性、交互、状态机或技术路线
2. 还没有确定最终实现方案，只是要缩小选择范围
3. 用户明确要 POC、demo、草稿或实验性验证

1. `prototype`

用于回答设计问题、验证状态机、验证交互或逻辑，不直接等同于可交付生产代码。

### 正式生产代码

同时满足以下条件时，按“正式生产代码”处理：

1. 目标是可合并、可交付、可持续维护的实现
2. 输入已经稳定到足以直接落代码，而不是继续探索问题定义
3. 产出需要接受 review、测试或构建校验

1. `implement`

如果当前仓库或目标改动明确属于 Spring Boot 应用，且实现集中在 controller、service、repository、REST API、异常处理、JPA 模式等后端惯例，先参考 `spring-boot-patterns`，再进入 `implement`。

`implement` 是主入口。需要行为验证时，优先让它串联：

1. `tdd`
2. 实现
3. `code-review`

如果当前已有 Spec 或 tickets，默认直接以它们作为 `implement` 的输入，而不是重新拆解。

满足以下任一项时，优先把 `tdd` 串到 `implement` 前：

1. 逻辑容易回归，且已有失败样例或可明确写出行为断言
2. 改动涉及核心规则、状态转换、解析、计费、权限等高风险逻辑
3. 先写测试比先写实现更容易锁定正确行为

### Bug / 回归

按下面标准选路：

1. 能稳定复现、影响范围集中、修复方向清楚：可直接修复，但之后仍要进入质量校验层
2. 不能稳定复现、根因不明、牵涉性能/并发/时序/环境差异：先走 `diagnosing-bugs`

1. 简单 Bug：直接修复，但仍要回到质量校验层
2. 复杂 Bug、棘手回归、性能问题：`diagnosing-bugs`

### 合并冲突

当阻塞点明确是 merge / rebase / cherry-pick 冲突，而不是业务逻辑本身时，直接用 `resolving-merge-conflicts`。

1. `resolving-merge-conflicts`

## 5. 质量校验层

实现完成后，统一进入验证收尾。

### 进入本层的检查标准

满足以下任一项，就进入质量校验层：

1. 代码或配置改动已经完成一个可验证批次
2. 用户目标声称“已完成”，需要确认是否真的可交付
3. 需要判断当前结果是否满足 Spec、tickets 或已确认需求

### 功能与规格符合度

检查标准：

1. 若有 Spec / tickets，每一项都能对应到当前实现结果
2. 若无 Spec，至少能对照已确认需求逐项说明“做到 / 未做到 / 有偏差”
3. 发现缺口时，要显式记录回流点，不要笼统写“后续再看”

1. 若有 Spec / tickets：逐项对照验收
2. 若无 Spec：对照用户已确认的需求边界验收

### 代码质量

进入 review 前，至少要满足：

1. 改动已经形成可读的提交候选，不是明显半成品
2. 能指出这次改动要验证的核心行为或风险点

1. `code-review`
2. Java 项目可叠加 `java-code-review`
3. 需要中文审查报告时叠加 `zh-code-reviewer`（输出评分 + 分级中文结构化报告，与 `code-review` 双轴结论互补，不替代）

重点检查两轴：

1. Standards：是否符合项目规范
2. Spec：是否忠实实现需求

### 验证执行

按仓库现有门槛执行，不要凭空新增流程；但已有门槛不能跳过。

运行仓库已有的：

1. lint
2. typecheck
3. tests
4. build（如果这是交付门槛）

### 问题回流

回流标准：

1. 需求没实现对，回到 `implement`
2. 根因不清、现象不稳定或验证结果互相矛盾，回到 `diagnosing-bugs`
3. 如果验证暴露的是需求或边界本身错误，回到需求层或规格设计层

发现问题后：

1. 一般缺陷回到 `implement`
2. 难复现或复杂根因问题回到 `diagnosing-bugs`

## 6. 收尾与长期维护

这一层处理的是“这次做完之后还要不要留下可持续资产”，不是重复验收。

### 进入本层的检查标准

满足以下任一项，就进入收尾与长期维护层：

1. 当前结果已通过本轮实现与校验，接下来重点是交接、沉淀或长期治理
2. 工作不会在本次对话内彻底结束，还需要跨天、跨人或后续迭代继续
3. 当前问题已经从“做出来”转成“怎样稳定维护和持续演进”

### 跨天或换人交接

满足以下任一项时，用 `handoff`：

1. 下一步要由别人接手
2. 本次对话结束后还要继续推进
3. 关键背景、风险和未完事项如果不写下来就容易丢失

1. `handoff`

### 定期架构整治 / 技术债清理

当目标已经不是交付单一功能，而是系统性地处理结构问题、历史包袱或长期演进阻力时，用 `improve-codebase-architecture`。

1. `improve-codebase-architecture`

### 迭代复盘

当用户要总结这轮开发中的问题、决策得失、流程改进点时，用 `retro`。

1. `retro`

### 技术选型 / 方案调研

当下一步卡在技术路线、工具选择或外部方案比较，而不是现有实现细节时，用 `research`。

1. `research`

出口：

1. 交接材料、治理项或调研结论已形成
2. 后续动作有人接、可跟踪，或明确本轮到此结束

## 路由规则

1. 需求模糊先澄清，不猜
2. 小任务默认短路径，不强行补 Spec / tickets
3. 多人协作、跨天推进、陌生领域或复杂依赖时，优先走规格化路径
4. 新模块先考虑 `codebase-design`，陌生老项目先考虑 `wayfinder`
5. 生产代码优先 `implement`，高风险逻辑优先 `tdd`
6. 复杂 Bug 优先 `diagnosing-bugs`，不要跳过复现和根因定位
7. 收尾至少做验收、review、验证；是否交接取决于是否需要跨人/跨天继续

## 推荐路径

### 路径 A：小需求 / 明确改动

1. 需求已清晰
2. 直接 `implement`
3. `code-review`
4. 跑验证

### 路径 B：中大型功能

1. `grill-with-docs`
2. `domain-modeling`（如有必要）
3. `to-spec`
4. `to-tickets`
5. `triage`
6. `implement`
7. `code-review`
8. 跑验证
9. `handoff`（如需）

### 路径 C：陌生项目 / 大规模重构

1. `setup-matt-pocock-skills`（若未初始化）
2. `wayfinder` 或 `codebase-design`
3. `to-spec` / `to-tickets`（若需多人协作）
4. `implement`
5. `code-review`
6. 跑验证
7. `improve-codebase-architecture`（可作为收尾）

### 路径 D：复杂 Bug / 回归

1. `diagnosing-bugs`
2. `code-review`
3. 跑验证
4. `handoff`（如需沉淀）

## 不要这样做

1. 不要把所有任务都强行走完整七阶段
2. 不要在需求已清晰时重复 grill
3. 不要在小修小补上硬拆 Spec 和 tickets
4. 不要跳过 review 和验证直接宣布完成
5. 不要把 `prototype` 产物默认当生产代码交付
