# Phase 1: 源文件分析 — 数据池、反问澄清与受众分层

在写任何汇报内容之前，先完整读取用户指定的源文件，建立唯一数据源，并一次性向用户反问澄清汇报参数。所有页面引用同一数据池，不允许自造数字。

## 源文件入口

1. 源文件必须由用户指定（Markdown 知识文档 / 技术方案 / 总结报告 / 存量 `.pptx` 等）；未指定时先索取，不得自行假设或凭对话记忆拼凑
2. 多个源文件时全部列出，请用户确认取舍与优先级
3. 存量 `.pptx` 先提取逐页文字/图片/备注再并入分析；提取只做内容搬运，原版式取舍由用户决定
4. 完整读取源文件后才允许起草数据池与分析结论，禁止抽样阅读

## 反问澄清清单（一次性列齐，批量回答）

能推断的先从源文件推断并标注推断依据，推断不了的与推断结果一起一次性列给用户批量确认，不一来一回：

| # | 反问项 | 判据与默认值 | 对后续 Phase 的影响 |
|---|--------|--------------|---------------------|
| 1 | 页面总数 | 默认按演讲时长换算（30 分钟 = 8-12 页）；用户明确页数优先 | Phase 2 母稿分页规模 |
| 2 | 汇报对象 | 领导层 / 技术同行 / 外部客户 / 大众；从源文件汇报线与术语密度推断后确认；未指定默认领导层 | 决定表达策略、术语规则与 Phase 2 母稿风格基调 |
| 3 | 汇报范围 | 源文件哪些章节/主题进 deck、哪些明确排除；范围外内容不得出现在母稿 | Phase 2 母稿内容取舍 |
| 4 | 演讲时长 | 决定页数换算与话术总量；未指定按页面总数反推 | Phase 2 分页、Phase 4 话术长度 |

答案与推断依据写入分析报告头部，随母稿头部元信息落盘（Phase 2 引用）。

## 数据池

### 目标

1. 同一指标在所有页面只有一个权威数值
2. 每个数值可追溯到代码、SQL、配置、API、CSV/Excel、监控或数据库结果
3. 快照、累计、估算、派生指标口径明确

### 执行步骤

1. 从源文件提取真实指标，估算值必须加 `~` 并注明依据
2. 建立数据池表：`数据项 | 口径说明 | 数值 | 用于页面`，落盘 `doc-ppt/<project>_数据池.md`
3. 标注快照值还是累计值，避免混用
4. 为派生指标写清计算公式
5. 在"数据使用提醒"里记录估算依据、适用边界和注意事项

### 多数据源合并

当同一指标来自 2 个及以上系统时：

1. 增加"来源系统"列
2. 明确统一口径，解释为何以某个系统为准
3. 出现冲突时标注主值与参考值
4. 检查分组值之和是否等于总计值，避免混用不同口径

### 模板

单数据源与多数据源两套成品骨架见 `templates/data-pool.md`，复制进项目数据池文档后填充，二选一，不得凭记忆转抄。

## 受众分层（母稿的内部分析输入）

受众分层是 Phase 2 母稿的前置分析，不再作为独立交付文档阶段；分析产物（技术明细理解 + 受众化表达要点）作为母稿起草输入。

目标受众由反问清单第 2 项确认，受众决定表达策略：

| 目标受众 | 表达策略 | 术语规则 |
|---|---|---|
| 领导层（默认） | 结论先行、业务能力、管理结论、数据支撑表 | 全部业务化，禁暴露表名/类名/API |
| 技术同行 | 保留架构决策、链路细节、性能与容量数据 | 可保留技术命名，缩写首次出现给全称 |
| 外部客户 | 价值与案例叙事、脱敏数据、品牌语气 | 全部业务化，且隐去内部系统名与敏感口径 |
| 大众/混合 | 故事线优先、每页一个信息点、少数字 | 全部业务化，禁用行话 |

### 执行顺序

1. 先做技术明细理解：流程、泳道、异常处理、代码级引用，确保对系统全貌理解完整
2. 再按受众表达策略提炼汇报表达（默认领导层：分层架构、能力总结、管理结论、数据支撑表）
3. 同步产出技术术语映射表，供 Phase 2 母稿检查表达（技术同行受众可精简为缩写对照表）

### 技术术语翻译规则

面向领导层、外部客户、大众受众时，母稿中不允许直接暴露（技术同行受众豁免，仅需缩写给全称）：

1. 数据库表名
2. Java 类名
3. API 路径
4. 无解释的内部缩写

术语映射表成品骨架（含示例行）见 `templates/term-mapping.md`；技术明细版与汇报版文档结构骨架见 `templates/doc-structure.md`（需要独立留档两份文档时使用，共用同一数据池）。

## Sub Agent 建议

1. 用 fresh sub agent 做源文件扫描、指标归并和口径冲突识别；主线程只接收已归并的候选数据池结果，再决定最终表格写法
2. 多数据源冲突必须回到主线程拍板，不允许多个 sub agent 各自写不同口径版本
3. 技术明细理解与受众化提炼可分两个 sub agent 先后执行，提炼输入必须同时包含数据池、技术明细草稿和目标受众
4. 主线程负责比较两份草稿，确认汇报表达没有绕过技术明细单独造结论，且数据一致、术语映射一致，再统一落盘

## 阻塞条件

1. 源文件未指定或未完整读取 → 不得起草数据池
2. 反问清单未获回答 → 可推断项按 best judgment 补齐并标注「假设：<内容>（未经用户确认）」后继续；无法推断项（页数与范围完全无依据）停在该项，先完成其余分析，最后把待确认项一次性列给用户
3. 关键数据无来源且无法估算 → 暂停并请求补充

## 交接（handoff）

Phase 1 结束、进入 Phase 2 前执行交接：

- 本环节产物：数据池 MD（`doc-ppt/<project>_数据池.md`，数据项/口径说明/数值/用于页面四列齐备）+ 反问答案（写入母稿头部元信息，Phase 2 落盘）
- 下一环节输入：数据池作 Phase 2 母稿数据引用源；反问答案（页数/汇报对象/汇报范围/演讲时长）定母稿分页规模与风格基调
- 交接校验：`scripts/check_phase_handoff.py doc-ppt --phase 1 --write` → 校验数据池 MD 存在，落盘 `_gen/handoff-phase1.md`
- FAIL 阻塞：数据池缺失，不得进入 Phase 2
