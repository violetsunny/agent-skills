# Module 6: 审计与核查

文档写完不等于写对。本模块把收口拆成三道门：确定性脚本审计 → 新鲜度审计 → fresh-context 事实核查。前两道抓机械可证的错误，第三道抓语义错误。

## 6.1 确定性脚本审计

技能自带只读审计脚本（登记见 `env-config.md`），仅 Python 3 标准库，不写任何文件：

```bash
python3 <技能目录>/scripts/audit_docs.py --root <项目根>
```

检查项：

| 节 | 检查 | 级别 |
|---|---|---|
| files | 5 个目标文件存在且可按 UTF-8 读取 | 缺失 WARN / 读不了 FAIL |
| links | 本地 Markdown 链接可解析；链接不得指向仓库外（越界视同断链）；外链、锚点、代码块内不查 | FAIL |
| paths | 反引号引用的仓库路径存在；不查：URL 片段、绝对路径、`~/` 与 `$` 开头的用户环境路径、含占位符的值、不含 `/` 的单段名称（如 `pom.xml`）、末段无扩展名且不以 `/` 结尾的值（如 `application/json`）、删除区登记项；模块相对路径（如 `src/test/java/`、`META-INF/spring.factories`）在仓库内任意位置后缀命中即视为存在 | FAIL |
| freshness | project-map / architecture 前 3 行内的 `<!-- Generated: YYYY-MM-DD ... -->` 新鲜度头 | 缺失或超 90 天 WARN / 日期无法解析或在未来 FAIL 或 WARN |
| delete-zone | AGENTS.md 删除区登记的路径未被重建 | 重建 FAIL |
| orphans | docs/ 两文件被 README 或 AGENTS 引用 | 无入链 WARN |

注：代码块豁免含 fenced 与 4 空格/tab 缩进两种形式；缩进行一律跳过检查，4 空格缩进的列表延续行内的链接与路径因此也不查（有意保守，宁可漏报不误报）。

写作约定：文中明确声明“尚未生成 / 懒创建”的目录路径（如未来的 `docs/adr/`）不用反引号包裹，或写成带 `…`/`*` 占位的形式；否则 paths 检查按“引用路径不存在”FAIL。禁止为过审计把真实路径改写成失真的 glob 或换名（`~/.m2` 改 `$HOME/.m2` 之类的等价豁免写法除外）。

退出码契约：

1. `0` = 通过（WARN 允许，但须逐条人工复核或写入执行摘要）
2. `1` = 完整性失败，必须修复后重跑，直到 0 才能进入语义核查
3. `2` = CLI 输入错误（目录不存在等）

执行时机：

1. **基线审计**：Step 0 定位项目根后立即跑一次，输出作为现状输入（哪些文件缺失、哪些链接已断）
2. **收口审计**：全部文档更新完成后必须跑，exit≠0 时修复重跑
3. 两次审计的 stdout 都重定向落盘到 `env-config.md` 登记的验证目录（`audit-baseline.txt` / `audit-final.txt`），脚本自身只读不写

原则：脚本只判“机械可证”的错误；WARN ≠ FAIL，语义正确性脚本不管，留给 6.3。

## 6.2 新鲜度审计（agent 步骤，脚本外）

收口时对未改动的文档做交叉比对：

```bash
# 逐文档取最后修改日期
for f in README.md docs/project-map.md docs/architecture.md; do
  echo "$f: $(git log -1 --format=%cs -- "$f")"
done
# 近 90 天源码变更涉及的文件
git log --since="90 days ago" --name-only --format= -- '*.java' '*.py' '*.ts' | sort -u
```

规则：

1. 文档 90+ 天未改、且其覆盖的源码目录近 90 天有实质变更 → 列入执行摘要 **Flagged**，提示人工复核
2. 文档 90+ 天未改、对应源码也未变 → 不 Flagged，不算过期
3. Git 历史不可用（shallow clone 等）→ 显式声明跳过，不猜测

## 6.3 fresh-context 事实核查（subagent）

写文档的 agent 会被自己的假设说服，核查必须用没看过写作过程的无上下文 subagent。

触发条件：收口审计 exit=0 后默认执行；用户明确要求快速运行时可跳过，但须在执行摘要注明“未做事实核查”。

操作步骤：

1. 按文件切分核查单元：每个文件一个 subagent，可并行
2. 报告落盘到 `env-config.md` 登记的验证目录，handoff 后主 agent 查不到 subagent 输出，必须落盘
3. subagent prompt 模板（占位符全部替换为绝对路径后再发送）：

```text
你在核查一套刚生成/更新的项目文档，扮演两个最挑剔的读者：冷读的开发者和开着仓库的事实核查员。

项目根：<绝对路径>。所有工具调用一律用绝对路径。
核查对象：<文档绝对路径>（只核查这一个文件）。

按顺序检查：
1. 事实：文中每条命令、路径、配置键、端口、默认值、行为声明。只读命令直接重跑；
   会改状态的命令不跑，只核对其参数与源码/配置是否一致。输出块必须与命令真实输出一致。
   路径和名称逐一对照仓库实际文件。
2. 结构：是否重复解释了其他文档才是 canonical owner 的内容（一个事实只住一个文件，其余链接）。
3. 职责：内容是否符合该文件角色（AGENTS=规则、README=入口、CHANGELOG=时间线、
   project-map=结构 reference、architecture=设计 explanation），有无串位。
4. 表达：空泛营销语（强大/优雅/企业级）、无证据断言、AI 腔、中英文空格缺失。

输出规则：
- 只报告，不重写文档。
- 每条发现：引用原行 + 问题一句话 + 一行修法，按严重度排序。
- 每个核实过的事实注明验证方式（跑了什么命令 / 对照了哪个文件哪一行）。
- 无法验证的声明单独列出并说明原因。
- 文件干净就明说干净，并列出核实过什么。
```

报告处理规则：

1. 默认“报告不重写”：把发现按严重度呈现给用户；仅当用户要求 verify-and-fix 或认可发现时才动手修
2. 核查员也可能错：驳回的发现连同理由写进报告，用户可推翻
3. 修复若改动了事实性声明，只对改动部分做第二轮 scoped 核查；纯措辞修复不需要二轮
4. 两轮不收敛即停，交用户裁决，禁止无限打磨

## 6.4 三道门的通过标准

| 门 | 通过标准 |
|---|---|
| 脚本审计 | exit=0，且每条 WARN 已复核或写入摘要 |
| 新鲜度审计 | Flagged 清单已生成（可以为空） |
| 事实核查 | 报告已落盘；FAIL 级发现已修复或经用户裁决保留 |

三道门全过（或显式声明跳过项）才能输出执行摘要。
