# Robot AIoT ADR Generator

为 ADR 场景提供一条完整链路：先成文，再核查，再做最小修正。

## 执行前依赖检查

无外部 skill 依赖，可在运行时 `~/.agents/skills/` 独立执行。

## 核心定位

本技能完成两件事：

1. 生成标准化 ADR 文档
2. 对 ADR 中关键技术断言执行验证链核查

适用范围：机器人、IoT、平台、中间件、协议选型、边云协同、架构升级、技术替换等决策归档。

边界：

1. 本技能核查技术事实，不替代团队对成本、业务优先级和组织取舍的最终拍板
2. 本技能只核查会影响决策可信度的关键断言，不做全文逐句审稿
3. 若环境不具备联网核查条件，可以交付 ADR 草稿或定稿，但必须显式写明“未经外部事实交叉验证”

## 最低输入

以下信息缺失时要追问；用户要求“直接生成”时可用 `[待补充]` 占位：

1. 核心业务或技术问题
2. 候选方案，至少 2 个
3. 最终选定方案
4. 作者或团队名称
5. ADR 编号；若未提供，可建议三位数字编号

可选增强信息：

1. 技术栈版本
2. 性能或容量目标
3. 外部依赖与约束
4. ADR 状态：`Proposed` / `Accepted` / `Deprecated` / `Superseded`
5. 是否要求执行验证链，或允许跳过联网核查

## 输出

默认输出三部分：

1. 文件路径建议：`docs/adr/ADR-数字编号-标题.md`
2. 完整 ADR Markdown 正文
3. 验证摘要或跳过说明

若执行验证链，摘要必须包含：

1. 本次核查的关键断言数量
2. `准确 / 不完整 / 错误 / 无法确定` 的数量或清单
3. 已修正项
4. 待人工确认项

可选附加输出：

1. `verification-report.md` 风格的完整核查报告
2. 仅当用户明确要求时，单独给出“修复前 / 修复后差异摘要”

## ADR 固定模板

```markdown

- **状态**：Proposed | Accepted | Deprecated | Superseded
- **日期**：{YYYY-MM-DD}
- **作者**：{姓名/团队}
- **最后修改**：{YYYY-MM-DD}

## 上下文

完整描述当前业务背景、技术栈约束、团队规模、性能指标、工期压力、现存痛点、业务诉求，把技术问题讲清楚。

## 决策

- 选用的组件/框架/版本明细
- 落地实现的具体方式、架构分层、接入规则
- 明确不做的边界范围，规避范围蔓延

## 后果

- 正面影响2

### 负面：

- 负面影响2

## 替代方案

  - 不选择核心原因：xxx

## 变更历史

```

## 工作流总览

```text
信息补齐
→ 生成 ADR 草稿
→ 提取关键断言（Critic）
→ 并行核查断言（Verifier × N，按需）
→ 最小修正 ADR（Repairer）
→ 输出 ADR 与验证摘要
```

## Phase 1: 生成 ADR 草稿

执行要求：

1. 严格使用固定模板，不删减章节
2. 状态只允许 `Proposed`、`Accepted`、`Deprecated`、`Superseded`
3. 后果至少 2 条正面、2 条负面
4. 替代方案至少 2 个，每个都要写优势、劣势和不选择原因
5. 候选方案不足 2 个时只能输出草稿，并明确替代方案信息不足
6. 自动补齐文件名建议与首条变更历史

## Phase 2: 验证链核查

本阶段使用 `prompts/` 下三类角色提示词：

1. `prompts/critic.md`：提取 ADR 中 5-12 条关键断言
2. `prompts/verifier.md`：每条断言独立联网核查
3. `prompts/repairer.md`：根据核查结果做最小修正

### 2.1 Critic

目标：

1. 从 ADR 草稿中提取 5-12 条关键断言
2. 只保留会影响决策可信度的断言
3. 为每条断言生成精确核查问题与建议核查路径

优先关注：

1. 版本能力与兼容性
2. 性能、延迟、容量、成本、SLA 等量化结论
3. 命令参数、配置项、接口行为、限制条件
4. 外部依赖、许可、生命周期、停维护风险

### 2.2 Verifier

目标：

1. 每条断言独立核查，避免上下文污染
2. 优先查官方文档、标准规范、厂商文档和高可信来源
3. 对每条断言给出 `准确 / 不完整 / 错误 / 无法确定` 结论

执行规则：

1. 每条断言一个独立核查上下文
2. 断言较多时可分批并行
3. 不把整篇 ADR 原文原样送入每个核查上下文

### 2.3 Repairer

目标：

1. 只修正文中被证实有误、不完整或过时的技术事实
2. 不重写已经成立的决策结构
3. 无法确定的内容保留时，显式标记风险或待确认项

## 交互模式

1. 默认全自动：`生成 ADR -> Critic -> Verifier × N -> Repairer -> 输出摘要`
2. 若用户说“先审再改”：完成 Verifier 后暂停，先展示核查结果，再由用户决定是否进入 Repairer
3. 若用户说“只查不改”：执行到 Verifier 即停止，只输出 ADR 草稿和核查报告，不进入 Repairer
4. 若用户指定重点关注项，例如“重点检查协议兼容性”或“重点检查命令参数”，需把该重点显式传递给 Critic 与 Verifier

## 触发与跳过规则

以下场景优先执行验证链：

1. ADR 包含大量版本、兼容性、协议能力或性能指标
2. ADR 将用于正式评审、归档或发布前质量把关
3. 用户明确要求“生成后顺便校验”或“审一下 ADR”

以下场景可跳过验证链：

1. 文档主要是内部取舍，外部事实很少
2. 用户明确要求“先成文，暂不核查”
3. 当前环境不具备联网核查条件

跳过时必须明确写出原因，例如：

1. `本次 ADR 主要为内部取舍说明，外部可验证断言较少，已跳过验证链。`
2. `当前环境不具备联网核查条件，本次交付为未经外部事实交叉验证的 ADR 草稿。`

## 守则

1. 先成文，再核查；不要在事实未成形时空跑验证链
2. 只核查关键断言，不做无意义的全文逐句审稿
3. 事实核查优先官方和权威来源，避免内容农场
4. 最小修复，不改动本来成立的决策结构
5. 无法确认的内容不能假装正确，必须显式标注
6. 已 `Accepted` 的 ADR 不直接篡改既有决策；若需改变结论，优先新增 ADR 并标记旧者为 `Superseded`
7. 本技能是独立 ADR 工作流；使用时不要求额外引用其他 ADR 或通用核查技能
