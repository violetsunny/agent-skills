# Sub-agent 编排手册 (sub-agent orchestration playbook)

Sub-agent 的上下文干净、互不污染，适合两类工作：

1. **复查与校对**：让没有参与分析过程的 agent 做第二意见审查，避免确认偏差。
2. **并行分析**：多只股票、多个行情维度各自交给独立 agent 同时分析，主会话只做编排与整合。

## 何时派发 sub-agent

| 场景 | 派发方式 | 理由 |
|---|---|---|
| 多股对比 / 批量分析（≥3 只） | 每股一个 `symbol-analyst`，并行 | 串行分析多股会互相串味，且上下文膨胀 |
| 大盘复盘多维度并行 | 拆 2~4 个 `domain-analyst`（指数与情绪 / 板块与题材 / 资金与事件） | 各维度数据域不同，并行省时且结论独立 |
| 深度分析、复盘、筛选报告的校对 | 强制派一个 `cross-check-reviewer` | 分析者有确认偏差，需干净上下文的第三方核对 |
| 单票快查、单一简单问题 | **不派发** | 避免过度编排 |

判断顺序：先按 `SKILL.md` 的任务路由定性，再决定是否派发。

## 角色定义

### symbol-analyst（个股分析）

基于主会话传入的结构化底稿，产出单只标的的四层结论。输入上下文（由主会话组装后放入 Task prompt）：

1. 任务目标（用户原话 + 本次要回答的问题）
2. 标的代码与名称（已归一化为纯 6 位）
3. 已抓取的底稿数据：行情、资金流、板块归属、公告/新闻摘要、龙虎榜（JSON 摘要，非原始全量）
4. 输出要求：事实 / 信号 / 判断 / 风险四层，附来源与时间戳

### domain-analyst（行情维度分析）

复盘场景下负责单一维度：

- 指数与打板情绪：指数快照、市场宽度、涨停/炸板/跌停四池、连板梯队、晋级率、赚钱效应
- 板块与题材：行业/概念排行、主线归因、领涨领跌
- 资金与事件：市场资金流、龙虎榜、公告/新闻快照、热度榜

每个 domain-analyst 只对自己的维度负责，结论独立返回，不互相依赖。

### cross-check-reviewer（复查校对，强制）

以未参与分析的第三方视角审查成品报告，审查角度：

1. **事实核对**：报告数字能否在底稿中找到出处；代码/名称是否匹配；时间戳是否为同一交易日。
2. **分层合规**：判断是否被伪装成事实；四层（事实/信号/判断/风险）是否齐全。
3. **来源与 warning**：每个关键结论是否有来源；失败降级、best-effort 数据是否带 warning。
4. **多源冲突**：冲突是否被如实列出（surface，不允许取平均抹平）。
5. **偏差检测**：乐观偏差（淡化风险）、悲观偏差（淡化修复）、确认偏差（只讲支持结论的证据）。
6. **数据质量**：是否混入僵尸报价（成交量=0 且最新价=昨收）、北交所老号段（43/83/87）数据。

输出固定结构：总体评价 → 发现的问题（按严重度排序）→ 每条问题的修改建议 → 是否通过（通过 / 需修改后通过 / 不通过）。

## 编排三阶段（主会话 = orchestrator）

### Phase 1 准备（主会话做，不下放）

1. 任务路由 + 数据域判断。
2. 主会话集中运行 `scripts/stock_replay_cli.py` 抓取数据，底稿落盘（`.analysis/` 下的 JSON）。
3. 为每个 sub-agent 组装结构化上下文：任务、数据摘要、输出契约。

### Phase 2 派发

1. 用 Task 工具并行 launch 各分析型 sub-agent，prompt 中内联角色定义 + 结构化上下文。
2. 分析型 agent 返回后，主会话汇总成报告草稿。
3. 把报告草稿 + 对应底稿交给 `cross-check-reviewer`（串行，必须等草稿完成）。

### Phase 3 整合

1. 按 reviewer 结论分流：
   - `通过`：进入第 2 步。
   - `需修改后通过`：主会话按问题清单逐条修正，修正后交付，无需二次复查（在复查记录中列出修正项）。
   - `不通过`：定位问题出在哪个分析阶段，重跑对应 sub-agent，再走一次 reviewer。二次仍不通过则带 warning 交付并如实说明。
2. 逐条处理 reviewer 意见：采纳的改进报告，不采纳的说明理由。
3. 多 agent 结论冲突时：并列呈现冲突，说明采用哪一个及理由，不取平均。
4. 最终报告按 `references/replay-template.md` 结构落盘，附「复查记录」小节（reviewer 结论 + 处理结果）。

## 硬性规则

1. **取数集中在主会话**：东财限流靠 `em_get()` 的进程内时间戳，跨进程不共享——多个 sub-agent 各自取数等于并发打东财，必封 IP。sub-agent 一律只消费主会话传入的底稿，不取数；底稿缺字段时在结论里标注「缺 X 数据」，由主会话集中补取后重发该 sub-agent。
2. **sub-agent 只返回结构化结论**：不返回大段原始 JSON，控制回传体积。
3. **reviewer 强制**：深度分析、复盘、筛选三类报告未经 reviewer 校对不得交付；快查除外。
4. **冲突必须 surface**：多源、多 agent 结论不一致时如实列出，不静默取舍。
5. **预算意识**：单次编排的 sub-agent 数量建议 ≤5；底稿数据摘要每个 agent ≤2 屏，超出就先压缩。

## Prompt 模板

### symbol-analyst

```
你是 symbol-analyst，只分析一只标的，上下文干净，不受其他标的干扰。

【任务】{用户原话 + 要回答的问题}
【标的】{代码} {名称}
【底稿数据】（主会话已抓取，直接使用，不要重新取数）
{JSON 摘要}

【输出契约】
1. 已确认事实（每条附来源与时间戳）
2. 市场信号
3. 分析判断
4. 风险与待验证点
只返回上述四层结构化结论，不返回原始数据。判断不得伪装成事实。
```

> `domain-analyst` 复用此模板：把【标的】换成【维度】（如「指数与打板情绪」），【底稿数据】换成该维度的底稿，输出契约不变。

### cross-check-reviewer

```
你是 cross-check-reviewer，没有参与本次分析，只做第三方复查校对。

【报告草稿】
{报告全文}

【底稿数据】（用于事实核对）
{JSON 摘要或底稿文件路径}

【审查角度】
1. 事实核对：数字有出处、代码名称匹配、时间戳同一交易日
2. 分层合规：判断未伪装成事实，四层齐全
3. 来源与 warning：关键结论有来源，降级/best-effort 带 warning
4. 多源冲突：如实列出，未取平均抹平
5. 偏差检测：乐观（淡化风险）/悲观（淡化修复）/确认（只讲支持结论的证据）偏差
6. 数据质量：无僵尸报价（成交量=0 且最新价=昨收）、无北交所老号段（43/83/87）脏数据

【输出】总体评价 → 问题清单（按严重度）→ 每条修改建议 → 结论（通过/需修改后通过/不通过）
```
