# Phase 2: 受众分层

将内容拆成两份独立文档，服务不同受众，但共用同一数据池。

目标受众由用户指定，未指定时默认领导层。开工前先确认受众，受众决定汇报版的表达策略：

| 目标受众 | 表达策略 | 术语规则 |
|---|---|---|
| 领导层（默认） | 结论先行、业务能力、管理结论、数据支撑表 | 全部业务化，禁暴露表名/类名/API |
| 技术同行 | 保留架构决策、链路细节、性能与容量数据 | 可保留技术命名，缩写首次出现给全称 |
| 外部客户 | 价值与案例叙事、脱敏数据、品牌语气 | 全部业务化，且隐去内部系统名与敏感口径 |
| 大众/混合 | 故事线优先、每页一个信息点、少数字 | 全部业务化，禁用行话 |

## 两份文档

1. 技术明细版：流程、泳道、异常处理、代码级引用
2. 目标受众汇报版：按上表表达策略从技术版提炼（默认领导层：分层架构、能力总结、管理结论、数据支撑表）

## 执行顺序

1. 先确认目标受众（用户指定，默认领导层）
2. 先写技术明细版，确保对系统全貌理解完整
3. 再写目标受众汇报版，从技术版按受众表达策略提炼
4. 同步产出技术术语映射表，供 Phase 4 检查表达（技术同行受众可精简为缩写对照表）

## Sub Agent 建议

1. 用第一个 sub agent 起草技术明细版，保证链路和异常处理完整
2. 目标受众汇报版如需交给第二个 sub agent，输入必须同时包含同一数据池、技术明细版草稿/定稿和目标受众，按“先技术、后提炼”的链路产出“结论 + 价值 + 风险”表达
3. 主线程负责比较两份草稿，确认汇报版没有绕过技术版单独造结论，且数据一致、术语映射一致，再统一落盘

## 技术术语翻译规则

面向领导层、外部客户、大众受众时，汇报版中不允许直接暴露（技术同行受众豁免，仅需缩写给全称）：

1. 数据库表名
2. Java 类名
3. API 路径
4. 无解释的内部缩写

术语映射表示例：

```markdown
## 技术术语映射表

| 技术命名 | 业务名称 | 说明 |
|---|---|---|
| ota_upgrade_task | 升级任务管理 | 升级任务的生命周期管理表 |
| UpgradePushService | 升级推送服务 | 负责向设备推送升级指令 |
| POST /api/upgrade/push | 推送升级指令 | 触发设备升级的 API |
| FOTA | 固件远程升级（FOTA） | Firmware Over-The-Air |
```
