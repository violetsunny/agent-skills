## Context

See `proposal.md` for motivation. 当前仓库已经沉淀了多类 skill 和 OpenSpec 能力，也已有对多个爬虫项目的调研索引，但缺少一个面向“直接执行抓取任务”的独立 crawler skill。该 skill 需要在仓库内以 project-local 目录存在，既能独立部署，又能清晰表达通用网页抓取、社媒专项优化和反爬/浏览器自动化三类能力的边界。

## Goals / Non-Goals

**Goals:**

- 定义一个最小闭环的 crawler skill 目录模型，便于独立部署和本仓库存放。
- 统一对外任务契约，使通用网页抓取、社媒专项优化和浏览器自动化共用一套输入语法。
- 定义稳定的输出契约，包括结果、运行摘要、错误摘要和调试产物。
- 为后续扩展更多平台适配和执行后端预留空间，而不破坏外部契约。

**Non-Goals:**

- 不在设计阶段锁定唯一执行库，例如 Playwright、Scrapy、curl_cffi 或 Selenium。
- 不承诺支持所有社媒平台的专有逆向签名与风控绕过逻辑。
- 不把该 skill 设计成知识门户、索引页或纯参考型 skill。
- 不在本设计中引入数据库落地、任务队列或远程服务编排等额外系统。

## Decisions

### 1. 统一任务契约，允许多执行模式

skill 对外暴露单一任务语法，允许在任务中声明目标 URL 或平台、抓取目标、页面类型、执行模式、输出格式、浏览器/代理/登录态选项。这样可以让调用者使用一个稳定入口，同时把 HTTP 模式和浏览器自动化模式作为内部可切换能力层。

备选方案是拆成多个 skill，例如一个通用爬虫 skill、一个社媒 skill、一个浏览器自动化 skill。未采用该方案，因为用户目标明确要求这三类能力组合为一个能独立做事的 skill，而且拆分后会导致调用入口分裂、任务契约重复。

### 2. 将社媒专项优化建模为能力层，而不是独立产品层

社媒平台抓取在本设计中属于 crawler skill 的增强层，提供动态渲染、登录态复用、评论/子评论抓取、搜索模式和创作者主页模式等规范行为。这样可以保持 skill 的对外概念一致，同时明确“社媒专项优化”是对通用抓取流程的扩展。

备选方案是单独创建社媒 skill。未采用，因为首版需求强调一个统一的独立部署 skill，而不是多个松散技能集合。

### 3. 执行后端划分为轻量 HTTP 模式与浏览器自动化模式

轻量 HTTP 模式面向静态页面、简单列表和详情抓取；浏览器自动化模式面向 JS 渲染、登录态依赖、滚动加载和反爬挑战页。任务契约中显式支持模式选择，并定义从 HTTP 升级到浏览器模式的触发边界和可观测输出。

备选方案是只保留浏览器自动化模式。未采用，因为这样会让首版 skill 在简单抓取场景下成本过高，也不利于定义清晰的能力分层。

### 4. 独立部署采用最小闭环目录结构

实现时使用仓库内 `skills/<skill-name>/` 目录，至少包含 `SKILL.md`、`scripts/`、`examples/`、`references/` 和配置样例文件。这样既符合当前仓库已有 `skills/` 组织方式，也满足独立部署所需的说明、脚本、样例和参考信息闭环。

备选方案是放到 `.agents/skills/`。未采用，因为当前仓库已经存在大量 project-local `skills/<name>/SKILL.md` 目录，可直接复用既有布局。

### 5. 优先显式失败，不做伪成功降级

当任务涉及未支持平台签名、专有逆向逻辑、缺少浏览器依赖或代理不可用时，skill 必须明确输出不支持或配置缺失，而不是静默降级为部分结果。这样可以保持调用边界清晰，符合“fail visibly”约束。

### 6. 输出契约采用“四段式”

每次运行都约定输出抓取结果、运行摘要、错误摘要和调试产物路径。这让 skill 在成功、部分失败和完全失败时都有统一的可观察结构，也便于后续脚本实现和问题定位。

## Risks / Trade-offs

- [统一语法覆盖面过宽] -> 通过任务字段分层和明确必填/选填项来控制复杂度，避免把平台专有逻辑硬塞入通用字段。
- [社媒能力过深演变成逆向项目] -> 在 spec 中明确“支持的平台能力”与“需专项适配的平台能力”边界，对未支持签名显式失败。
- [多执行模式增加实现复杂度] -> 首版只要求提供最小脚本入口和模式切换契约，避免过早实现完整抓取引擎。
- [独立部署与仓库耦合边界不清] -> 使用 skill 自带脚本、样例和配置，避免依赖仓库其他模块提供运行时服务。

## Migration Plan

1. 恢复并确认 proposal/spec/design/tasks 工件一致。
2. 在 `skills/` 下创建新的 crawler skill 目录骨架。
3. 实现最小可运行的脚本入口、任务解析和样例配置。
4. 补充通用抓取、社媒专项优化和浏览器自动化的文档与参考材料。
5. 根据完成情况更新 `tasks.md` 并验证 change 已可进入完整 apply。

## Open Questions

- 首版是否需要在示例中内置具体社媒平台名称，还是先用平台类型和能力矩阵描述即可。
- 默认结果落地形式是否仅限文件输出，还是需要在后续 change 中补充数据库或外部存储接口。
