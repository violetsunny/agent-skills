# ADR 标准模板

严格使用以下结构生成 ADR 文档，不删减任何必填章节。

```markdown
# ADR-{三位数字编号}：{简洁决策标题}

- **状态**：Proposed | Accepted | Deprecated | Superseded
- **日期**：{YYYY-MM-DD}
- **作者**：{姓名/团队}
- **最后修改**：{YYYY-MM-DD}

## 上下文

完整描述当前业务背景、技术栈约束、团队规模、性能指标、工期压力、现存痛点、业务诉求，把技术问题讲清楚。

## 决策

我们决定采用{最终方案名称}。具体来说：
- 选用的组件/框架/版本明细
- 落地实现的具体方式、架构分层、接入规则
- 明确不做的边界范围，规避范围蔓延

## 后果

### 正面：
- 正面影响1（性能/开发效率/维护成本/业务支撑能力）
- 正面影响2（扩展性/兼容性/运维成本）

### 负面：
- 负面影响1（学习成本、运维复杂度、第三方依赖风险）
- 负面影响2（短期改造成本、资源开销、技术债务）

## 替代方案

- 方案A：{完整描述}
  - 优势：xxx
  - 劣势：xxx
  - 不选择核心原因：xxx

- 方案B：{完整描述}
  - 优势：xxx
  - 劣势：xxx
  - 不选择核心原因：xxx

## 撤销条件

当以下条件出现时，应当重新评审、修订或废弃本架构决策：
- 条件1：业务量级翻倍、性能指标无法满足
- 条件2：底层核心框架停止维护、存在高危安全漏洞
- 条件3：出现成本差距50%以上的更优标准化方案
- 条件4：团队人员结构变更，无人员维护该技术栈

## 变更历史

| 日期 | 变更类型 | 原因 | 操作人 |
| ---- | -------- | ---- | ------ |
| {YYYY-MM-DD} | 创建 | 首次编写架构决策文档 | {作者姓名} |
```

## 校验清单

- [ ] 编号从 0001 递增，保持唯一
- [ ] 状态为四种合法值之一
- [ ] 后果至少 2 正面 + 2 负面
- [ ] 替代方案至少 2 个，每个含优势/劣势/淘汰原因
- [ ] 撤销条件至少 3 条
- [ ] 变更历史首行已填充创建记录

## 状态流转规则

```
Proposed → Accepted → (Deprecated | Superseded)
```

- **Proposed**：待评审，尚未采纳
- **Accepted**：已采纳，正在或即将落地
- **Deprecated**：弃用，不再推荐使用
- **Superseded**：被新 ADR 替代，需标注替代者编号
