# Skill: ADR-Generator

## 元信息
- 名称：ADR架构决策记录生成器
- 版本：v1.0
- 作者：后端架构团队
- 功能定位：根据业务/技术需求，自动生成标准规范ADR架构决策文档，严格遵循统一仓库模板
- 触发关键词：ADR、架构决策记录、架构方案选型、技术方案归档、架构文档、决策记录
- 支持输出格式：标准Markdown ADR文件，适配仓库 `docs/adr/` 目录存放规范

## 能力约束
1. 严格使用统一ADR模板结构，不删减任何必填章节：头部元信息、上下文、决策、后果、替代方案、撤销条件、变更历史
2. 状态仅允许四种：Proposed（待评审）/ Accepted（已采纳）/ Deprecated（弃用）/ Superseded（被新方案替代）
3. 后果必须至少2条正面、2条负面；替代方案不少于2个，每个方案写明优缺点+淘汰原因
4. 自动生成可直接存入代码仓库的文件命名：`ADR-数字编号-标题.md`
5. 输出完整可复制的Markdown文档，附带文件存放路径建议：`仓库根目录/docs/adr/`
6. 自动填充变更历史首行创建记录，预留后续修改行

## 使用指令

### 快捷调用
`/adr-generator` + 需求描述

### 输入必填信息（用户缺少则主动询问补齐）
1. 本次架构要解决的核心业务/技术问题
2. 候选技术方案（至少2个，最多4个）
3. 最终选定的方案
4. 作者/团队名称
5. 预期文档编号（无则自动分配001递增格式）

## 交互流程

1. 用户触发技能后，校验输入信息完整性，缺失信息逐条提问
2. 整理用户需求，填充完整结构化ADR
3. 输出两段内容：
   - ① 仓库存放指引：文件路径、文件名规范
   - ② 完整可复制ADR Markdown正文
4. 附加优化建议：如何更新变更历史、如何修改状态、如何Superseded旧ADR

## 输出示例

```
# 文件存放路径：项目仓库/docs/adr/ADR-012-行情数据统一缓存方案.md

# ADR-012：行情数据统一缓存方案

- **状态**：Proposed
- **日期**：2026-08-02
- **作者**：量化后端组
- **最后修改**：2026-08-02

## 上下文

当前量化交易系统行情接口QPS峰值8000，原始MySQL查询延迟200ms以上，无法满足低延迟交易需求；现有服务无统一缓存层，各个业务模块各自缓存，数据不一致、内存占用失控；技术栈固定JDK21、SpringBoot3.2，容器集群部署，要求数据一致性1s内、延迟降低至20ms以内，工期2周完成改造。

## 决策

我们决定采用Redis Cluster作为全局行情缓存。具体来说：
- 选用Redis 7.2 Cluster三主三从集群，开启持久化RDB+AOF混合持久化
- 使用Spring Data Redis统一封装缓存工具类，统一key命名规范、过期策略
- 不做：不落地全量历史行情、不基于Redis做复杂聚合计算、不跨机房同步缓存

## 后果

### 正面：
- 行情接口平均延迟降至15ms，峰值QPS支撑2万，满足交易低延迟要求
- 全局统一缓存管控，消除多模块数据不一致问题，减少重复数据库查询

### 负面：
- 新增Redis集群运维成本，需要额外监控内存、分片槽位、主从同步状态
- 存在缓存击穿、雪崩风险，需要额外开发过期随机偏移、互斥锁防护逻辑

## 替代方案

- 方案A：本地Caffeine进程内存缓存
  - 优势：无网络IO，延迟最低，无第三方组件依赖
  - 劣势：多实例数据不一致，内存无法共享，单机内存上限约束数据量
  - 不选择核心原因：集群多节点部署，无法保证多实例行情数据实时统一，存在交易数据错乱风险

- 方案B：H2内存数据库
  - 优势：支持SQL复杂查询，兼容现有数据库代码
  - 劣势：重启丢失数据，集群无法共享内存，海量行情数据占用JVM堆内存引发GC卡顿
  - 不选择核心原因：无法集群共享，堆内存溢出风险高，不符合7*24稳定交易要求

## 撤销条件

当以下条件出现时，应当重新评审、修订或废弃本架构决策：
- 条件1：行情QPS突破5万，Redis集群分片扩容成本超出预算30%
- 条件2：行情数据要求强一致性，1s延迟窗口无法满足交易业务规则
- 条件3：公司引入统一分布式缓存中间件，统一替换Redis技术栈
- 条件4：运维团队无法承接Redis集群日常故障排查、版本升级工作
```

## 注意事项

1. **ADR 编号**：从 0001 开始递增，保持唯一性
2. **状态流转**：Proposed → Accepted → (Deprecated | Superseded)
3. **不可变性**：已 Accepted 的 ADR 不应修改，如需变更应创建新的 ADR 并标记 Superseded
4. **简洁性**：每个 ADR 聚焦一个决策，避免混杂多个主题
5. **可追溯性**：变更历史要完整记录
