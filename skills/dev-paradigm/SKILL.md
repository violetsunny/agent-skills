# 开发范式工作流

七阶段固定编排，前一阶段的"闸门"未通过不进入下一阶段。每阶段绑定固定命令，主流程不可跳过，特殊路径见下文。

```
需求对齐 → 拆分任务 → 确认执行 → Review → 测试执行 → 修复 → 修改内容总结
```

## 阶段总览

| # | 阶段 | 命令 | 闸门（通过条件） |
|---|------|------|------------------|
| 1 | 需求对齐 | `/grill-with-docs` | 用户确认需求已清晰 |
| 2 | 拆分任务 | `/to-spec` → `/to-tickets` | 用户审批任务列表 |
| 3 | 确认执行 | `/tdd` + `/implement` | 所有任务编码完成 |
| 4 | Review | `code-review` skill | 问题清单已产出并分级 |
| 5 | 测试执行 | lint + typecheck + tests | 测试通过，Warning 已处理或接受 |
| 6 | 修复 | `/diagnosing-bugs` | 零失败、零未处理 Critical/Warning |
| 7 | 修改内容总结 | `/dev-commit` + `/handoff` | 已提交 + 交接完成 |

---

## 阶段 1：需求对齐

**命令：** `/grill-with-docs`

**做什么：** 用结构化追问把模糊需求想清楚，同步沉淀术语定义和业务约束到项目文档。

**执行要点：**
- 快速场景可降级用 `/grill-me`（不带文档沉淀），但正式开发一律用 `/grill-with-docs`
- 回答 AI 的追问时，把关键决策、边界条件、非目标记录下来
- 编码相关的需求对齐，优先用 `/grill-with-docs`；若涉及不熟悉的领域模型，先用 `/domain-modeling`

**闸门：** 用户明确说出"需求清楚了""可以拆任务了"等确认语，方可进入阶段 2。

---

## 阶段 2：拆分任务

**命令：** `/to-spec` → `/to-tickets`

**做什么：**
1. `/to-spec` — 将阶段 1 的对齐结果转化为结构化规格说明（Spec）
2. `/to-tickets` — 将 Spec 拆解为可独立执行的开发任务列表

**执行要点：**
- 每个 Ticket 应是一个可独立验证的最小工作单元（如"实现手机号校验工具类"而非"做登录功能"）
- Ticket 顺序应有依赖关系标注（哪些可并行、哪些必须前置）
- 核心业务逻辑的 Ticket 标记为"需 TDD"

**闸门：** 用户审批任务列表（确认范围、优先级、拆分粒度合理），方可进入阶段 3。

---

## 阶段 3：确认执行

**命令：** `/tdd` + `/implement`

**做什么：** 按 Ticket 顺序逐个实现，核心逻辑走 TDD（先写测试 → 再写代码 → 最后重构）。

**执行要点：**
- 先输出执行计划（哪些 Ticket 用 TDD、哪些直接编写），让用户确认后再动手
- 每个 Ticket 完成后立即验证该 Ticket 的验收条件
- `/implement` 用于在 TDD 循环中指导具体代码实现
- 遇到不熟悉的代码库，先用 `/domain-modeling` 理解领域模型再编码
- 编码过程中发现需求遗漏，回到阶段 1 补充对齐，不要自行猜测

**闸门：** 所有 Ticket 编码完成，代码可编译/构建通过。

---

## 阶段 4：Review

**命令：** 加载 `code-review` skill

**做什么：** 对本次改动做代码审查，只产出问题清单，不在此阶段修复。修复统一在阶段 6 进行。

**执行要点：**
- Review 范围 = 阶段 3 的全部改动
- 重点关注：是否符合 Spec、是否遵循项目编码规范、是否有安全隐患、是否有性能问题
- Java 项目额外加载 `java-code-review` skill 做空安全/异常处理/并发检查
- Review 结果按严重度分级：Critical（必须修） / Warning（建议修） / Info（可选）
- 产出问题清单后直接进入阶段 5，不在此阶段改代码

**闸门：** 问题清单已产出并分级，无需在此阶段修复。

---

## 阶段 5：测试执行

**命令：** 运行项目的 lint + typecheck + 测试套件

**做什么：** 全量验证，确保改动没有引入回归。

**执行要点：**
- 先跑 lint 和 typecheck（静态检查），再跑测试（动态验证）
- 测试覆盖：单元测试 + 集成测试 + 阶段 3 中 TDD 写的测试
- 记录所有失败的测试用例和错误信息
- 如果全部通过且 Review/测试中的 Warning 均已处理或经用户确认接受，直接跳到阶段 7
- 如果有测试失败、未修复的 Critical，或存在尚未处理的 Warning，进入阶段 6

**闸门：** 全部测试通过，且 Review/测试中的 Warning 已处理或经用户确认接受。否则进入阶段 6。

---

## 阶段 6：修复

**命令：** `/diagnosing-bugs`

**做什么：** 统一修复阶段 4 Review 产出的 Critical/Warning 问题和阶段 5 测试中发现的问题。

**执行要点：**
- 先复现问题，再定位根因，最后修复——禁止盲目猜测
- 优先修 Critical，再修未被用户接受的 Warning；Info 级问题记录到交接文档，不在本轮修
- 每次修复后重新运行相关测试验证
- 修复引入新问题时，回到阶段 5 重跑全量测试
- 最多重试 3 轮（阶段 5↔6 循环）；超过 3 轮仍有失败，暂停并向用户报告当前状态和剩余问题
- 复杂架构问题可用 `/improve-codebase-architecture` 评估结构性改进

**闸门：** 零失败测试，且不存在未修复的 Critical 或未处理的 Warning。回到阶段 5 验证通过后进入阶段 7。

---

## 阶段 7：修改内容总结

**命令：** `/dev-commit` + `/handoff`

**做什么：**
1. `/dev-commit` — 生成规范提交说明并执行提交
2. `/handoff` — 生成交接文档（决策记录、待优化点、测试情况）

**执行要点：**
- 提交前确认改动范围，排除无关文件（如 `__pycache__`、临时文件）
- 提交说明遵循三行格式（TYPE / JIRA / DIFF）
- 交接文档记录：技术决策及理由、已知限制和待优化项、测试覆盖情况、后续建议
- 最终交接用 `/handoff`

**闸门：** 代码已提交 + 交接文档已生成。流程结束。

---

## 特殊路径

特殊路径跳过主流程的前置阶段，但 Review → 测试 → 修复 → 总结 的验证收尾顺序与主流程一致。

### 纯 Bug 修复（跳过阶段 1-3）

当任务是修复已知 Bug 而非新功能开发时，`/diagnosing-bugs` 同时承担诊断和编码（≈ 阶段 3）：
1. `/diagnosing-bugs` — 复现、定位、修复（≈ 阶段 3 编码）
2. `code-review` skill — 审查修复（= 阶段 4）
3. 测试执行 → 修复 → 修改内容总结（= 阶段 5-7）

### 纯重构（跳过阶段 1-2）

当任务是不改行为的结构优化时：
1. `/improve-codebase-architecture` — 分析并规划（≈ 阶段 2 拆分）
2. `/tdd` + `/implement` — 确保重构不破坏行为（= 阶段 3）
3. Review → 测试执行 → 修复 → 修改内容总结（= 阶段 4-7）

---

## 守则

1. 前一阶段闸门未通过，不进入下一阶段
2. 编码中发现需求问题，回退到阶段 1 重新对齐，不自行猜测
3. 每个阶段完成后向用户汇报进度并请求确认
4. 提交前必须通过 lint + typecheck + 测试，不允许跳过验证直接提交
5. 交接文档不是可选步骤——每次开发结束时都必须生成
