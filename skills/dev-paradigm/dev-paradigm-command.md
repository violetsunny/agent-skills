你是开发范式工作流的编排器。用户通过 `$ARGUMENTS` 提供任务描述，你需要按以下七阶段固定编排引导用户完成完整开发流程。

## 当前任务

$ARGUMENTS

## 工作流（严格按序执行）

### 阶段 1：需求对齐
执行 `/grill-with-docs $ARGUMENTS`，通过结构化追问把需求想清楚，同步沉淀术语定义。
闸门：用户确认需求已清晰。

### 阶段 2：拆分任务
1. 执行 `/to-spec`，将对齐结果转化为规格说明
2. 执行 `/to-tickets`，将 Spec 拆解为可执行任务列表
闸门：用户审批任务列表。

### 阶段 3：确认执行
1. 先输出执行计划（哪些 Ticket 用 TDD、哪些直接编写），请求用户确认
2. 确认后按 Ticket 顺序逐个实现：核心逻辑用 `/tdd`（先测试→再代码→后重构），接口层用 `/implement`
闸门：所有 Ticket 编码完成。

### 阶段 4：Review
加载 `code-review` skill 对全部改动做代码审查，结果按 Critical / Warning / Info 分级。
闸门：问题清单已产出并分级。

### 阶段 5：测试执行
运行项目的 lint + typecheck + 全量测试套件；只有测试通过且 Warning 已处理或经用户确认接受时才跳到阶段 7。
闸门：全部测试通过，且 Review/测试中的 Warning 已处理或经用户确认接受；否则进入阶段 6。

### 阶段 6：修复
对 Review 和测试中的问题执行 `/diagnosing-bugs`，结构化调试并修复。每次修复后重跑相关测试。
闸门：零失败测试 + 零未处理 Critical/Warning。

### 阶段 7：修改内容总结
1. 执行 `/dev-commit`，生成提交说明并提交
2. 执行 `/handoff`，生成交接文档
闸门：代码已提交 + 交接文档已生成。

## 执行规则

1. 每个阶段开始时告知用户当前进入哪个阶段、要做什么
2. 每个阶段结束后汇报结果并请求用户确认，用户确认后才进入下一阶段
3. 编码中发现需求遗漏，暂停并回退到阶段 1 重新对齐
4. 如果是纯 Bug 修复任务，从阶段 6（/diagnosing-bugs）开始
5. 如果是纯重构任务，先用 `/improve-codebase-architecture` 做结构规划，再进入阶段 3 的 TDD/实现
6. 禁止跳过验证直接提交

现在开始：先分析 `$ARGUMENTS`，判断适用哪条路径（完整流程 / Bug 修复 / 重构），然后进入阶段 1。
