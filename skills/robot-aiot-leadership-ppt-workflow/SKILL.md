# Robot AIoT 领导汇报 PPT 工作流

将技术项目数据转化为领导可读的 PPT 汇报，核心原则：
**让领导一目了然，一眼看懂** — 每页必须有业务价值结论 + 数据支撑，
不讲代码实现。

本技能覆盖从原始数据到最终 PPTX 的全链路，涉及三个外部技能调用：
- **robot-aiot-draw-flowchart** — 在文档分层完成后，生成分层架构图/流程图 XML
- **robot-aiot-xml-html-bridge** — 在 XML 生成后，稳定转换为 HTML 预览稿，作为 PPT 前的主约束
- **ppt-master** — 在母稿逐页 HTML 化后，agent 依据每页 HTML 手工编写 SVG 页面，由 ppt-master 生成最终 PPTX 文件

强制中间层原则：
- **XML 先转 HTML**：凡是由 `robot-aiot-draw-flowchart` 生成的图表 XML，在进入 PPT 阶段前必须先通过 `robot-aiot-xml-html-bridge` 转成 HTML 预览文件
- **母稿逐页转 HTML**：在调用 `ppt-master` 之前，必须把 PPT 母稿的每一页都落成单页 HTML
- **按 HTML 转 PPT**：agent 依据每一页 HTML 的结构、样式、层级手工编写 ppt-master 支持的 SVG 页面，不是 ppt-master 直接读 HTML
- **没有 HTML 不得生成 PPT**：只要图表 HTML 或页面 HTML 未完成，PPT 生成阶段不得开始

---

## 输出目录约定

所有输出产物统一放在当前运行项目的 `doc-ppt/` 目录下，不散落到其他位置。

```
doc-ppt/
├── <chart-name>.xml            — 图表 XML（Phase 3，robot-aiot-draw-flowchart 产出）
├── <chart-name>.html           — 图表 HTML（Phase 3.5，robot-aiot-xml-html-bridge 产出）
├── <project>_PPT母稿.md        — 母稿（Phase 4）
├── pages/                      — 逐页 HTML（Phase 4）
│   ├── 01-cover.html
│   ├── 02-overview.html
│   └── ...
└── <project>.pptx              — 最终 PPTX（Phase 5，ppt-master 产出）
```

## 工作流总览

```
Phase 1: 方案基础     → 提取真实指标，建立统一数据池（单一数据源）
Phase 2: 受众分层     → 技术明细版MD + 领导汇报版MD（同一数据，不同表达）
Phase 3: 图表生成     → 调用 robot-aiot-draw-flowchart 生成分层架构图/流程图 XML
Phase 3.5: 桥接转换  → 调用 robot-aiot-xml-html-bridge 将 XML 稳定转 HTML 并保留原样式
Phase 4: PPT母稿     → 按页结构化：标题→结论→数据→话术，并将每页落成 HTML 页面样式
Phase 5: PPT生成     → 调用 ppt-master，agent 依据每页 HTML 手工编写 SVG，生成最终 PPTX
```

每个阶段产出是下一阶段的输入，逐级收敛。

## Phase 1: 方案基础 — 数据池建立

在写任何汇报内容之前，先建立**唯一数据源**。所有页面从数据池引用，
不允许任何页面自造数字。

### 为什么

- 不同页面出现同一指标的不同数值，汇报当场就会失去可信度。
- 数据池集中管理后，修正一处即全局生效。
- 先定"有哪些指标"再定"怎么展示"，结构更清晰。

### 怎么做

1. **从源头提取真实指标**：读代码、SQL、配置文件、API 返回、CSV/Excel 数据、监控看板或数据库结果。每个数字必须可追溯来源 — 不能凭空编造。估算值用 `~` 前缀标注，并注明估算依据。
2. **建立数据池表**：列含 `数据项 | 口径说明 | 数值 | 用于页面`，作为后续所有内容的引用源。
3. **区分快照与累计**：每个指标标注是当前快照（瞬时值）还是历史累计。混用是汇报中最常见的数据错误。
4. **估算值显式标记**：非直接测量的值必须带 `~` 前缀，并在"数据使用提醒"子表中说明估算方法。
5. **定义计算口径**：派生指标（如成功率）在数据池中写清计算公式，消除歧义。

### 数据池模板

```markdown
## 核心数据池

| 数据项 | 口径说明 | 数值 | 用于页面 |
|---|---|---:|---|
| <指标名> | <计算口径> | <数值> | <用于哪些页> |

### 数据使用提醒

| 数据项 | 使用提醒 |
|---|---|
| <指标> | <注意事项：快照/累计、估算依据等> |
```

## Phase 2: 受众分层 — 技术明细版 + 领导汇报版

将内容拆分为**两份独立文档**，服务不同受众：

1. **技术明细版**（给工程团队）：完整流程图、泳道图、阶段拆解、异常处理、代码级引用
2. **领导汇报版**（给管理层）：分层架构、能力总结、管理结论、数据支撑表

两份文档共用 Phase 1 的数据池，但表达方式不同。

### 为什么

- 工程师要理解"怎么做的"——需要流程图、异常路径、代码引用
- 领导要理解"能做什么、有多稳"——需要架构图、能力表、一句话结论
- 混在一起写，对领导太技术、对工程师太高层面

### 怎么做

1. **先写技术明细版**：它迫使你彻底理解系统全貌。包含：完整流程图（Mermaid）、泳道图、阶段拆解、异常处理、版本治理、配置机制。
2. **再写领导汇报版**：从技术版中提炼：管理结论（每主题一句话）、分层架构描述、能力看板（数据表）、逐页能力摘要。

### 技术明细版结构参考

```markdown
# <项目> 技术明细版

## 一、系统概述
## 二、全流程图（Mermaid）
## 三、泳道图与角色分工
## 四、阶段拆解与异常处理
## 五、版本治理与配置机制
## 六、扩展能力与生态支撑
```

### 领导汇报版结构参考

```markdown
# <项目> 领导汇报版

## 一、管理结论（每主题一句话）
## 二、分层架构描述
## 三、能力看板（数据表）
## 四、逐页能力摘要
## 五、数据口径说明
```

## Phase 3: 图表生成 — 调用 robot-aiot-draw-flowchart

技术明细版和领导汇报版的 MD 文档完成后，**立即调用 `robot-aiot-draw-flowchart`
技能**，生成汇报所需的图表 XML 文件。

### 为什么

- 图表是领导汇报的视觉锚点 — 领导先看图再看字。
- 分层架构图能在一屏内表达系统全貌和能力定位。
- 流程图能直观展示闭环逻辑，比文字描述更高效。
- draw.io XML 格式可编辑、可渲染、可嵌入 PPT。

### 怎么做

1. **确定图表类型**：根据汇报内容选择：
   - **分层架构图**：系统架构展示、多模块分层说明（推荐用于 PPT 首页主视觉）
   - **泳道流程图**：多角色协作流程
   - **线性/分支流程图**：单链路升级流程
   - **循环流程图**：重试机制、闭环治理

2. **调用 robot-aiot-draw-flowchart 技能**：
   - 使用 `skill` 工具加载 `robot-aiot-draw-flowchart`
   - 该技能提供统一的图标样式、配色方案和 XML 生成能力
   - 从 `references/layered-architecture.md` 加载分层架构图绘制规范（如适用）
   - 从 `references/flowchart-patterns.md` 加载流程图绘制规范（如适用）

3. **图表内容原则**：
   - **架构图是业务能力图，不是技术架构图** — 展示系统"能做什么"，不是"怎么搭的"
   - 图表底部添加**数据锚点**（2-3个关键数字），证明系统是已落地的实际系统
   - **首页架构图定基调**：首页分层架构图确立 PPT 全局的配色方案和视觉基调，后续页面沿用该配色体系
   - **后续页面多样式**：首页架构图风格简洁庄重，但后续页面应采用多种数据可视化样式（看板卡片、漏斗图、对比表、闭环链路图、数据带等），充分展示系统业务能力，不要全部沿用首页的简洁风格
   - 数据值、品牌名称等必须与 Phase 1 数据池一致

4. **产出文件**：保存 `.xml` 文件，放在 `doc-ppt/` 目录下，作为图表真源，供 Phase 3.5 转换使用。

### 图表引用方式

在 PPT 母稿中引用图表：
```markdown
- 图表源文件：`doc-ppt/<图表文件名>.xml`
- 图表状态：Phase 3 已完成，待进入 Phase 3.5 转换
```

## Phase 3.5: XML 到 HTML 桥接转换 — 调用 robot-aiot-xml-html-bridge

在 Phase 3 图表 XML 生成后，**必须立即调用 `robot-aiot-xml-html-bridge` 技能**，
把 XML 转成 HTML 预览稿。

### 为什么

- 领导汇报 workflow 现在把 HTML 视为 PPT 生成前的主约束层
- XML 虽然是真源，但不适合直接做页面编排审查
- 先把 XML 落成 HTML，才能稳定检查视觉结果、冻结样式，再进入页面级 HTML 编排

### 怎么做

1. 使用 `skill` 工具加载 `robot-aiot-xml-html-bridge`
2. 把 `doc-ppt/<图表文件名>.xml` 作为输入，生成 `doc-ppt/<图表文件名>.html`
3. 校验 HTML 是否保留 XML 的原有样式、布局层级、尺寸比例和关键标签关系
4. 只有当 HTML 校验通过后，才允许进入 Phase 4

### 产出文件

```markdown
- 图表真源：`doc-ppt/<图表文件名>.xml`
- 图表 HTML：`doc-ppt/<图表文件名>.html`
```

### 阻塞规则

- 没有完成图表 HTML，不允许进入母稿逐页 HTML 化
- 图表 HTML 与 XML 视觉不一致，不允许进入 PPT 阶段
- 任何 XML 改动后，关联图表 HTML 必须重生

## Phase 4: PPT母稿 — 按页结构化

将汇报内容结构化为**母稿**（Markdown 文档），定义每页内容。母稿是数据分析和
最终 PPTX 之间的桥梁；但真正进入 PPT 生成前，还必须补齐一层**逐页 HTML 页面稿**。

### 为什么

- 先用 Markdown 写内容，聚焦"说什么"而非"怎么排版"
- 文本格式便于审查、修改和交叉校验数据一致性
- HTML 可以先把每页的视觉结构、内容层级、图表摆位、留白和重点样式固定下来
- 最终 PPTX 生成（Phase 5）应变成从 HTML 到幻灯片的机械还原，而不是从 Markdown 直接猜版式

### 每页四要素

每页必须包含：

```markdown
## 第 N 页：<页面标题>

### 标题
> <一句话定位 — 这页证明什么>

### 页面结论
> <一句话结论 — 听众应带走什么>

### 页面上屏内容
<表格、图表、关键数据 — 实际上屏的内容>

### 汇报话术
- <要点 — 展示这页时说什么>
```

### 内容原则

1. **一页一主题**：每页回答一个问题。一页回答两个问题就拆。
2. **数据先行，话术跟上**：每页必须有数据支撑表或数字标注。话术解释数据"意味着什么"，不重复数据"是什么"。
3. **业务价值一句话**：每行数据加一个"业务价值"列，说明"为什么这对业务重要"。领导先读价值列，再读数据列。
4. **极简锚点**：视觉页（架构图、流程图）下方加 2-3 个数字锚点。示例：`85.8万台 | 3个区域 | 99.99%+`。证明图代表的是真实系统。
5. **闭环表达**：描述流程时用闭环结构：`准备 → 执行 → 治理`，配表说明每阶段**实际承载了什么**，不只是标签。

### 母稿模板

```markdown
# <项目> 领导汇报PPT母稿

## 一、汇报总原则
### 首页核心结论
> <全文一句话主旨>

### 全场主线
- <主线1>
- <主线2>

## 二、核心数据池
<Phase 1 数据池表>

## 三、N 页 PPT 页面母稿

## 第 1 页：<标题>
### 标题 / 页面结论 / 上屏内容 / 汇报话术
（引用 Phase 3.5 生成的图表 HTML，XML 作为图表真源追溯）

## 第 2 页 ...
...

## 四、可直接复用的领导口径
## 五、数据口径说明
## 六、上会前校准清单
```

### 母稿扩展原则

在母稿基础内容完成后，逐页做"业务能力 + 数据支撑"扩展：
- 每页增加 1-2 个能力落脚点，不堆砌话术
- 视觉页加数字锚点，让领导一眼确认系统规模
- 数据表加"业务价值"列，一句话说清能力价值
- 流程页加"实际承载"列，让闭环不空洞
- 漏斗/递进页加一句话递进逻辑
- 治理页加一句话闭环：`可查 → 可隔离 → 可修复`
- 案例页加横向对比结论

### 设计系统生成（逐页 HTML 化前置步骤）

在母稿内容定稿后、逐页 HTML 化之前，先生成与汇报主题匹配的设计系统：

1. **调用 `ui-ux-pro-max --design-system`**：执行 `ui-ux-pro-max --design-system "<项目描述> <行业> <风格关键词>"`（如 `"物联网平台运维 科技蓝 企业级"`），获取设计系统输出，包含：
   - 配色方案（primary color、accent color、辅助色）
   - 字体配对（标题字体 + 正文字体）
   - 间距系统（spacing scale）
   - 反模式建议

2. **加载 `material-3` MD3 间距参考**：读取 `material-3/references/layout-and-responsive.md`，参考 MD3 的 8dp 间距 token 系统（8/16/24/32/48px），作为页面区域间距和内边距的对齐基准

3. **提取注入参数**：从 `ui-ux-pro-max` 输出中提取配色方案、字体配对、间距系统，准备注入 `page-html-template.md` 的 `:root` CSS 变量

#### 配色冲突规则

当 `ui-ux-pro-max` 推荐的主色与首页架构图 XML 确立的主色不一致时：

- **首页架构图主色 MUST 优先**覆盖设计系统推荐的 `--primary-color`
- `ui-ux-pro-max` 的配色作为辅助色和补充色使用
- 保留 `ui-ux-pro-max` 的字体配对、间距系统、辅助色建议，只让出主色

### 逐页 HTML 化要求

在母稿内容定稿后，每一页都要产出一个 HTML 页面文件，作为 PPT 生成的直接参照。
**首先从 `references/page-html-template.md` 加载页面模板**，按模板规范定义的 16:9 画布（1920×1080px）、8 种页面类型布局和样式色板来生成每页 HTML。

要求如下：

1. **一页对应一个 HTML 文件**：建议命名为 `doc-ppt/pages/01-cover.html`、`doc-ppt/pages/02-overview.html`
2. **结构先于美化**：HTML 要先把标题区、结论区、图表区、数据区、备注区的布局固定好
3. **样式可还原**：颜色、字号层级、对齐方式、卡片边框、图表占位比例、页边距都要明确，避免 PPT 阶段再猜
4. **引用图表 HTML**：Phase 3 生成的图表优先以 HTML 形式嵌入页面，而不是只写“这里放一张图”
5. **保留分页意识**：每个 HTML 文件只表达一页幻灯片内容，不能做成长网页
6. **页面 HTML 受图表 HTML 约束**：若页面中嵌入图表，则不得脱离图表 HTML 另画一份风格不同的版本

可采用如下落地方式：

```markdown
## 第 N 页输出物

- 母稿定义：`doc-ppt/<项目>_PPT母稿.md`
- 单页 HTML：`doc-ppt/pages/<页码>-<slug>.html`
- 关联图表：`doc-ppt/<图表名>.html`
```

### 逐页 HTML 生成后检查

每页 HTML 生成后，必须执行以下两项检查：

1. **布局审查清单（10 项）**：从 `references/page-html-template.md` 第 5 节加载布局审查清单，逐项检查画布尺寸、蓝条间距、元素不重叠、分栏均衡、padding、字号下限、箭头可见性、徽章对齐、内容溢出、水平居中。不通过的项需修复后重新检查。
2. **技术表名不外露**：grep 检查 HTML 中是否残留数据库表名（如 `t_device_file_version`、`t_specify_push_record`）或查询口径描述，替换为业务可理解的描述。

## Phase 5: PPT生成 — 调用 ppt-master

母稿定稿并通过交叉校验后，**调用 `ppt-master` 技能**生成最终 PPTX 文件。
agent 依据逐页 HTML 的布局、配色、内容层级，手工编写 ppt-master 支持的 SVG 页面设计，
然后由 ppt-master 生成可编辑的 PPTX。

### 移交前校验清单

在调用 ppt-master 之前，必须完成以下校验：

- [ ] 母稿中所有数据与数据池完全一致
- [ ] `~` 前缀一致（估算值全标、精确值全不标）
- [ ] 无零宽空格（U+200B）等不可见字符
- [ ] 所有表格列数 = 分隔行列数
- [ ] "快照"与"累计"标注清晰
- [ ] Phase 3 生成的图表 XML 已全部通过 `robot-aiot-xml-html-bridge` 转成对应 HTML
- [ ] 图表 HTML 保留 XML 原始样式，且已完成保真校验
- [ ] 每页四要素齐全（标题、结论、上屏内容、话术）
- [ ] 母稿每一页都已生成对应 HTML 页面文件
- [ ] 每页 HTML 的布局、配色、图表占位和数据层级已确认可直接映射到 PPT
- [ ] 图表 HTML 或页面 HTML 任一未完成时，PPT 阶段未提前启动
- [ ] 配色一致性：图表 HTML 与页面 HTML 的主色、强调色来自同一色系，不出现完全不同的配色体系
- [ ] 间距规范：页面 HTML 区域间距 ≥ 16px、内边距 ≥ 20px，尽量对齐 MD3 8dp 倍数（8/16/24/32/48px）

### 调用 ppt-master

使用 `skill` 工具加载 `ppt-master` 技能，提供：

1. **母稿文件路径**（`doc-ppt/<项目>_PPT母稿.md`）— 输入文件必须是 Markdown 格式，ppt-master 对 MD 的解析最稳定
2. **图表 XML 文件路径**（`doc-ppt/<图表名>.xml`）— 作为图表样式追溯源
3. **图表 HTML 文件路径**（`doc-ppt/<图表名>.html`）— 由 `robot-aiot-xml-html-bridge` 生成，作为图表视觉还原参照，要求与 XML 保持一致
4. **逐页 HTML 文件路径**（`doc-ppt/pages/*.html`）— 作为 agent 编写 SVG 的视觉参照，不作为 ppt-master 的直接输入格式；agent 依据每页 HTML 的布局、配色、内容层级手工编写 ppt-master 支持的 SVG 页面
5. **页数和结构**（共 N 页，每页主题）
6. **风格参照说明**：PPTX 的配色方案应参照首页架构图 XML/HTML 确立的视觉基调，保持色彩体系统一；但页面布局和数据展示样式应多样化（看板卡片、漏斗图、对比表、闭环链路、数据带等），充分展示业务能力，不要全部沿用首页的简洁风格

将母稿 MD、图表 XML、图表 HTML、逐页 HTML 一并作为参照材料。
其中**逐页 HTML 是 agent 编写 SVG 页面的视觉参照**，XML 是图表样式追溯源，MD 是内容语义源。三者职责不能混淆。
agent 依据逐页 HTML 的布局、配色、内容层级，手工编写 ppt-master 支持的 SVG 页面设计，然后由 ppt-master 根据自身工作流生成可编辑的 PPTX 文件。
具体渲染能力（图表嵌入、表格格式化、备注填充等）取决于 ppt-master 的路由选择，
本技能不做假设，只确保移交的母稿、图表文件和逐页 HTML 内容完整、格式正确。

> **风格一致性 ≠ 风格单一**：Phase 3 通过 robot-aiot-draw-flowchart 生成的首页
> 架构图 XML 确立了配色方案和视觉基调，调用 ppt-master 时应传达"配色统一、
> 布局多样"。后续页面在保持配色体系统一的前提下，应采用多种数据可视化样式
> 展示系统业务能力，避免所有页面都是简洁风格，要让汇报"酷"起来。

### 移交后的验证

PPTX 生成后，检查：
- [ ] 页数与母稿一致
- [ ] 每页标题与母稿一致
- [ ] 每页 PPT 布局与对应 HTML 基本一致（这是 agent 手工映射后的验证，不是 ppt-master 自动还原）
- [ ] 图表正确渲染，且与图表 HTML/原始 XML 视觉一致
- [ ] 数据表数值与母稿一致
- [ ] 无乱码或格式错位

## 交叉校验（贯穿 Phase 2-5）

从 Phase 2 产出两份 MD 文档起，到 Phase 5 生成 PPTX 后，全程执行系统性交叉校验。
两份 MD 文档间的数据一致性是第一道门 — 技术版和领导版引用同一数据池，数值必须完全匹配。
母稿完成后，跨页数据一致性是第二道门 — 跨页数据不一致会直接摧毁汇报可信度。

### 校验清单

| 检查项 | 验证什么 | 怎么验证 |
|---|---|---|
| **数据一致性** | 同一指标在所有页面数值相同 | Grep 每个关键数字，计数出现次数，验证全部匹配 |
| **表格格式** | 每个表头列数 = 分隔行列数 | 逐表读取，数 header 行和 separator 行的 `|` 数 |
| **不可见字符** | 无零宽空格（U+200B）等 | 扫描文件中 `\u200b`、`\u00a0` 等 |
| **估算标记** | 估算值有 `~`，精确值无 `~` | Grep 每个指标，验证 `~` 一致性 |
| **快照与累计** | 每个指标明确标注是当前快照还是历史累计 | 检查数据池"使用提醒"表覆盖所有指标 |
| **分组合计** | 各分组值之和 = 总计值 | 将各分组数值相加，验证等于总计值 |
| **描述-数值匹配** | 文字描述与数值一致（如"按X估算"时值=X） | 逐条读描述，验证与实际值匹配 |
| **页面引用** | 数据池"用于页面"列与实际页面使用一致 | 逐指标检查，确认出现在所列页面 |

### 常见数据错误

1. **分组合计不匹配**：各分组值之和 ≠ 总计值。通常是混用了不同口径的数值。
2. **估算前缀漂移**：初稿用 `~912`，后续编辑漏掉 `~` 变成 `912`。Grep 可捕获。
3. **描述-数值矛盾**：文字说"按 NA 比例估算"但值已不等于 NA 的值。值变更时需同步更新描述。
4. **零宽空格**：从格式化文本复制可注入 U+200B，导致搜索失败。必须扫描清除。
5. **分隔行列数不匹配**：表头加了一列但忘了在 separator 行加对应的 `|---|`。最常见表格格式 bug。

## 真源与重生顺序

所有产物有明确的上下游关系，数据变更时必须按重生链逐级刷新，不允许跳步。

### 重生链

```
数据池 MD 改动 → 母稿 MD 更新 → 图表 XML 重生 → 图表 HTML 重生 → 页面 HTML 重生
```

- 每一级产物的上游变了，本级必须重生
- 不允许跳过中间环节（如数据池改了直接改页面 HTML，跳过母稿和图表）
- 每次重生后必须重跑交叉校验

### 禁止规则

1. **不允许只手改 HTML 来同步 XML 变更**：XML 变更后，HTML 必须通过 `robot-aiot-xml-html-bridge` 整稿重生
2. **不允许只改页面 HTML 不改母稿**：页面 HTML 的内容来源是母稿，母稿不改就不应该改页面 HTML
3. **不允许只改图表 HTML 不改图表 XML**：图表 XML 是真源，HTML 是桥接层，真源不变就不应该改桥接层

## 迭代修正

母稿不是一次写成的 — 经过多轮迭代修正：

### 迭代循环

```
起草页面 → 用户审查 → 识别问题 → 修正 → 交叉校验 → 用户审查 → 重复
```

### 迭代原则

- **不做加法做减法**：每次迭代应让文档更短，不是更长。加了新内容就要找旧的来删。
- **每改一处，全文校验**：任何数字或描述变更后，重跑完整交叉校验清单。第3页的改动可能破坏第6页的一致性。
- **确认重生链同步**：每次迭代后必须确认重生链中所有下游产物已同步刷新（母稿→图表XML→图表HTML→页面HTML），不能只改了一层就交付。
- **领导视角**：每轮迭代后，从领导视角通读全文母稿。问自己："如果我第一次看，能在30秒内理解结论吗？"

## 总结

本技能的价值在于**方法论，非具体数据**：

1. 数据池先行，所有页面引用同一数据源
2. 受众分层：技术版讲"怎么做的"，领导版讲"能做什么"
3. 文档完成后立即调用 robot-aiot-draw-flowchart 生成图表 XML
4. 再调用 robot-aiot-xml-html-bridge，把 XML 稳定转换为图表 HTML
5. 没有图表 HTML，不得进入页面级 HTML 和 PPT 阶段
6. 按页结构化母稿：标题→结论→数据→话术
7. 逐页 HTML 化前，调用 `ui-ux-pro-max --design-system` 生成配色/字体/间距设计系统，参考 `material-3` MD3 规范，首页架构图主色优先
8. 母稿定稿后，每一页必须先转成单页 HTML，固定样式和布局
9. 调用 ppt-master 时，agent 依据每页 HTML 手工编写 SVG 页面，以 XML 为图表样式追溯源
10. 交叉校验数据一致性和页面一致性，每改一处全文校验
11. 定稿后调用 ppt-master 生成最终 PPTX

具体指标、架构和业务内容因项目而异，但遵循此流程可确保汇报始终数据驱动、口径一致、领导可读。
