# QA 智能体设计指南

在构建哈尼斯时，若需要包含 QA 智能体，可参考本指南。内容基于真实项目（SatangSlide）中发现的 BUG 模式及其根本原因分析，提供一套易于遗漏的缺陷类型以及系统化的验证方法。

## 1. QA 智能体容易遗漏的缺陷模式

### 1-1. 边界接口不一致（Boundary Mismatch）

最常见的缺陷类型：两个组件各自“实现正确”，但在连接处协议不匹配。

| 边界接口 | 不一致示例 | 易被忽略的原因 |
|----------|------------|----------------|
| API 响应 → 前端 Hook | API 返回 `{ projects: [...] }`，Hook 期望 `SlideProject[]` | 单独验证时两侧都“正常”，但未做交叉比对 |
| API 字段名 → 类型定义 | API 使用 `thumbnailUrl`（camelCase），类型定义为 `thumbnail_url`（snake_case） | TypeScript 泛型强制类型转换后编译通过，类型系统不报错 |
| 文件路径 → 链接 href | 页面实际路径 `/dashboard/create`，链接却指向 `/create` | 未对文件结构与 href 做交叉检查 |
| 状态转换表 → 实际 status 更新代码 | 状态表中定义 `generating_template → template_approved`，代码中却遗漏该转换 | 只检查状态表存在，不检查所有更新代码是否覆盖全部转换 |
| API 端点 → 前端 Hook | API 端点存在，但没有对应的 Hook（从未被调用） | 未对 API 列表与 Hook 列表做 1:1 映射 |
| 即时响应 → 异步结果 | API 立即返回 `{ status }`，前端却访问 `data.failedIndices` | 未区分同步响应与异步结果之间的结构差异 |

### 1-2. 为何静态代码评审难以捕获这类问题

- **TypeScript 泛型的局限：** 如 `fetchJson<SlideProject[]>()`，即便运行时响应为 `{ projects: [...] }`，编译仍然通过；
- **`npm run build` 通过 ≠ 运行时行为正确：** 类型强制转换、`any`、泛型等都会让编译成功但运行时失败；
- **“存在性检查”与“连接一致性检查”的区别：** 检查“API 是否存在”与检查“API 响应是否符合调用方预期”是完全不同的两种验证。

## 2. 集成一致性验证（Integration Coherence Verification）

集成一致性验证是 QA 智能体中必须包含的 **交叉比较验证** 部分。

### 2-1. API 响应 ↔ 前端 Hook 类型的交叉验证

**方法：** 比较每个 API 路由中 `NextResponse.json()` 的对象结构，与对应 Hook 中 `fetchJson<T>` 的泛型类型 T。

```markdown
验证步骤：
1. 在 API 路由中提取传入 NextResponse.json() 的对象结构（shape）。
2. 在对应 Hook 中查看 fetchJson<T> 的类型参数 T。
3. 比较 shape 与 T 是否一致。
4. 检查是否存在包裹结构：若 API 返回 `{ data: [...] }`，则 Hook 是否正确地提取 `.data`。
```

**特别注意以下模式：**
- 分页 API：API 返回 `{ items: [], total, page }`，前端却直接期望数组；
- DB 中 snake_case 字段经 API 映射为 camelCase，再映射到前端类型时发生不一致；
- 立即响应（如 HTTP 202）与最终结果在结构上的差异。

### 2-2. 文件路径 ↔ 链接/路由路径映射

**方法：** 从 `src/app/` 下的 page 文件中抽取 URL 路径，再与代码中所有 `href`、`router.push()`、`redirect()` 的目标路径进行对比。

```markdown
验证步骤：
1. 从 src/app/ 下的 page.tsx 文件路径中抽取 URL 模式：
   - `(group)` 目录在 URL 中忽略；
   - `[param]` 视为动态路径段。
2. 在代码中收集所有 href=、router.push(、redirect( 的值；
3. 确认每个链接都对应一个实际存在的 page 文件路径；
4. 注意 route group 内页面的 URL 前缀（例如 `dashboard/`）。
```

### 2-3. 状态转换的完整性追踪

**方法：** 提取所有 `.update({ status: "..." })` 调用，并与状态转换表进行对比。

```markdown
验证步骤：
1. 从状态转换表（如 STATE_TRANSITIONS）中提取允许的状态转换列表；
2. 在所有 API 路由中搜索 `.update({ status: "..." })` 模式；
3. 确认每个状态更新都在状态转换表中定义；
4. 找出状态转换表中定义但在代码中从未执行的转换（“死”转换）；
5. 特别检查：从中间状态（如 generating_template）到最终状态（template_approved）的转换是否遗漏。
```

### 2-4. API 端点 ↔ 前端 Hook 的一一映射

**方法：** 列出所有 API 路由及所有前端 Hook，检查是否能形成合理的一一对应关系。

```markdown
验证步骤：
1. 在 src/app/api/ 下的 route.ts 文件中，按 HTTP 方法列出所有 API 端点；
2. 在 src/hooks/ 下的 use*.ts 文件中，列出所有 fetch 调用的 URL；
3. 找出存在但未被 Hook 调用的 API 端点，并标记为“未使用”；
4. 判断“未使用”是否为设计意图（如管理 API），还是调用遗漏。
```

## 3. QA 智能体设计原则

### 3-1. 使用 `general-purpose` 类型，而非 `Explore`

若 QA 智能体使用 `Explore` 类型，则只能读取代码，无法执行脚本或修改代码。然而高效的 QA 通常需要：
- 使用 Grep 进行模式搜索（如提取所有 `NextResponse.json()` 调用）；
- 运行脚本自动比对（如 API shape vs Hook 类型）；
- 必要时提出修改建议或执行修复。

**建议：** 将 QA 智能体设定为 `general-purpose` 类型，并在定义中明确“验证 → 报告 → 发出修改请求”的工作流程。

### 3-2. 检查清单应优先关注“交叉比较”，而非“存在性”

| 弱检查清单 | 强检查清单 |
|------------|------------|
| API 端点是否存在？ | API 响应结构是否与对应 Hook 类型一致？ |
| 状态转换表是否存在？ | 所有 status 更新代码是否符合状态转换表定义？ |
| 页面文件是否存在？ | 所有链接是否指向实际存在的页面？ |
| TS 是否开启严格模式？ | 是否存在通过泛型强制转换绕过类型安全的情况？ |

### 3-3. “同时阅读两侧”的原则

要捕捉边界接口 BUG，仅阅读一侧代码是不够的。必须：
- 同时阅读 API 路由和对应 Hook；
- 同时阅读状态转换表和实际 status 更新代码；
- 同时阅读文件结构和链接路径。

应在智能体定义中明确写出这一原则。

### 3-4. QA 不应只在最终阶段执行，而应在各模块完成后立即执行

若在编排器中仅在“Phase 4：全部完成后”才执行 QA，则：
- BUG 会集中堆积，修复成本更高；
- 早期边界接口不一致会传播到后续模块，加大问题范围。

**推荐模式：** 每个后端 API 完成后，即刻进行该 API 与对应 Hook 的交叉验证（增量式 QA），而不是等待整体结束。

## 4. 验证检查清单模板

适用于 Web 应用的集成一致性检查，建议直接嵌入 QA 智能体定义中。

```markdown
### 集成一致性验证（Web 应用）

#### API ↔ 前端连接
- [ ] 所有 API 路由的响应结构与对应 Hook 的泛型类型一致
- [ ] 包裹结构（如 { items: [...] }）在 Hook 中被正确解包
- [ ] snake_case ↔ camelCase 转换一致且无遗漏
- [ ] 即时响应（202）与最终结果在前端得到正确区分与处理
- [ ] 每个 API 端点均有对应的前端 Hook，并确实被调用

#### 路由一致性
- [ ] 代码中所有 href/router.push 目标路径均对应实际存在的 page 文件
- [ ] 路由组（(group)）在 URL 中被正确忽略或处理
- [ ] 动态段（[id] 等）被正确填充并传递参数

#### 状态机一致性
- [ ] 状态转换表中定义的所有转换在代码中都有实际执行（不存在“死”转换）
- [ ] 所有 status 更新代码对应状态转换表中的合法转换（无“非法”转换）
- [ ] 从中间状态至最终状态的转换路径完整且无遗漏
- [ ] 前端以 status 分支（如 `if status === "X"`）的分支值在运行时确实可达

#### 数据流一致性
- [ ] 数据库字段名与 API 响应字段名的映射保持一致
- [ ] 前端类型定义字段名与 API 响应字段名一致
- [ ] 对可选字段（nullable）的空值处理在前后端保持一致
```

## 5. QA 智能体定义模板

用于在哈尼斯中定义 QA 智能体时参考，可直接调整为具体项目所需。

```markdown
---
name: qa-inspector
description: "QA 验证专家。检查规格符合性、集成一致性以及设计质量。"
---

# QA Inspector

## 核心角色

负责根据规格验证实现质量，并特别关注 **各模块之间的集成一致性**。

## 验证优先级

1. **集成一致性**（最高优先级）—— 边界接口不一致是运行时错误的主要来源；
2. **功能规格符合性**—— API、状态机和数据模型是否符合设计；
3. **设计质量**—— 颜色、排版与响应式布局等；
4. **代码质量**—— 未使用代码与命名规范等。

## 验证方法：“同时阅读两侧”

在进行边界验证时，必须同时打开“生产者”和“消费者”两侧的代码：

| 验证对象 | 左侧（生产者） | 右侧（消费者） |
|----------|----------------|----------------|
| API 响应结构 | route.ts 中的 NextResponse.json() 调用 | hooks/ 中的 fetchJson<T> 调用 |
| 路由 | src/app/ 中的 page 文件路径 | href 与 router.push 的目标路径 |
| 状态转换 | STATE_TRANSITIONS 状态转换表 | `.update({ status })` 的实际代码 |
| DB → API → UI | 数据库表字段 | API 响应字段与类型定义字段 |

## 团队通信协议

- 一旦发现问题，立即向相关智能体发出具体修改请求（包含文件名、行号与建议改法）；
- 对边界问题，必须同时通知边界两侧的智能体；
- 向负责人（编排器）提交验证报告，区分“通过/失败/未验证”项。
```

## 实战案例：SatangSlide 中发现的 BUG

本指南中的所有原则都源自以下实际 BUG 所总结的经验：

| BUG | 边界接口 | 根本原因 |
|-----|----------|----------|
| `projects?.filter is not a function` | API → Hook | API 返回 `{projects:[]}`，Hook 期望数组 |
| 仪表盘所有链接 404 | 文件路径 → href | 链接漏写 `/dashboard/` 前缀 |
| 主题图片不显示 | API → 组件 | 字段名 `thumbnailUrl` vs `thumbnail_url` 不一致 |
| 主题选择无法保存 | API → Hook | 存在 select-theme API 却没有对应 Hook |
| 生成页面一直加载 | 状态转换 → 代码 | 未编写从 `template_approved` 的状态过渡代码 |
| `data.failedIndices` 访问导致崩溃 | 即时响应 → 前端 | 将后台异步结果当作即时响应字段访问 |
| 完成后查看幻灯片 404 | 文件路径 → href | 实际路径 `/dashboard/projects/` 被链接写成 `/projects/` |
