# 智能体团队设计模式

## 执行模式：智能体团队 vs 子智能体

理解两种执行模式的核心差异，并选择合适的模式。

### 智能体团队（Agent Teams）——默认模式

团队负责人通过 `TeamCreate` 创建团队，团队成员作为独立的 Claude Code 实例运行。成员之间通过 `SendMessage` 直接通信，并通过共享任务列表（`TaskCreate`/`TaskUpdate`）进行自我协调。

```
[负责人] ←→ [成员A] ←→ [成员B]
  ↕          ↕          ↕
  └──── 共享任务列表 ────┘
```

**核心工具：**
- `TeamCreate`：创建团队并启动团队成员
- `SendMessage({to: name})`：向特定成员发送消息
- `SendMessage({to: "all"})`：广播消息（成本高，少用）
- `TaskCreate`/`TaskUpdate`：管理共享任务列表

**特点：**
- 成员之间可以直接交流、质疑和相互验证
- 信息可以在成员间直接交换，而不必经由负责人
- 通过共享任务列表进行自我协调（成员可主动请求任务）
- 成员空闲时自动向负责人发出通知
- 可通过“计划审批模式”在危险操作前进行审查

**限制：**
- 每个会话只能 **激活一个团队**（但可以在不同 Phase 间解散旧团队并创建新团队）
- 不支持嵌套团队（团队成员不能再创建自己的团队）
- 负责人固定（不可切换）
- Token 成本较高

**团队重构模式：**
如果每个 Phase 需要不同专家组合，则先将现有团队的产物保存到文件 → 销毁团队 → 创建新团队。之前团队的产物保存在 `_workspace/` 中，新团队可以通过 Read 访问。

### 子智能体（Sub-agents）——轻量模式

主智能体通过 `Agent` 工具生成子智能体。子智能体只将结果返回给主智能体，彼此之间不通信。

```
[主智能体] → [子智能体A] → 返回结果
         → [子智能体B] → 返回结果
         → [子智能体C] → 返回结果
```

**核心工具：**
- `Agent(prompt, subagent_type, run_in_background)`：生成子智能体

**特点：**
- 轻量、快速
- 结果以摘要形式返回主上下文
- Token 使用更经济

**限制：**
- 子智能体之间无法通信
- 所有协调由主智能体承担
- 不适合需要实时协作/相互挑战的场景

### 模式选择决策树

```
智能体数量 ≥ 2 ?
├── 是 → 是否需要智能体之间通信？
│        ├── 是 → 选择智能体团队（默认）
│        │         通过交叉验证、发现共享和实时反馈提升质量。
│        │
│        └── 否 → 可以选择子智能体模式
│                 适用于仅需结果传递的生成-验证、专家池等场景。
│
└── 否（仅 1 个智能体） → 子智能体模式
                    单一智能体无需组建团队。
```

> **核心原则：** 智能体团队是默认模式。只有在确认“成员间通信确实不需要”时，才选择子智能体模式。

## 智能体团队架构类型

### 1. 流水线（Pipeline）

顺序工作流，前一智能体的输出是下一智能体的输入。

```
[分析] → [设计] → [实现] → [验证]
```

**适用场景：** 每一步都强烈依赖前一步的产物。
**示例：** 小说创作——世界观 → 人物 → 剧情 → 写作 → 编辑。
**注意：** 某一环节成为瓶颈会拖慢整个流水线。尽量将各阶段设计得相对独立。
**团队模式适配性：** 顺序依赖较强时，团队模式的优势有限。但若流水线中有可并行的子阶段，团队模式会更有价值。

### 2. 扇出/扇入（Fan-out/Fan-in）

并行处理后再整合结果，适合执行彼此独立的工作。

```
         ┌→ [专家A] ─┐
[分发] → ├→ [专家B] ─┼→ [整合]
         └→ [专家C] ─┘
```

**适用场景：** 需要对同一输入做不同视角/领域的分析。
**示例：** 综合调研——同时调查官方信息、媒体、社区与背景资料 → 整合报告。
**注意：** 最终整合阶段质量决定整体质量。
**团队模式适配性：** 扇出/扇入是智能体团队最自然的模式，**必须使用团队模式**。成员之间共享发现、相互挑战，可以让一个成员的发现实时影响其他成员的研究方向，显著提升整体质量。

### 3. 专家池（Expert Pool）

根据情况选择并调用不同专家。

```
[路由器] → { 专家A | 专家B | 专家C }
```

**适用场景：** 输入类型不同，需要不同处理方式。
**示例：** 代码评审——按安全、性能、架构等不同方向调用对应专家。
**注意：** 路由器的分类准确度是核心。
**团队模式适配性：** 更适合子智能体模式。只调用需要的专家，不必维持常驻团队。

### 4. 生成-验证（Producer-Reviewer）

生成智能体与验证智能体成对工作。

```
[生成] → [验证] → （如有问题）→ [生成] 重新执行
```

**适用场景：** 产出质量非常重要且存在可客观检验的标准。
**示例：** 漫画创作——画师生成 → 审稿人检视 → 有问题的画格重新生成。
**注意：** 必须设置最大重试次数（2~3 次），防止无限循环。
**团队模式适配性：** 团队模式很有价值。通过 SendMessage 在生成者与审稿人间进行实时反馈交换。

### 5. 监督者（Supervisor）

中心智能体管理任务状态，并动态分配子任务给下层智能体。

```
         ┌→ [工人A]
[监督者] ─┼→ [工人B]    ← 监督者观察状态并动态分配
         └→ [工人C]
```

**适用场景：** 工作量可变，且需要在运行时决定任务分配。
**示例：** 大规模代码迁移——监督者分析文件列表并为工人分批分配任务。
**与扇出的区别：** 扇出模式在事先固定任务分配；监督者模式则基于运行时进度进行动态调度。
**注意：** 为防止监督者成为瓶颈，需适当增大单次下发任务的粒度。
**团队模式适配性：** 智能体团队的共享任务列表与监督者模式天然匹配。通过 TaskCreate 管理任务，成员可自行请求任务。

### 6. 分层委派（Hierarchical Delegation）

上层智能体递归地向下层智能体委派任务，用于逐层分解复杂问题。

```
[总负责人] → [组长A] → [执行者A1]
                    → [执行者A2]
         → [组长B] → [执行者B1]
```

**适用场景：** 问题天然具有层次分解结构。
**示例：** 全栈应用开发——总负责人 → 前端组长 →（UI/逻辑/测试）+ 后端组长 →（API/数据库/测试）。
**注意：** 层级超过 3 层容易引起延迟和上下文丢失，建议控制在 2 层以内。
**团队模式适配性：** 团队不支持嵌套（团队成员不能再创建团队）。可采用：第 1 层使用团队模式，第 2 层使用子智能体模式，或将结构扁平化为单一团队。

## 复合模式

实战中常见的是多种模式的组合，而非单一模式：

| 复合模式 | 结构 | 示例 |
|----------|------|------|
| **扇出 + 生成-验证** | 并行生成后分别验证 | 多语言翻译——4 种语言并行翻译 → 各自由母语审稿人检视 |
| **流水线 + 扇出** | 将流水线中的部分阶段并行化 | 分析（顺序）→ 实现（并行）→ 集成测试（顺序） |
| **监督者 + 专家池** | 监督者动态调用专家 | 客户支持——监督者分类问题后分配给适当专家 |

### 复合模式下的执行模式选择

**原则：** 所有复合模式默认使用智能体团队。成员之间的积极沟通是提升结果质量的关键动力。

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| **调研 + 分析** | 智能体团队 | 调研者之间共享发现，并在矛盾信息上进行实时讨论 |
| **设计 + 实现 + 验证** | 智能体团队 | 设计者、实现者与验证者之间形成反馈闭环 |
| **监督者 + 工人** | 智能体团队 | 利用共享任务列表进行动态任务分配和进度共享 |
| **生成 + 验证** | 智能体团队 | 生成者与验证者实时反馈，最小化反复返工 |

> 只有在单一智能体执行完全隔离的、一次性的任务时才考虑混入子智能体模式。

## 智能体类型选择

调用 Agent 工具时，通过 `subagent_type` 参数指定智能体类型。团队成员也可以使用自定义智能体定义。

### 内置类型

| 类型 | 工具访问权限 | 适用场景 |
|------|--------------|----------|
| `general-purpose` | 全部（含 WebSearch、WebFetch） | 网络调研与通用任务 |
| `Explore` | 只读（不可 Edit/Write） | 代码库探索与分析 |
| `Plan` | 只读（不可 Edit/Write） | 架构设计与规划 |

### 自定义类型

在 `.claude/agents/{name}.md` 中定义智能体后，可通过 `subagent_type: "{name}"` 调用。自定义智能体可访问全部工具。

### 选择标准

| 场景 | 推荐类型 | 理由 |
|------|----------|------|
| 角色复杂且需在多会话复用 | **自定义类型**（`.claude/agents/`） | 将角色与工作原则以文件形式管理 |
| 简单调研/收集，提示词足够 | **`general-purpose`** + 详细提示 | 无需额外智能体文件，仅依赖提示说明 |
| 只需阅读代码（分析/评审） | **`Explore`** | 防止误修改文件 |
| 仅需设计/规划 | **`Plan`** | 专注分析，避免变更代码 |
| 需要修改文件的实现任务 | **自定义类型** | 具备完整工具访问能力并有专业指引 |

**原则：** 所有智能体都必须以 `.claude/agents/{name}.md` 文件形式定义。即便使用内置类型，也应生成智能体定义文件，明确角色、原则和通信协议。这样才能在后续会话中复用，并保证团队协作质量。

**模型：** 所有智能体统一使用 `model: "opus"`。调用 Agent 工具时必须显式指定 `model: "opus"` 参数。

## 智能体定义结构

```markdown
---
name: agent-name
description: "用 1–2 句话描述角色，并列出触发关键词。"
---

# Agent Name — 一句角色概述

你是 [领域] 的 [角色] 专家。

## 核心角色
1. 角色 1
2. 角色 2

## 工作原则
- 原则 1
- 原则 2

## 输入/输出协议
- 输入： [从哪里接收什么]
- 输出： [输出到哪里，输出什么]
- 格式： [文件格式与结构]

## 团队通信协议（团队模式下）
- 接收消息： [从哪些智能体接收何种消息]
- 发送消息： [向哪些智能体发送何种消息]
- 任务请求： [在共享任务列表中请求哪些类型任务]

## 错误处理
- [失败时的行为]
- [超时时的行为]

## 协作
- 与其他智能体的协作关系
```

## 智能体拆分标准

| 标准 | 拆分 | 合并 |
|------|------|------|
| 专业领域 | 领域不同则拆分 | 领域重叠则合并 |
| 并行性 | 可独立并行则拆分 | 完全顺序依赖则考虑合并 |
| 上下文负载 | 上下文负载重则拆分 | 轻量且快速则合并 |
| 复用性 | 在其他团队也可复用则拆分 | 仅在当前团队使用则可合并 |

## 智能体复用设计

在创建新智能体前，务必检查与既有智能体是否存在重叠。随着哈尼斯多次构建，相似角色的智能体很容易以不同名字不断增加。

| 场景 | 处理方式 |
|------|----------|
| 既有智能体完全覆盖新角色 | 不创建新智能体，直接复用既有智能体 |
| 既有智能体部分覆盖，且可一般化 | 将既有智能体一般化扩展 |
| 既有智能体仅在特定领域有意特化 | 创建新智能体，保持区分 |
| 角色范围完全不同 | 直接创建新智能体 |

**原则：** 一个智能体越专注于单一角色，复用性越高、重叠越少。若一个智能体承担两个以上角色，应先评估是否可拆分。

**对既有智能体进行一般化时：** 依赖该智能体的编排器与团队结构可能发生变化。扩展前需确认依赖关系，一般化后通过试运行（dry-run）验证既有行为是否保持正确。

## Skill 与 Agent 的区分

| 维度 | Skill（技能） | Agent（智能体） |
|------|---------------|-----------------|
| 定义 | 过程知识 + 工具集合 | 专家角色 + 行为原则 |
| 位置 | `.claude/skills/` | `.claude/agents/` |
| 触发方式 | 用户请求关键词匹配 | 通过 Agent 工具显式调用 |
| 规模 | 小到大（可包含完整工作流） | 相对较小（角色定义） |
| 作用 | "如何做" | "由谁做" |

Skill 是智能体执行任务时参考的**流程指南**，Agent 是使用 Skill 的**专家角色定义**。

## Skill 与 Agent 的连接方式

智能体有三种方式使用 Skill：

| 方式 | 实现方式 | 适用场景 |
|------|----------|----------|
| **调用 Skill 工具** | 在智能体提示中明确 "通过 Skill 工具调用 /skill-name" | Skill 是独立工作流，且用户也可以直接调用 |
| **在提示中内联** | 在智能体定义中直接嵌入 Skill 内容 | Skill 较短（50 行以内）且仅供该智能体使用 |
| **加载参考文件** | 通过 Read 按需加载 Skill 的 references/ 文件 | Skill 内容较大或仅在特定条件下需要 |

推荐：可复用性高的使用 Skill 工具；专用 Skill 可内联；内容较大则使用参考文件按需加载。
