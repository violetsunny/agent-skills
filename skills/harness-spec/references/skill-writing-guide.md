## 1. description 编写模式

description 是 Skill 唯一的触发机制。Claude 在 `available_skills` 列表中只读取 name 与 description，以决定是否调用某个 Skill。

### 触发机制理解

Claude 倾向于用自身基础工具处理简单任务，因此即便 description 写得很好，也未必在“很简单的请求”（例如“帮我读一下 PDF”）中触发 Skill。而在任务复杂、步骤多且具有专业性时，被触发的概率更高。

### 编写原则

1. 同时写明 **Skill 做什么** 和 **在什么具体场景下应被触发**；
2. 明确与“看起来类似但不应触发本 Skill”的场景之间的边界条件；
3. 风格略带“主动”，以抵消 Claude 在触发决策上的保守倾向。

### 良好示例

```yaml
description: "执行所有 PDF 相关任务：读取 PDF 文件、提取文本/表格、合并、拆分、
  旋转、添加水印、加密/解密、OCR 等。只要用户提到 .pdf 文件或请求 PDF 形式的输出，
  就必须使用此 Skill。尤其适用于需要将 PDF 内容进行转换、编辑或分析的场景，而不仅仅是简单阅读。"
```

```yaml
description: "处理所有表格类文件（Excel/CSV/TSV）的任务，包括新增列、公式计算、
  格式调整、图表生成与数据清洗。只要用户提到这类文件——即使只说‘下载目录里的 xlsx’——
  都应考虑使用此 Skill。"
```

### 不良示例

- `"处理数据的 Skill"` —— 描述太模糊，不清楚处理哪种文件、何种任务；
- `"PDF 相关工作"` —— 未列举具体动作，也未说明典型触发场景。

## 2. 正文编写风格

### 以“原因”开头（Why-first）

LLM 在理解“为什么要这样做”时，更容易在复杂或边界情形下做出正确判断。因此比起纯粹的规则，更应传达背后的原理。

**不良示例：**
```markdown
ALWAYS 使用 pdfplumber 进行表格抽取。NEVER 使用 PyPDF2 处理表格。
```

**良好示例：**
```markdown
在处理表格时使用 pdfplumber。PyPDF2 更适合纯文本抽取，无法保持表格的行/列结构，
因此不适合用于表格提取。而 pdfplumber 可以识别单元格边界并返回结构化数据。
```

### 一般化原则

当测试或反馈暴露问题时，应避免只针对某一个示例进行窄范围修补，而是要在原理层面进行一般化调整。

**过拟合式修补示例：**
```markdown
当存在名为“Q4 收入”的列时，将该列转换为数值类型。
```

**一般化修补示例：**
```markdown
当列名包含“收入”“金额”“数量”等暗示数值含义的关键词时，
应尝试将该列转换为数值类型。若转换失败，则保留原值不报错。
```

### 使用命令式语气

Skill 是针对智能体的指令文档，建议使用“……执行”“……完成”这类命令式风格，而非“可以……”、“建议……”这类弱化语气。

### 节约上下文

每一句话都占用上下文窗口，应判断其价值：
- 若是 Claude 已知的通识知识，可省略；
- 若缺少此说明智能体容易犯错，则保留；
- 若一段长说明不如一个具体示例有效，可替换为示例。

## 3. 输出格式定义模式

当 Skill 的产出格式十分重要时，需在正文中明确约定输出结构。

```markdown
## 报告结构
请严格遵循以下模板：

# [标题]
## 摘要
## 关键发现
## 建议
```

格式定义必须简洁，并尽量包含实际示例，提高可执行性。

## 4. 示例编写模式

相较于长篇文字说明，精心设计的示例通常更有效。

```markdown
## 提交信息（commit message）格式

**示例 1：**
输入：新增基于 JWT 的用户认证逻辑
输出：feat(auth): implement JWT-based authentication

**示例 2：**
输入：修复登录页面中“显示密码”按钮无效的问题
输出：fix(login): fix password visibility toggle
```

示例应覆盖典型场景与边界场景，并明确输入与输出对应关系。

## 5. 逐步信息披露模式

### 模式 1：按领域拆分

```text
bigquery-skill/
├── SKILL.md（概览 + 领域选择指南）
└── references/
    ├── finance.md（收入与清算指标）
    ├── sales.md（销售机会与管道）
    └── product.md（API 使用量与功能行为）
```

当用户询问收入相关问题时，只需加载 finance.md；询问销售相关问题时加载 sales.md。

### 模式 2：条件式详细说明

```markdown
# DOCX 处理

## 文档创建
使用 docx-js 创建新文档。→ 详见 [DOCX-JS.md](references/docx-js.md)。

## 文档编辑
简单编辑可直接修改 XML。
**如需跟踪修订（Track Changes）**：请参考 [REDLINING.md](references/redlining.md)。
```

### 模式 3：大体量参考文件结构化

对于超过 300 行的参考文件，需在顶部添加目录：

```markdown
# API 参考

## 目录
1. [认证](#认证)
2. [端点列表](#端点列表)
3. [错误码](#错误码)
4. [限流规则](#限流规则)

---

## 认证
...
```

## 6. 脚本打包判断标准

在测试过程中观察智能体的日志或对话内容，若出现以下模式，则应将脚本打包至 `scripts/`：

| 信号 | 行动 |
|------|------|
| 3 个以上测试中重复生成相同助手脚本 | 将该脚本打包到 `scripts/` |
| 每次执行都重复安装相同依赖（pip/npm） | 在 Skill 中明确安装步骤或预打包依赖说明 |
| 每次都采用相同多步骤方法 | 在 Skill 正文中写成标准流程 |
| 经常遭遇同类错误并采取同样规避方式 | 在 Skill 中记录已知问题与解决方案 |

被打包的脚本应经过充分测试，确保稳定可靠。

## 7. 数据 schema 规范

为保持 Skill 之间数据交换的一致性，需遵循统一的 schema。以下示例可用于 Skill 测试与评估：

### eval_metadata.json

记录每个测试案例的元数据：

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户任务提示词",
  "assertions": [
    "产出中包含 X",
    "生成了 Y 格式的文件"
  ]
}
```

### grading.json

存储断言打分结果：

```json
{
  "expectations": [
    {
      "text": "产出中包含 '北京'",
      "passed": true,
      "evidence": "在第 3 步中发现 '北京地区数据提取'"
    }
  ],
  "summary": {
    "passed": 2,
    "failed": 1,
    "total": 3,
    "pass_rate": 0.67
  }
}
```

**字段命名注意：** 必须使用 `text`、`passed`、`evidence`，不要改用 `name`、`met`、`details` 等变体。

### timing.json

记录执行时间与 Token 使用情况：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

需在子智能体完成通知中立即保存 `total_tokens` 与 `duration_ms`，否则之后无法恢复。

## 8. 不应写入 Skill 的内容

- README.md、CHANGELOG.md、安装指南等面向用户的文档；
- 关于 Skill 构建过程的元信息（测试结果、迭代历史等）；
- 面向终端用户的说明书（Skill 是面向智能体的指令，而非用户文档）；
- Claude 已经掌握的一般性知识（如常见库的基础用法）。

## 9. Skill 复用设计

在创建新 Skill 前，应检查是否与既有 Skill 存在功能重叠。随着哈尼斯多次构建，相似功能的 Skill 可能以不同名称不断积累。

| 场景 | 处理方式 |
|------|----------|
| 既有 Skill 完全覆盖新功能 | 不创建新 Skill，改为将智能体连接到既有 Skill |
| 既有 Skill 部分覆盖，且可一般化 | 将既有 Skill 一般化扩展 |
| 既有 Skill 包含刻意的领域特化部分 | 创建新 Skill，并保持两者区分 |
| 功能范围完全不同 | 直接创建新 Skill |

**原则：** 一个 Skill 越专注于单一职责，其复用性越高、重叠越少。当 Skill 同时承担多个角色时，应先评估是否可拆分。

### 一般化的边界

一般化理论上可以无限进行，但应在 **预期职责范围** 终止。保留有意设计的领域特化，消除偶然引入的耦合。

示例："Fintech 风险评估 PDF" Skill

| 步骤 | 结果 |
|------|------|
| 去除 Fintech 依赖 | 得到 "评估结果 PDF" Skill —— 若职责确实在风险评估，则在此停止一般化 |
| 再去除评估依赖 | 得到 "PDF 排版" Skill —— 若已有类似 Skill，应直接复用而非新建 |

若 Skill 的职责刻意限定为“Fintech 风险评估”，则无需进一步一般化，应作为特化 Skill 存在。

扩展既有 Skill 时需注意：依赖该 Skill 的智能体行为可能发生改变。扩展前应确认依赖关系，并在 description 中同步更新使用范围。
