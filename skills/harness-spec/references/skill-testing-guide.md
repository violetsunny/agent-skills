## 1. 测试框架概览

Skill 的质量评估由 **定性评估** 与 **定量评估** 组合完成：

| 类型 | 方法 | 适用 Skill |
|------|------|------------|
| **定性评估** | 用户直接审阅产出 | 文风、设计、创作类等主观质量 |
| **定量评估** | 基于断言的自动打分 | 文件生成、数据提取、代码生成等可客观验证任务 |

核心循环：**编写 Skill → 执行测试 → 评估结果 → 改进 Skill → 重新测试**。

## 2. 测试提示词编写

### 基本原则

测试提示词必须是 **真实用户可能输入的、具体且自然的句子**。过于抽象或人工痕迹严重的提示词测试价值较低。

### 不良示例

```text
"处理 PDF"
"提取数据"
"生成图表"
```

### 良好示例

```text
"请在下载文件夹里的 'Q4_收入_最终_v2.xlsx' 中，用 C 列（收入）和 D 列（成本）
计算新增一个利润率（%）列，并按利润率从高到低排序。"
```

```text
"请从这份 PDF 中把第 3 页的表格提取出来，并转换为 CSV。表头有两行，
第一行是分类，第二行是真正的列名。"
```

### 提示词的多样性

- 语气上覆盖 **正式 / 口语** 两类；
- 意图上覆盖 **显式说明 / 需要推断** 两类（如直接说明文件格式 vs 需从上下文推断）；
- 难度上覆盖 **简单任务 / 复杂任务**；
- 部分提示词可以包含缩写、错别字、随意表达等。

### 覆盖范围

初始可使用 2–3 个测试提示词，但需覆盖：
- 1 个核心使用场景；
- 1 个边界场景；
- （可选）1 个复杂复合场景。

## 3. 执行测试：有 Skill vs 基线

### 3-1. 对比执行结构

针对每个测试提示词，需同时运行两个子智能体：

**有 Skill 的执行：**
```text
提示词："{测试提示词}"
Skill 路径：{Skill 路径}
输出目录：_workspace/iteration-N/eval-{id}/with_skill/outputs/
```

**基线执行：**
```text
提示词："{相同的测试提示词}"
不加载 Skill
输出目录：_workspace/iteration-N/eval-{id}/without_skill/outputs/
```

### 3-2. 基线的选择

| 场景 | 基线方案 |
|------|----------|
| 新 Skill 构建 | 在不加载 Skill 的情况下使用相同提示词执行 |
| 现有 Skill 的改进 | 将 Skill 修改前的版本作为基线（需保存旧版本快照） |

### 3-3. 捕获执行时间与 Token 数据

在子智能体完成时收到的通知中，要 **立即** 保存 `total_tokens` 与 `duration_ms`，这些数据只在通知时可用，之后无法恢复。

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

## 4. 定量评估：基于断言的打分

### 4-1. 编写断言

当产出结果可以客观验证时，需编写断言以实现自动打分。

**优秀断言的特征：**
- 可明确判断真/假；
- 具备清晰、描述性的名称，使人能一眼看出其检验内容；
- 检验的是 Skill 的关键价值点。

**不良断言的示例：**
- 总是通过的断言（如“输出不为空”）；
- 需要主观判断的断言（如“写得很好”）。

### 4-2. 可编程验证

若断言可以通过代码验证，应编写脚本自动执行验证。这比人工检查更快、更稳定，而且可在每次迭代中重复使用。

### 4-3. 小心“不区分”型断言

如果某断言在“有 Skill”和“基线”两种配置中都 100% 通过，则无法衡量 Skill 的增益。发现此类断言时，应删除或替换为更具挑战性的断言。

### 4-4. 打分结果的数据结构

```json
{
  "expectations": [
    {
      "text": "已添加利润率列",
      "passed": true,
      "evidence": "在 E 列发现 'profit_margin_pct' 列"
    },
    {
      "text": "按利润率降序排序",
      "passed": false,
      "evidence": "保持原始顺序，未进行排序"
    }
  ],
  "summary": {
    "passed": 1,
    "failed": 1,
    "total": 2,
    "pass_rate": 0.50
  }
}
```

## 5. 使用专业智能体协助评估

### 5-1. 评分者（Grader）

负责基于断言对结果进行打分，并可从产出中提取可验证的事实声明进行进一步验证。

**角色：**
- 对每个断言判定通过/失败，并提供证据；
- 从产出中提取事实性语句并进行验证；
- 对评估体系本身提供反馈（例如某断言过于简单或表述不清）。

### 5-2. 比较者（Comparator，盲测）

在匿名化的 A/B 条件下对两份结果进行质量评估，不提前告知哪一份使用了 Skill。

**适用场景：** 当需要严格确认“新版本是否确实更好”时，进行严格对比；对于普通迭代流程可不使用。

**评估指标：**
- 内容：准确性与完整性；
- 结构：组织方式与排版质量；
- 综合评分。

### 5-3. 分析者（Analyzer）

从评估数据中分析统计模式：
- 识别“不区分型”断言（两种配置均高分）；
- 识别结果波动较大的评估（每次执行结果差异大，说明不稳定）；
- 分析时间/Token 与质量之间的权衡（Skill 是否通过提高成本获得更好结果）。

## 6. 迭代改进循环

### 6-1. 收集反馈

将产出展示给用户并收集反馈。如果用户没有任何反馈，可视为“当前版本无明显问题”。

### 6-2. 改进原则

1. **将反馈一般化** —— 不针对单个测试案例作窄范围修改，而是提升 Skill 在原则层面的表现；
2. **删除无价值内容** —— 如果 Skill 指示智能体执行低价值或冗余任务，应删减这些指示；
3. **解释背后理由** —— 将用户反馈中隐含的理由补充进 Skill，使智能体理解“为何如此重要”；
4. **将重复性操作打包为脚本** —— 若在所有测试中都出现同样的助手脚本，应将其预先打包到 `scripts/` 中。

### 6-3. 迭代步骤

```text
1. 修改 Skill；
2. 在新的 iteration-N+1/ 目录中重新执行全部测试案例；
3. 将结果与前一 iteration 对比展示给用户；
4. 收集反馈；
5. 再次修改 Skill → 重复上述流程。
```

**停止条件：**
- 用户满意；
- 用户不再提供反馈（所有产出看上去都没有问题）；
- 没有明显的进一步改进空间。

### 6-4. 草稿→复审模式

在修改 Skill 时，先写出草稿，再以“新的视角”进行复审后改进。不要试图一次成稿，而是通过草稿—审阅循环逐步优化。

## 7. description 触发验证

### 7-1. 构造触发评估查询

需编写 20 个评估查询：10 个应触发（should-trigger），10 个不应触发（should-NOT-trigger）。

**查询质量要求：**
- 真实用户可能说出的自然句子；
- 包含文件路径、个人上下文、列名、公司名等具体细节；
- 兼顾长度、语气与格式多样性；
- 更关注边界场景，而非易判定的“标准场景”。

**Should-trigger 查询（8–10 个）：**
- 表达上具有多样性（正式/口语，但意图一致）；
- 有些查询不显式说明需要哪种 Skill，但语境中明确需要该 Skill；
- 包含非典型使用场景；
- 在与其他 Skill 竞争时，该 Skill 应当获胜的场景。

**Should-NOT-trigger 查询（8–10 个）：**
- **重点在 Near-miss** —— 关键词相似，但更适合其他工具或 Skill；
- 类似“写斐波那契函数”这类完全无关的查询无须测试；
- 选择临近领域、模糊表达或关键词重叠但语境不同的案例。

### 7-2. 验证与既有 Skill 的冲突

需检查新 Skill 的 description 是否与既有 Skill 的触发范围发生冲突：

1. 收集所有既有 Skill 的 description；
2. 检查新 Skill 的 should-trigger 查询是否会错误触发既有 Skill；
3. 若存在冲突，需在新 Skill description 中明确边界条件，避免触发重叠。

### 7-3. （可选）自动优化流程

当需要自动优化 description 时，可进行如下步骤：

1. 将 20 个评估查询拆分为训练集（60%）与测试集（40%）；
2. 使用当前 description 测量触发准确率；
3. 分析失败案例，生成改进后的 description；
4. 在测试集上评估不同版本 description 的触发效果；
5. 最多重复 5 次，每次选取测试集表现最佳的描述 —— 避免只在训练集上优化导致过拟合。

> 上述流程可使用 `claude -p` 的自动化脚本执行，成本较高，适合在 Skill 已相对稳定后作为收尾优化手段使用。

## 8. 工作空间结构

用于管理测试与评估结果的推荐目录结构：

```text
{skill-name}-workspace/
├── iteration-1/
│   ├── eval-descriptive-name-1/
│   │   ├── eval_metadata.json
│   │   ├── with_skill/
│   │   │   ├── outputs/
│   │   │   ├── timing.json
│   │   │   └── grading.json
│   │   └── without_skill/
│   │       ├── outputs/
│   │       ├── timing.json
│   │       └── grading.json
│   ├── eval-descriptive-name-2/
│   │   └── ...
│   └── benchmark.json
├── iteration-2/
│   └── ...
└── evals/
    └── evals.json
```

**约定：**
- eval 目录使用**描述性名称**而非简单编号（如 `eval-multi-page-table-extraction`）；
- 每次迭代使用独立的 iteration 目录，避免覆盖旧结果；
- `_workspace/` 目录中的内容不应删除，以便进行事后验证和审计。
