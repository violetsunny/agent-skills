# Harness — 智能体团队与技能架构师

根据具体领域/项目构建 harness，定义各智能体的角色，并生成这些智能体将使用的技能的元 Skill。

**核心原则：**
1. 统一管理智能体定义文件和技能配置：项目级 `.claude/agents/`、`.claude/skills/` 以及 workspace 级 `.agents/AGENTS.md`、`.agents/skills/` 都视为智能体/技能来源。
2. **默认使用智能体团队作为基本执行模式。**
3. **在 CLAUDE.md 中注册 harness 指针，并在 AGENTS.md 中维护智能体视图。** —— CLAUDE.md 记录 harness 存在、触发规则与变更历史，供 CLAUDE 会话入口使用；AGENTS.md/.agents/skills 记录当前项目的智能体/技能布局，供 workspace 工具使用，两者处于同一项目级别但服务不同工具栈。
4. **harness 不是静态配置而是不断演化的系统。** —— 每次执行后，都要根据反馈持续更新智能体、技能、AGENTS.md 和 CLAUDE.md。

## 工作流

### Phase 0：现状审计

当 harness Skill 被触发时，首先要检查现有 harness 的状态。

1. 读取项目级与 workspace 级智能体/技能配置：
   - 项目级：`项目/.claude/agents/`、`项目/.claude/skills/`、`项目/CLAUDE.md`、`项目/AGENTS.md`、`项目/.agents/skills/`；
   - workspace 级：`.agents/AGENTS.md`、`.agents/skills/`（如存在）。
2. 根据当前状态对执行模式进行分支：
   - **新建 harness**：项目级智能体/技能目录不存在或为空，且 AGENTS.md 中无配置 → 从 Phase 1 开始完整执行。
   - **扩展既有 harness**：存在既有 harness（无论配置来自 `.claude` 目录还是 AGENTS.md/.agents/skills/），并有新增智能体/技能需求 → 按下方 Phase 选择矩阵，仅执行需要的 Phase。
   - **运营/维护**：针对既有 harness 的审计、修改、同步请求 → 进入 Phase 7-5 的运营/维护工作流。

   **扩展 harness 时的 Phase 选择矩阵：**
   | 变更类型 | Phase 1 | Phase 2 | Phase 3 | Phase 4 | Phase 5 | Phase 6 |
   |---------|---------|---------|---------|---------|---------|---------|
   | 新增智能体 | 可跳过（利用 Phase 0 结果） | 仅做部署决策 | 必须执行（含 3-0） | 若需要专用技能则执行（含 4-0） | 修改编排器 | 必须执行 |
   | 新增/修改技能 | 可跳过 | 可跳过 | 可跳过 | 必须执行（含 4-0） | 若连接发生变化则执行 | 必须执行 |
   | 架构变更 | 可跳过 | 必须执行 | 仅对受影响智能体执行（含 3-0） | 仅对受影响技能执行（含 4-0） | 必须执行 | 必须执行 |

3. 在 `.claude/agents/`、`.claude/skills/`、AGENTS.md 与 `.agents/skills/` 之间对比智能体/技能列表，与 CLAUDE.md 中的记录进行交叉检查，识别不一致（漂移）。
4. 将审计结果向用户进行简要汇报，并确认后续执行计划。

### Phase 1：领域分析

1. 从用户请求中识别领域/项目。
2. 识别核心工作类型（生成、验证、编辑、分析等）。
3. 基于 Phase 0 审计结果，分析与既有智能体/技能之间的冲突或重叠（同时考虑 `.claude` 与 `.agents`/AGENTS.md 两套来源）。
4. 探索项目代码库——了解技术栈、数据模型和关键模块。
5. **识别用户熟练程度** —— 利用对话中的线索（使用术语、提问深度）估计技术水平，调整后续沟通的语气与细节。对编程经验不足的用户，不要在没有解释的前提下使用“断言（assertion）”“JSON 模式（JSON schema）”等术语。

### Phase 2：团队架构设计

#### 2-1. 执行模式选择

**智能体团队是最高优先级的默认模式。** 当有两名以上智能体协作时，应优先考虑团队模式。团队成员通过直接消息（SendMessage）和共享任务列表（TaskCreate）进行自我协调，共享发现、讨论冲突、补足遗漏，以提升结果质量。

| 模式 | 使用场景 | 特性 |
|------|----------|------|
| **智能体团队**（默认） | 两名及以上智能体协作，需要实时协调与反馈交换，中间产物需相互参照 | 使用 `TeamCreate` + `SendMessage` + `TaskCreate` 进行自我协调 |
| **子智能体**（备选） | 单一智能体完成工作，仅需将结果返回给主智能体，团队通信开销较大时 | 通过 `Agent` 工具直接调用，使用 `run_in_background` 进行并行 |
| **混合模式** | 各 Phase 特性不同，例如：并行收集（子智能体）→ 基于共识的整合（团队） | 按 Phase 组合使用团队与子智能体模式 |

**决策顺序：**
1. 先评估能否采用智能体团队——只要有两名以上智能体，团队模式应作为默认选择。
2. 当团队通信在结构上不必要（只需结果传递）、且团队开销超过收益时，再改用子智能体模式。
3. 若各 Phase 特性显著不同，则考虑混合模式——在编排器中逐个 Phase 明确执行模式。

> 关于模式的详细对比表和模式化决策树，请参考 `references/agent-design-patterns.md` 中的“执行模式”部分。

#### 2-2. 架构模式选择

1. 将整体工作拆分为若干专业领域。
2. 决定智能体团队结构（具体模式见 `references/agent-design-patterns.md`）：
   - **流水线**：顺序依赖的工作流程；
   - **扇出/扇入**：并行且相互独立的工作；
   - **专家池**：按情况选择并调用不同专家；
   - **生成-验证**：先生成，再进行质量审核；
   - **监督者**：中心智能体负责状态管理与动态任务分配；
   - **分层委派**：上层智能体向下层智能体递归委派任务。

#### 2-3. 智能体拆分标准

围绕专业性、并行性、上下文和复用性四个维度进行判断。详细标准请参考 `references/agent-design-patterns.md` 中的“智能体拆分标准”章节。与既有智能体的重叠与复用分析在 Phase 3-0 中进行。

### Phase 3：智能体定义生成

#### 3-0. 既有智能体重叠性分析

在创建新的智能体之前，先检查 `项目/.claude/agents/` 和 AGENTS.md 中的既有智能体是否存在角色重叠。随着 harness 多次构建，相似角色的智能体可能会以不同名称重复出现。

> 关于重叠分类标准与复用设计，请参考 `references/agent-design-patterns.md` 中的“智能体复用设计”部分。

**所有智能体都必须以 `项目/.claude/agents/{name}.md` 文件的形式进行定义，并在 AGENTS.md 中同步其存在。** 不允许仅在 Agent 工具的 prompt 中直接写入角色：
- 将智能体定义保存在文件中，才能在后续会话中复用；
- 必须明确团队通信协议，才能保证智能体之间的协作质量；
- harness 的核心价值在于：将“谁来做”（智能体）与“怎么做”（技能）明确分离。

即便使用内置类型（`general-purpose`、`Explore`、`Plan`），也必须生成智能体定义文件。内置类型通过 Agent 工具的 `subagent_type` 参数指定，而定义文件中则描述角色、原则和通信协议。

**模型设置：** 所有智能体统一使用 `model: "opus"`。调用 Agent 工具时必须明确指定 `model: "opus"` 参数。harness 的质量高度依赖于智能体的推理能力，而 opus 能提供最佳质量。

**团队重构：** 每个会话只能激活一个智能体团队，但可以在不同 Phase 间解散团队并创建新团队。例如在流水线模式中，不同 Phase 可能需要不同的专家组合，此时应将前一团队的产出保存到文件，然后销毁团队并创建新团队。

每个智能体都要在 `项目/.claude/agents/{name}.md` 中定义，并在 AGENTS.md 中更新对应条目。必备章节包括：核心角色、工作原则、输入/输出协议、错误处理、协作方式。在团队模式下，应增加 `## 团队通信协议` 一节，明确消息接收/发送对象以及任务请求范围。

> 关于定义模板和示例文件，请参考 `references/agent-design-patterns.md` 的“智能体定义结构”以及 `references/team-examples.md`。

**若包含 QA 智能体，需遵守以下要求：**
- QA 智能体应使用 `general-purpose` 类型（`Explore` 为只读，不适合执行验证脚本）；
- QA 的核心不只是“存在性检查”，而是**“边界交叉比对”** —— 同时读取 API 响应与前端 Hook，并比较其结构；
- QA 测试不应仅在整体完成后执行一次，而要在各模块完成后逐步执行（渐进式 QA）；
- 详细指南请参考 `references/qa-agent-guide.md`。

### Phase 4：技能生成

为每个智能体生成其所需技能，并保存在 `项目/.claude/skills/{name}/SKILL.md` 中，同时在 `.agents/skills/` 与 `项目/.agents/skills/` 中维护技能视图，确保 workspace 工具看到与项目实际技能配置一致的索引。详细编写指南请参见 `references/skill-writing-guide.md`。

#### 4-0. 既有技能重叠性分析

在创建新技能前，检查 `项目/.claude/skills/` 与 `.agents/skills/` 中的既有技能是否存在功能重叠。随着多次构建 harness，相似功能的技能可能会以不同名称不断累积。

> 关于重叠分类标准和一般化模式，请参考 `references/skill-writing-guide.md` 中的“技能复用设计”章节。

#### 4-1. 技能结构

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML 前言区（name、description 必需）
│   └── Markdown 正文
└── Bundled Resources（可选）
    ├── scripts/    - 用于重复性或确定性工作的可执行代码
    ├── references/ - 按需加载的参考文档
    └── assets/     - 输出使用的文件（模板、图片等）
```

#### 4-2. description 编写 —— 主动引导触发

description 是技能的唯一触发机制。Claude 在判断是否触发技能时相对保守，因此 description 需要写得**积极（pushy）**。

**坏示例：** `"处理 PDF 文档的技能"`
**好示例：** `"执行所有 PDF 相关任务：读取 PDF 文件、提取文本/表格、合并、拆分、旋转、添加水印、加密、OCR 等。只要用户提到 .pdf 文件或请求 PDF 形式的输出，就必须使用此技能。"`

关键：既要说明技能能做什么，也要写出具体的触发场景，还要与“看起来相似但不应触发本技能”的情况区分开来。

#### 4-3. 正文编写原则

| 原则 | 说明 |
|------|------|
| **解释 Why** | 尽量避免只给出“必须/禁止”的硬性指令，而要说明背后的原因。LLM 理解原因后，在边界场景中更容易做出正确判断。 |
| **保持精简** | 上下文窗口是公共资源，SKILL.md 正文应控制在 500 行以内。不必要的细节要删除或移入 references/。 |
| **面向一般性** | 不要只针对单一示例制定窄规则，而要阐明可泛化的原理，以适应多种输入。避免过度拟合。 |
| **重复逻辑要打包** | 若在测试执行中发现智能体反复编写相同脚本，应将这些脚本预先打包到 `scripts/` 中。 |
| **使用命令式语气** | 文本风格以命令式/指令式为主，例如“执行…”“完成…”而不是模糊描述。 |

#### 4-4. 分层加载（逐步信息披露）

技能采用三级加载体系来管理上下文：

| 层级 | 加载时机 | 规模目标 |
|------|----------|----------|
| **元数据**（name + description） | 始终在上下文中 | 约 100 词 |
| **SKILL.md 正文** | 技能被触发时 | 少于 500 行 |
| **references/** | 仅在需要时读取 | 不设行数上限（脚本可在不加载的情况下直接执行） |

**规模管理规则：**
- 当 SKILL.md 接近 500 行时，需将细节内容拆分至 references/，并在正文中保留“何时读取该文件”的指引。
- 对于超过 300 行的 reference 文件，应在顶部加入**目录（ToC）**。
- 若按领域/框架存在多个变体，可在 references/ 下按子目录划分，仅在相关场景加载对应文件。

```
cloud-deploy/
├── SKILL.md（工作流 + 选型指南）
└── references/
    ├── aws.md    ← 仅在选择 AWS 时读取
    ├── gcp.md
    └── azure.md
```

#### 4-5. 技能与智能体的连接原则

- 一个智能体可以绑定 1~N 个技能（1:1 或 1:多）；
- 多个智能体也可以共享同一个技能；
- 技能负责“如何执行”，智能体负责“由谁执行”。

> 更多编写模式、示例和数据 schema 规范请参考 `references/skill-writing-guide.md`。

### Phase 5：集成与编排

编排器是一种特殊 Skill，用于将各个智能体和技能连接起来，形成完整工作流并协调整个团队。在 Phase 4 生成的各技能中，“某智能体做什么以及如何做”由各自 Skill 定义，而编排器则定义“由谁在何时以何种顺序协作完成整体任务”。具体模板见 `references/orchestrator-template.md`。

**扩展既有 harness 时的编排器修改：** 若当前工作是扩展既有 harness，则不重新创建编排器，而是在原有编排器上进行修改：将新增智能体反映到团队结构、任务分配和数据流中，并在 description 中加入与新智能体相关的触发关键词；同时确保 CLAUDE.md 中的 harness 指针与 AGENTS.md 中的智能体视图与实际配置一致。

根据 Phase 2-1 中选择的执行模式，编排器采用不同模式：

#### 5-0. 编排器模式（按执行模式划分）

**智能体团队模式（默认）：**

编排器通过 `TeamCreate` 创建团队，并使用 `TaskCreate` 分配任务。团队成员通过 `SendMessage` 进行直接通信和自我协调。负责人（编排器）负责监控进度和汇总结果。

```
[编排器/负责人]
    ├── TeamCreate(team_name, members)
    ├── TaskCreate(tasks with dependencies)
    ├── 团队成员通过 SendMessage 自我协调
    ├── 汇总结果并整理输出
    └── 销毁团队
```

**子智能体模式（备选）：**

编排器通过 `Agent` 工具直接调用子智能体。使用 `run_in_background: true` 实现并行执行，结果仅返回给主智能体。当不需要团队通信且希望降低开销时使用。

```
[编排器]
    ├── Agent(agent-1, run_in_background=true)
    ├── Agent(agent-2, run_in_background=true)
    ├── 等待并收集结果
    └── 生成整合输出
```

**混合模式：**

在不同 Phase 组合使用不同模式，常见模式包括：
- **并行收集（子智能体）→ 共识整合（团队）**：Phase 2 使用子智能体并行收集独立信息，Phase 3 组建团队进行讨论并基于共识整合结果；
- **团队生成 → 子智能体验证**：Phase 2 由团队生成初稿，Phase 3 由单个子智能体执行独立验证；
- **跨 Phase 重构团队**：在各 Phase 间使用 `TeamDelete` 与 `TeamCreate` 重建团队，并插入子智能体调用。

采用混合模式时，应在编排器中每个 Phase 的开头标明该 Phase 的执行模式（例如：`**执行模式：智能体团队**`）。

#### 5-1. 数据传递协议

在编排器中明确智能体之间的数据传递方式：

| 策略 | 方式 | 适用模式 | 适用场景 |
|------|------|----------|----------|
| **消息传递** | 使用 `SendMessage` 在团队成员间发送消息 | 团队模式 | 实时协调、反馈交换、轻量状态传递 |
| **任务驱动** | 使用 `TaskCreate`/`TaskUpdate` 共享任务状态 | 团队模式 | 任务进度追踪、依赖关系管理以及任务请求本身 |
| **文件传递** | 将数据写入并读取约定路径下的文件 | 团队 + 子智能体 | 处理大体量数据、结构化产物或需要审计追踪时 |
| **返回值传递** | 通过 `Agent` 工具返回消息 | 子智能体模式 | 主智能体直接接收子智能体输出 |

**推荐组合（团队模式）：** 任务驱动（协调） + 文件传递（产物） + 消息传递（实时沟通）。

**推荐组合（子智能体模式）：** 返回值传递（结果收集） + 文件传递（大体量产物）。

**混合模式：** 根据各 Phase 所采用的执行模式组合上述策略。

采用文件传递时的规则：
- 在工作目录下创建 `_workspace/` 文件夹，用于保存中间产物；
- 文件命名约定：`{phase}_{agent}_{artifact}.{ext}`（如 `01_analyst_requirements.md`）；
- 仅将最终产物输出到用户指定路径，中间文件保存在 `_workspace/` 中，用于后续验证和审计。

#### 5-2. 错误处理

在编排器中包含错误处理策略。核心原则：对同一操作最多重试一次；若再次失败，则在报告中标明该部分结果缺失，继续向前执行；对于互相冲突的数据，不删除任何一方，而是保持并注明来源。

> 关于各种错误类型的策略表和实现细节，请参见 `references/orchestrator-template.md` 中的“错误处理”章节。

#### 5-3. 团队规模指南

| 工作规模 | 建议团队规模 | 每名成员的任务数量 |
|----------|-------------|--------------------|
| 小规模（5~10 项工作） | 2~3 名成员 | 每人 3~5 项 |
| 中规模（10~20 项工作） | 3~5 名成员 | 每人 4~6 项 |
| 大规模（20 项以上工作） | 5~7 名成员 | 每人 4~5 项 |

> 团队规模越大，协调开销越高。通常 3 名专注的成员要优于 5 名分散注意力的成员。

#### 5-4. 在 CLAUDE.md 与 AGENTS.md 中注册 harness 指针与视图

完成 harness 配置后，需要在项目的 `CLAUDE.md` 与 `AGENTS.md` 中同时登记信息：

- CLAUDE.md：记录 harness 的存在、领域名称、触发规则与变更记录；
- AGENTS.md：记录当前项目的智能体列表、技能列表以及它们在 `.claude/agents/`、`.claude/skills/` 和 `.agents/skills/` 中的路径。

**CLAUDE.md 模板：**

````markdown
## Harness：{领域名称}

**目标：** {用一行概括 harness 的核心目标}

**触发规则：** 当用户提出与 {领域} 相关的工作请求时，应使用 `{orchestrator-skill-name}` Skill。对于简单问题，可以直接回答。

**变更记录：**
| 日期 | 变更内容 | 目标 | 原因 |
|------|----------|------|------|
| {YYYY-MM-DD} | 初始构建 | 全局 | - |
````

> CLAUDE.md 不记录智能体/技能列表或目录结构，这些信息由 AGENTS.md 和文件系统维护。CLAUDE.md 是供 CLAUDE 会话入口使用的“指针 +变更历史”。

AGENTS.md 则需要包含至少：
- 当前项目的智能体名称列表及对应 `项目/.claude/agents/{name}.md` 路径；
- 当前项目的技能名称列表及对应 `项目/.claude/skills/{name}/SKILL.md` 与 `.agents/skills/`/`项目/.agents/skills/` 路径；
- （可选）按领域或角色对智能体/技能进行分组，便于 workspace 工具检索。

#### 5-5. 后续工作支持

编排器不仅需要支持初次执行，还应覆盖后续执行与迭代改进。需满足以下三点：

1. 在编排器 description 中加入后续执行相关关键词：
   - “重新执行”“再次运行”“更新”“修改”“补充”等；
   - “仅重新执行 {领域} 的 {部分工作}”；
   - “基于之前结果”“提升当前结果”等。

2. 在编排器的 Phase 1 中加入上下文检查步骤：
   - 若 `_workspace/` 存在，且用户请求部分修改 → **仅重新执行相关智能体**；
   - 若 `_workspace/` 存在，且用户提供新输入 → **执行全新运行**（可将旧 `_workspace` 重命名为 `_workspace_prev/`）；
   - 若 `_workspace/` 不存在 → **执行初始运行**。

3. 在每个智能体定义中增加再调用时的行为说明：
   - 若存在之前的结果文件，应进行读取并基于此改进输出；
   - 若用户提供反馈，应针对相应部分进行修订。

> 详见 `references/orchestrator-template.md` 中的“Phase 0：上下文检查”章节。

### Phase 6：验证与测试

对生成的 harness 进行验证，详细测试方法请参见 `references/skill-testing-guide.md`。

#### 6-1. 结构验证

- 检查所有智能体文件是否位于正确路径；
- 验证技能的前言区（name、description）；
- 检查智能体之间的引用是否一致；
- 确认未生成任何命令（commands）；
- 检查 AGENTS.md 与实际 `.claude/agents/`、`.claude/skills/`、`.agents/skills/` 路径是否一致。

#### 6-2. 按执行模式验证

- **智能体团队模式**：检查团队成员之间的通信路径、任务依赖关系以及团队规模是否合理；
- **子智能体模式**：检查各智能体的输入输出连接、`run_in_background` 设置以及返回值收集逻辑；
- **混合模式**：确认编排器中每个 Phase 的执行模式已明确标注，并确保在模式切换处的数据传递不断档（如从团队模式切换到子智能体模式时，团队输出能正确传递给子智能体）。

#### 6-3. 技能执行测试

对所有新建技能进行实际执行测试：

1. **编写测试提示** —— 为每个技能设计 2~3 个贴近实际的测试提示，用自然且具体的用户语句表示。
2. **有技能 vs 无技能 对比执行** —— 若条件允许，可并行运行“有技能”和“无技能”的版本以比较价值：
   - **有技能版本**：在加载技能后执行任务；
   - **基线版本（无技能）**：在不加载技能的情况下执行同一提示。
3. **评估结果** —— 从定性（用户评价）与定量（基于断言的检查）两个维度评估输出质量。对于可客观验证的产物（如文件生成、数据提取），定义断言；对于主观内容（如文风、设计），主要依赖用户反馈。
4. **迭代改进** —— 若测试发现问题：
   - 将反馈进行一般化，而非仅针对单一示例进行狭义修改；
   - 修改技能后进行回归测试；
   - 当用户满意且不存在明显可提升空间时结束迭代。
5. **将重复模式打包** —— 若在测试执行中发现智能体反复编写同类脚本（如所有测试中均生成相同助手脚本），则应将这类脚本预先打包到 `scripts/` 目录中。

#### 6-4. 触发验证

验证每个技能的 description 是否能被正确触发：

1. 设计 8~10 个**应触发**的查询 —— 覆盖正式/随意、显式/隐式等多种说法；
2. 设计 8~10 个**不应触发**的查询 —— 虽然关键词相似，但更适合其他工具/技能的“边界”查询。

**边界查询设计要点：**
- 像“写一个斐波那契函数”这类明显无关的查询测试价值不大；
- 更适合类似“将这个 Excel 文件中的图表导出为 PNG”（xlsx Skill vs 图像转换 Skill）这样含糊边界场景。

同时检查与既有技能之间是否存在触发冲突。

#### 6-5. 试运行测试

- 检查编排器 Skill 的 Phase 顺序是否合理；
- 确认数据传递路径不存在空白段（dead link）；
- 确认所有智能体的输入都与前一 Phase 的输出相匹配；
- 确认各错误场景下的回退路径能够正常执行。

#### 6-6. 编写测试场景

- 在编排器 Skill 中增加 `## 测试场景` 小节；
- 至少描述一个正常流程和一个错误流程。

### Phase 7：harness 演化

harness 并非一次性成果，而是需要根据用户反馈不断演化的系统。

#### 7-1. 执行后的反馈收集

每次执行完 harness 后，都要主动征询用户反馈：
- “结果是否有需要改进的地方？”
- “智能体团队构成或工作流是否有你想调整的部分？”

若用户不愿反馈，则直接进入下一步；无需强求，但必须提供反馈机会。

#### 7-2. 反馈的反映路径

不同类型反馈对应不同修改对象：

| 反馈类型 | 修改对象 | 示例 |
|----------|----------|------|
| 结果质量 | 对应智能体的 Skill | “分析太浅显” → 在对应 Skill 中加入更高深度标准 |
| 智能体角色 | 智能体定义 `.md` | “需要增加安全审查” → 新增安全审查智能体 |
| 工作流顺序 | 编排器 Skill | “应当先验证再生成” → 调整 Phase 顺序 |
| 团队构成 | 编排器 + 智能体 | “这两个角色可以合并” → 合并智能体定义 |
| 触发遗漏 | Skill description | “这种表达不会触发 Skill” → 扩充 description 中的触发关键词 |

#### 7-3. 变更记录

所有变更都应记录在 CLAUDE.md 的**变更记录**表中（参照 Phase 5-4 模板中的“变更记录”部分）：

```markdown
**变更记录：**
| 日期 | 变更内容 | 目标 | 原因 |
|------|----------|------|------|
| 2026-04-05 | 初始构建 | 全局 | - |
| 2026-04-07 | 新增 QA 智能体 | agents/qa.md | 针对产出质量不足的反馈 |
| 2026-04-10 | 增加语气指引 | skills/content-creator | 针对“文本风格过于生硬”的反馈 |
```

通过变更记录可以跟踪 harness 的演化方向，防止出现质量回退（regression）。AGENTS.md 中也应同步记录智能体/技能的新增、删除和重命名，使 workspace 工具能够感知配置演化。

#### 7-4. 演化触发条件

不仅在用户明确提出“请修改 harness”时需要进行演化，在以下情况也应主动建议演化：
- 相同类型的反馈出现两次及以上；
- 某智能体出现重复失败模式；
- 用户经常绕过编排器，改用手动方式执行某些任务。

#### 7-5. 运营/维护工作流

针对既有 harness 的点检、修改和同步工作，应采用系统化流程。在 Phase 0 中经“运营/维护”支路进入时执行以下步骤：

**Step 1：现状审计**
- 对比 `.claude/agents/` 中的文件列表与编排器 Skill 中的智能体构成、AGENTS.md 中的智能体列表，生成不一致列表；
- 对比 `.claude/skills/` 与 `.agents/skills/` 目录与编排器 Skill 中的 Skill 构成，生成不一致列表；
- 将审计结果报告给用户。

**Step 2：渐进式修改**
- 按用户请求逐项执行智能体新增/修改/删除，以及 Skill 新增/修改/删除；
- 每次修改后立即执行 Step 3（同步）。

**Step 3：更新 CLAUDE.md 与 AGENTS.md 变更记录**
- 在 CLAUDE.md 的变更记录表中记录日期、变更内容、目标和原因；
- 在 AGENTS.md 中更新智能体/技能列表以及对应路径，必要时维护单独的变更注记区。

**Step 4：变更验证**
- 对修改后的智能体/Skill 进行结构验证（按 Phase 6-1）；
- 若变更影响触发逻辑，则执行触发验证（按 Phase 6-4）；
- 对于架构级大变更（如新增/删除 3 个以上智能体），应进一步执行 Phase 6-3（执行测试）和 6-5（试运行）。
- 最后确认 CLAUDE.md 与 AGENTS.md 中的记录均与实际文件系统状态一致。

## 产出物检查清单

完成构建后需确认：

- [ ] `项目/.claude/agents/` —— **所有智能体定义必须生成文件**（即使使用内置类型也不例外）；
- [ ] `项目/.claude/skills/` —— 各 Skill 文件（SKILL.md + references/）；
- [ ] `.agents/AGENTS.md` 与 `项目/AGENTS.md` —— 智能体视图与 `.claude/agents/` 一致；
- [ ] `.agents/skills/` 与 `项目/.agents/skills/` —— Skill 视图与 `.claude/skills/` 一致；
- [ ] 至少一个编排器 Skill（包含数据流、错误处理和测试场景）；
- [ ] 所有执行模式均已明确标注（智能体团队 / 子智能体 / 混合模式；使用混合模式时按 Phase 指明）；
- [ ] 所有 Agent 调用均明确指定 `model: "opus"` 参数；
- [ ] 在创建新智能体前已完成既有智能体重叠性分析（Phase 3-0）；
- [ ] 在创建新 Skill 前已完成既有 Skill 重叠性分析（Phase 4-0）；
- [ ] `.claude/commands/` 目录中**未创建任何命令**；
- [ ] 不存在与既有智能体/Skill 的冲突；
- [ ] Skill description 编写足够积极（pushy），且包含后续工作关键词；
- [ ] SKILL.md 正文控制在 500 行以内，若超过则将细节拆分到 references/；
- [ ] 已通过 2~3 个测试提示对 Skill 进行执行验证；
- [ ] 已完成触发验证（should-trigger + should-NOT-trigger）；
- [ ] **已在 CLAUDE.md 中注册 harness 指针**（触发规则 + 变更记录）；
- [ ] **已在 AGENTS.md 中同步所有智能体/Skill 的新增/删除/修改信息**；
- [ ] **在编排器 Phase 1 中加入上下文检查步骤**（区分初次/后续/部分重运行）。
