# Phase 2-4: 模板生成、架构评审、验证链核查与合规校验

## 模板选择

| 模板 | 适用场景 | 输出长度 | 特点 |
|------|---------|---------|------|
| ADR 标准 | 单一架构决策记录 | 1-3 页 | 聚焦一个决策，固定结构 |
| 技术提案 | 综合技术方案设计 | 5-15 页 | 含架构图、时序图、接口、风险、排期 |
| 简报 | 决策评审或向上汇报 | 1 页 | 问题、方案、风险、成本、决策 |

选择规则：

1. 用户明确指定则按指定模板
2. 单一决策优先 ADR
3. 系统级、多模块设计优先技术提案
4. 快速评审优先简报

## 生成要求

1. 使用对应模板：`adr-standard-template.md`、`tech-proposal-template.md`、`brief-template.md`
2. 所有章节都要有内容；缺口使用 `[待补充]`
3. 代码块必须标注语言
4. 图表优先使用 Mermaid
5. 次要展开内容使用 `[EXPAND]...[/EXPAND]`
6. Confluence 原生宏需求使用 `confluence-storage` 围栏

## 架构评审

文档初稿完成后，在发布前执行一次架构级审视。

评审重点：

1. 决策是否真正回应核心问题
2. 备选方案是否充分，淘汰理由是否成立
3. 边界、非目标、约束、风险、回滚条件是否明确
4. 是否遗漏性能、容量、可用性、安全、运维、扩展性、迁移成本等关键视角
5. 图、表、接口说明和实施计划是否一致

如果只是表达瑕疵可直接修正文案；若存在关键缺口，先修正文档再进入合规校验。

## 验证链核查

当文档中包含较多可外部验证的技术断言时，在合规校验前增加一次 `verify-chain` 式核查。

典型触发项：

1. 中间件、云产品、协议或框架的版本能力与兼容性结论
2. 吞吐、延迟、容量、成本、SLA 等引用了公开数据或经验阈值的表述
3. 命令参数、配置项含义、接口行为、限制条件等容易因版本变化失真的事实

可跳过场景：

1. 文档主体是内部取舍、组织边界或业务优先级判断
2. 只是本地草稿收敛，用户明确要求先成文后核查
3. 当前环境不具备联网核查条件

执行要求：

1. 先由评审阶段提取需要核查的关键断言，不要把整篇文档不加筛选地送去核查
2. 只修正被核实有误、不完整或已过时的事实，不重写已成立的决策结构
3. 无法完成核查时，必须显式记录跳过原因，再继续后续流程

## 合规校验

模板级详细清单以模板文件为准。主流程只保留快速判断：

1. ADR：编号、状态、替代方案、后果、撤销条件完整
2. 技术提案：架构图、时序图、方案对比、风险、排期、验收标准完整
3. 简报：问题、推荐方案、风险、成本、决策需求完整且能在一页内表达

## 通用格式校验

1. 不写原始 HTML，改用 `confluence-storage` 围栏
2. emoji 只使用受支持名称
3. Mermaid 节点标签避免 `(` `)` `|`
4. 块公式 `$$` 必须独占行首
5. 有序列表插图时改用加粗编号，避免 Confluence 重编号
