## IoT 架构三阶段框架（PasIOT）

用户项目采用三阶段演进模型，回答架构问题时应以此框架为参照：

| 阶段 | 核心建设方式 | 关键词 |
|---|---|---|
| 第一阶段：业务 IOT | 有什么业务起什么服务 | 烟囱系统、设备孤岛、快速交付 |
| 第二阶段：物模型 + 边云协同 | 统一设备能力抽象 + 云边职责分离 | 平台化、标准化、设备影子、规则引擎 |
| 第三阶段：AIOT | 感知→认知→行动智能闭环 | 多模态感知、AI 推理、预测运维、自主执行 |

详细分析见 `references/pasiot-three-stages.md`。

### 物联通用四层结构

| 层 | 职责 |
|---|---|
| 感知层 | 设备或边缘层数据采集 |
| 网络层 | 通讯传输（远程/短程/高带宽/窄带宽） |
| 平台层 | 平台接入、物模型、数据处理（规则引擎、Camel） |
| 应用层 | 基于数据做分析和可视化，用于决策 |

### 第二阶段四大挑战

1. **异构性数据**：JSON/XML/纯文本/16进制——需协议转换层归一化
2. **海量数据处理**：5000亿条时序数据存储场景
3. **安全性保证**：鉴权、mTLS双向认证、黑白名单、数据加密
4. **实时性**：控制指令时延、告警时效、边缘本地响应

## AIOT "感认行"闭环

```
感知 → 归一化 → 认知 → 决策 → 执行 → 验证 → 学习
```

- **感**：多模态采集（传感器、视频、音频、用户行为、工单文本）
- **认**：状态理解、故障诊断、意图识别、趋势预测、根因分析
- **行**：设备控制、工单创建、OTA、策略执行、结果验证

## 物理 AI 与具身智能

- **物理 AI（Physical AI）**：AI 对物理规律、空间环境、设备约束和动作结果的理解
- **具身智能（Embodied Intelligence）**：智能体通过传感器和执行器在真实环境中持续感知、规划和行动
- 物联场景载体：机器人、自动驾驶车辆、智能产线、无人仓储、能源系统
- 具身智能 ≠ 接入大模型，需要：多模态感知融合、物理世界模型、安全执行约束、持续学习闭环

## 本体论与动态本体

- **本体论**：对实物构建本体，不断充实语义，构筑其所在图谱世界（企业数字版高德地图）
- **静态本体**：知识图谱——设备类型、空间关系、组织架构、业务规则
- **动态本体**：实时状态 + 历史事件 + 运行规律 + 能力反馈 → 本体持续自我迭代和自我更新

### 元元模型→元模型→模型→实例 四层结构

```
元元模型：基本属性、规则、行为（测点、时间、计算规则）
  ↓
元模型：基础模型（物模型）
  ↓
模型：本体类（产品）
  ↓
实例：本体对象（设备）
```

### 能力与数据双飞轮

- **数据飞轮**：采集 → 提炼 → 验证 → 资产化 → 重复迭代
- **能力飞轮**：工具能力（规则库、决策树、工作流、模板库、低代码包、知识库、脚本）→ 现场执行 → 结果反馈 → 能力评估 → 增量优化（联邦学习 + 增量优化）
- 双飞轮突破产品边界思维：能力飞轮形成工具和反哺能力对数据进行反馈

## 物联机理仿真（AIOT 最终目标）

```
边端感知 → 云端接入 → 模型底座（机理打造/数据建模）→ 数字孪生 → 仿真推演
```

### 三种模型职责区分

| 模型 | 职责 | 回答的问题 |
|---|---|---|
| 物模型 | 设备能采什么、能做什么 | What（能力契约） |
| 机理模型 | 设备为什么这样运行（热力学、运动方程、运行约束） | Why（物理知识底座） |
| 数据模型 | 从运行数据中能学习什么 | What-if（数据驱动预测） |

### 仿真流程

```
真实设备数据 → 校准机理模型和数据模型 → 数字孪生状态
  → 候选策略仿真 → 风险/成本/收益评估 → 执行与结果反馈
```

## AI 决策安全约束

高风险场景必须遵循"AI 建议 + 规则兜底"：
1. AI 提出建议
2. 确定性规则校验（参数范围、权限、安全边界）
3. 审批机制（高风险需人工确认）
4. 执行 + 结果验证
5. 熔断和回滚能力

**不建议自动执行**：工业安全联锁、高压设备控制、核心产线停机、OTA 全量升级、涉及人身安全的设备动作。

## 知识文档编辑工作流

当用户要求在 AIOT笔记.md 或类似知识文档中补充内容时：

1. **先读后写**：读取目标章节当前内容和后续章节标题，确认插入点
2. **批量编号**：如果插入新章节会导致编号变化，一次性完成所有重新编号（不要逐节修改，避免级联"继续"提示）
3. **保留上下文**：不删除用户已有内容，在合适位置插入新章节
4. **回读校验**：写入后 grep 关键标题和概念，确认落盘正确
5. **行数报告**：每次重大编辑后报告文件总行数，让用户感知文档规模变化

### Wiki 三层架构工作流（AIOTK 项目）

AIOTK 项目采用 Karpathy 三层 Wiki 架构（`raw/` → `wiki/` ← `CLAUDE.md` 规则），当用户要求将知识整理到 Wiki 时：

1. **Raw 不可变**：`raw/` 目录下文件绝对禁止修改，仅作为事实来源归档
2. **先归档 raw，再编译 wiki**：将原始笔记复制到 `raw/notes/`，然后在 `wiki/sources/` 创建摘要页
3. **YAML frontmatter 必填**：每个 wiki 页面必须包含 frontmatter（title、type、created、updated 等）
4. **Kebab-case 文件名**：所有 wiki 文件名使用小写连字符命名（如 `pasiot-three-stages.md`）
5. **至少 3 条双链**：每个知识页至少包含 3 个 `[[path/name]]` 双向链接，避免孤立页面
6. **同步更新 index.md**：新增或变更页面后必须更新 `wiki/index.md`
7. **追加 log.md**：每次操作后追加记录到 `wiki/log.md`，格式为 `[操作类型] 路径 | 变更范围 | summary`
8. **Lint 自检**：检查 frontmatter 完整性、链接有效性、命名合规、无孤立页面
9. **保留根文件**：不删除根目录原始文档（如 `AIOT笔记.md`），仅复制到 wiki 和 raw

## Pitfalls

1. **物模型 ≠ 业务模型**：`power=true` 是设备属性，`房间舒适度达标` 是业务指标，`本月节能率` 是运营指标。不要把业务字段塞进物模型。
2. **设备影子不是真实状态**：影子是云端管理视图，设备离线期间影子可能与实际不一致。
3. **边云职责冲突**：实时控制和本地自治归边缘，全局分析和资产管理归云端，不要混用。
4. **AI 幻觉导致误控**：AIOT 阶段必须有确定性规则兜底，不能让大模型直接操作设备。
5. **数据量爆炸**：10 万设备 × 20 属性 × 每分钟上报 = 28.8 亿条/天，必须提前规划边缘聚合、变化上报、分层存储。
6. **跨厂商映射成本**：统一物模型后，每个厂商设备的协议映射仍需开发和维护，低估此成本会导致项目延期。
7. **架构模式错配**：第一阶段不一定要微服务——游戏/军工等强一致性场景用单体更合适；DDD/CQRS 是复杂度上升后的优化手段，不应过早引入。微服务拆分优先考虑独立计算模块、高 QPS 服务和旁路服务三类。
8. **JetLinks vs ThingsBoard 物模型定位不同**：JetLinks 物模型是前置约束（先定义物模型再编解码），强调管控；ThingsBoard 物模型是后置约束（Converter 中转换），强调灵活。选型时需根据标准化治理需求决定。
9. **协议分层理解**：IoT 协议应区分通信协议（MQTT/HTTP/TCP/UDP/CoAP）、工业通信协议（ModBus/OPC UA/BACnet IP）和物联数据协议（对异构数据做业务范式下的标准化认识）。物联数据协议才是"协议转换"的核心。
10. **物模型三层模型**：物模型→产品→设备是三层结构。物模型定义抽象能力（属性/事件/操作/标签），产品以品牌+型号继承物模型，设备在产品基础上扩展个性属性（IMEI/SN/经纬度/海拔等）。
11. **海量存储选型**：时序遥测数据优先 TDengine/InfluxDB，不要用 MySQL；OLAP 与 OLTP 分离；冷热分层存储。5000亿条时序数据是真实规模，需提前规划。
12. **时序存储深度对比**：InfluxDB（社区生态好、Flux 语法）、TDengine（超级表+连续查询、高压缩比、国产首选）、TimescaleDB（PG 扩展、SQL 兼容、适合已有 PG 栈）、ClickHouse（列存 OLAP、聚合查询极快但不适合高频单行写入）、HBase（超大规模归档、写多读少、延迟高）。5000亿条场景推荐 TDengine 做热时序 + ClickHouse 做聚合分析 + HBase/对象存储做冷归档。
13. **动态本体 ≠ 静态模型**：知识图谱是静态本体，动态本体需要实时状态、历史事件、运行规律和能力反馈持续迭代，双飞轮（数据飞轮+能力飞轮）驱动自我更新。
14. **物模型/机理模型/数据模型三者互补**：物模型定义能力契约（What），机理模型描述物理原理（Why），数据模型学习运行规律（What-if）。AIOT 仿真推演需要三者协同。
15. **M7 语音包重新压缩仅遍历根目录**：`VoiceListServiceImpl.handleVoiceFile`（~L579）解压原 ZIP 时支持子目录，但重新压缩时只遍历 `tmpWorkDirectory.listFiles()`（第一层），且仅保留根目录下 `endsWith(".mp3")`（大小写敏感，`.MP3` 不匹配）的文件和 `index` 文件；`.wav`、图片、文本及子目录内的文件全部被丢弃。**症状**：上传后 ZIP 只剩 `index`，MP3 音频全部丢失。**修复方向**：重新压缩时递归遍历子目录并保留相对路径。修改此流程前务必先核对原 ZIP 的目录结构。详见 `references/m7-voice-pack-versioning.md`。
16. **OTA 版本查询优先级覆盖**：`DevServiceImpl.getUpgradeDeviceVersion` 的优先级链是 压测 > 定推 > 关键版本 > 最新版本。定推任务会覆盖关键版本和最新版本，如果设备有定推记录但已是目标版本，定推记录会被自动清除（`removeSpecifyPushById`）。排查"设备查不到预期版本"时，先检查是否有压测或定推任务覆盖了正常版本查询。详见 `references/ota-upgrade-flow.md`。
17. **OTA 黑名单仅判定导航模块**：`BanListServiceImpl.checkAddBanList` 只处理 `FIRMWARE_IS_MODULE_1`（导航模块）且 `upgradeStatus=3`（失败）的设备，整包升级失败不会触发自动黑名单。排查黑名单未生效时需确认失败模块类型。同时压测设备被排除在黑名单判定之外。详见 `references/ota-upgrade-flow.md`。
