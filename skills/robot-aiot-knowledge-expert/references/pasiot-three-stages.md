# PasIOT 三阶段演进详细分析

> 来源：用户会话 2026-08-04，对 PasIOT 三阶段架构的完整梳理

## 总体框架

| 阶段 | 核心建设方式 | 系统关注点 | 典型特征 |
|---|---|---|---|
| 第一阶段：业务 IOT | 有什么业务，就建设什么服务 | 功能上线和业务交付 | 烟囱式系统、设备孤岛、协议孤岛 |
| 第二阶段：物模型 + 边云协同 | 先抽象设备和能力，再承载业务 | 统一连接、统一模型、云边协同 | 平台化、标准化、复用能力 |
| 第三阶段：AIOT | 以感知、认知、行动构建智能闭环 | 自主理解、自主决策、自主执行 | 多模态感知、AI 推理、智能控制 |

## 第一阶段：以业务为基准的业务 IOT

### 特性

- 业务优先：系统以业务流程为中心
- 快速交付：快速接入设备、实现功能、支持业务流程
- 服务与业务强绑定：一个业务 ≈ 一套服务 ≈ 一套数据模型 ≈ 一套设备接入

### 技术架构

```
设备 → 专用协议接入 → 业务服务 → 专用数据库 → 业务前端/App
```

每个业务独立建设完整链路，服务名称直接体现业务含义（如 `air-conditioner-service`、`lighting-service`）。

### 架构模式选型（第一阶段适用）

第一阶段的业务 IoT 在架构模式上并非只有一种选择，需根据业务特征决定：

#### 单体架构（Monolith）

**适用场景**：游戏、军工/国防、强一致性要求高的场景

- 强一致性：单体内部调用无需经过网络，事务天然 ACID，避免分布式一致性的复杂度
- 减少网络开销：进程内调用 vs RPC/HTTP，时延从毫秒级降到微秒级
- 运维简单：一个进程、一次部署、一条监控链路
- 适合设备数量有限、业务逻辑紧密耦合、实时控制要求极高的场景

**IoT 典型用例**：
- 军工装备控制系统（不能容忍网络分区导致的指令丢失）
- 游戏外设实时控制（手柄→主机→设备，时延敏感）
- 单一产线紧耦合控制系统

#### 微服务架构（Microservices）

**适用场景**：独立计算模块、资源密集型服务、旁路服务

三种典型拆分模式：

1. **独立计算模块**：数据汇总分析服务
   - 与主业务流程解耦，可独立扩缩容
   - 典型：能耗统计、设备报表、运营看板

2. **资源密集型服务**：高 QPS 服务
   - 独立部署，避免拖垮主业务
   - 典型：设备状态查询（万级设备并发心跳）、指令下发网关

3. **旁路服务**：发送邮件/短信、记录用户行为日志
   - 非核心路径，允许异步和最终一致性
   - 典型：告警通知、操作审计日志、消息推送

**IoT 微服务拆分原则**：
- 按业务领域拆（空调服务、照明服务、能耗服务）
- 按资源特征拆（CPU 密集 vs I/O 密集 vs 高 QPS）
- 旁路逻辑异步化（消息队列解耦）

#### DDD + CQRS

**适用场景**：领域驱动建模、读写分离

- **DDD**：以领域为核心组织代码，适合业务逻辑复杂的 IoT 系统
   - 限界上下文（Bounded Context）对应业务域（设备域、告警域、工单域）
   - 聚合根（Aggregate Root）对应核心实体（设备、产品、规则）
   - 领域事件（Domain Event）解耦跨域协作

- **CQRS**：命令与查询分离
   - 写侧（Command）：设备控制、属性设置、规则创建 → 走主库，保证一致性
   - 读侧（Query）：设备列表、状态查询、历史数据 → 走从库/缓存/时序库，支持高并发
   - 适合 IoT 读多写少的场景（百万级设备状态查询 vs 千级指令下发）

#### 整洁架构（Clean Architecture）

核心思想：业务规则不应依赖具体框架、数据库、消息中间件或设备协议；外部技术通过适配器接入核心业务。

**IoT 场景收益**：
- 设备控制领域不依赖 MQTT 客户端、Modbus 寄存器或 BACnet 对象
- 云端控制和边缘控制可复用同一领域规则
- 协议替换或厂商 SDK 隔离时不影响业务逻辑
- 模拟设备测试更简单

**注意**：整洁架构不是无限分层，对简单查询保持简化；对设备控制、告警、OTA、权限和安全联锁等核心链路，应优先保护领域规则和依赖方向。

#### 中台架构

核心思想：把多个业务反复建设的共性能力沉淀为平台能力，通过标准接口和领域服务向上层业务复用。

**IoT 设备中台能力**：设备注册/认证/生命周期、产品与物模型、属性/服务/事件、设备影子、OTA、规则引擎、数据权限、协议适配

**业务中台能力**：用户/租户/组织/空间、设备绑定、告警/工单/售后、通知/计费/能耗/运营分析

**技术中台能力**：API 网关、认证授权、Kafka/MQTT Broker/Redis、时序数据库/对象存储、日志/指标/链路追踪/审计、限流/熔断/灰度发布

**架构思想关系**：
- DDD：划分领域边界
- 整洁架构：保护领域核心和依赖方向
- CQRS：分离控制写入与数据查询
- 中台架构：沉淀跨业务复用能力
- 微服务：按独立部署和资源特征拆分
- 边云协同：决定能力运行在边缘还是云端

**推荐演进路径**：

```
DDD 划分边界 → 整洁架构保护领域核心 → CQRS 分离控制写入与数据查询
→ 中台沉淀跨业务复用能力 → 微服务按独立部署和资源特征拆分 → 边云协同决定能力的执行位置
```

**选型决策参考**：

| 条件 | 推荐模式 | 原因 |
|---|---|---|
| 强一致性 + 低时延 + 业务紧密耦合 | 单体 | 进程内调用，无需分布式事务 |
| 多业务域 + 需独立扩缩 + 旁路异步 | 微服务 | 按领域和资源特征拆分 |
| 复杂业务规则 + 读写比差异大 | DDD + CQRS | 领域建模清晰，读写各取最优 |

**注意**：第一阶段通常先用单体或简单微服务快速交付，DDD/CQRS 是业务复杂度上升后的优化手段，不应过早引入。

### 主要问题

1. **设备和业务高度耦合**：控制逻辑直接写在业务服务中，业务需要理解设备协议
2. **业务烟囱**：每个业务独立设备模型、Topic 设计、状态表、告警表、用户绑定
3. **设备数据无法复用**：同一设备数据被多个系统重复采集
4. **数据标准不统一**：不同团队定义不同字段（power vs switchStatus vs onOff）
5. **边缘能力不足**：所有逻辑放云端，网络断开时无法控制
6. **业务创新成本高**：跨设备联动需要重新开发跨业务系统

### 解决方向

1. 统一设备身份
2. 统一物模型
3. 独立设备接入层
4. 业务与设备解耦
5. 统一数据和事件模型
6. 边缘网关 + 云边协同
7. 平台化设备能力

## 第二阶段：以物模型和边云协同为基础的 IoT

### 物联通用四层结构

第二阶段 IoT 系统可归纳为四层：

| 层 | 职责 | 典型组件 |
|---|---|---|
| 感知层 | 设备或边缘层数据采集 | 传感器、执行器、边缘网关、RTU |
| 网络层 | 通讯传输（远程/短程/高带宽/窄带宽） | MQTT、CoAP、Modbus TCP、BACnet/IP、LoRa、NB-IoT、4G/5G |
| 平台层 | 平台接入、物模型、数据处理（规则引擎、Camel） | EMQX、JetLinks、ThingsBoard、Kafka、规则引擎 |
| 应用层 | 基于数据做分析和可视化，用于决策 | 看板、报表、告警中心、运维助手 |

### 四大挑战

1. **异构性数据**：JSON、XML、纯文本、16进制数据——设备上报格式不统一，需协议转换层归一化
2. **海量数据处理**：设备规模扩大后时序数据量指数增长（5000亿条时序数据存储场景）
3. **安全性保证**：
   - 鉴权：设备身份认证、Token/API Key
   - 双向认证：TLS mTLS（X.509 设备证书）
   - 黑白名单：IP/MAC/设备ID 访问控制
   - 数据加密：传输层 TLS、应用层 payload 加密
4. **实时性**：控制指令时延要求、告警触发时效、边缘本地响应

### 特性

- 设备能力标准化：设备能力从协议字段中解耦
- 协议和业务解耦：协议适配层映射不同协议到统一物模型
- 设备平台化：通用能力（注册、认证、物模型管理、影子、OTA、告警、规则引擎）
- 边云协同：实时控制和本地自治归边缘，全局分析和资产管理归云端

### 协议分层：通信协议 vs 物联数据协议

IoT 协议需区分为两层理解：

| 层 | 含义 | 典型协议 |
|---|---|---|
| 通信协议 | 负责设备与平台之间的消息传输通道 | MQTT、HTTP、TCP、UDP、CoAP |
| 工业通信协议 | 面向工业/楼宇现场总线的传输协议 | ModBus、OPC UA、BACnet IP |
| 物联数据协议（物联协议） | 对异构数据在业务范式下进行标准化认识和解析 | 物模型编解码、DeviceMessageCodec、Converter |

物联数据协议是对异构数据（JSON/XML/纯文本/16进制）进行业务范式下的统一理解，是"协议转换"的核心。

### 物模型三层模型

物模型不是单一概念，而是"物模型→产品→设备"三层结构：

| 层 | 职责 | 包含内容 |
|---|---|---|
| 物模型 | 定义设备类型的抽象能力 | 基础属性、量测属性、事件（上行）、操作（下行）、标签 |
| 产品 | 继承物模型，以品牌和型号确定 | 物模型能力 + 产品规格定义 |
| 设备 | 在产品基础上具体实现和个性扩展 | 基础属性（IMEI、SN、经纬度、海拔、生产商、所属企业、位置空间）、量测属性实例、事件（上下线）、操作（上报量测、上报状态、下行指令控制）、标签实例 |

```
物模型（抽象能力定义）
  └─ 产品（品牌+型号，继承物模型）
       └─ 设备（具体实例，扩展个性属性）
```

### 物模型 JSON 示例

```json
{
  "productKey": "air-conditioner",
  "properties": [
    {"id": "power", "name": "电源状态", "type": "boolean", "accessMode": "rw"},
    {"id": "targetTemperature", "name": "目标温度", "type": "number", "unit": "°C", "min": 16, "max": 30, "accessMode": "rw"},
    {"id": "indoorTemperature", "name": "室内温度", "type": "number", "unit": "°C", "accessMode": "r"}
  ],
  "services": [{"id": "setMode", "input": {"mode": ["cool","heat","fan","auto"]}}],
  "events": [{"id": "fault", "parameters": {"code": "string", "severity": "integer"}}]
}
```

### 设备影子

设备影子（Shadow Device）是对物理世界设备状态的数字化描述，使用 metadata 进行表达，处理离线状态、事件告警等场景。

```json
{
  "deviceId": "ac-001",
  "desired": {"power": true, "targetTemperature": 24},
  "reported": {"power": false, "targetTemperature": 26},
  "version": 12,
  "syncStatus": "PENDING"
}
```

解决：离线状态管理、期望状态记录、上线自动补偿、多端查看、指令幂等。

### JetLinks vs ThingsBoard 对比

两者均采用"传输组件+协议"方式采集和解析数据，通过队列经由规则引擎处理，但物模型约束方式不同：

| 对比项 | JetLinks | ThingsBoard |
|---|---|---|
| 物模型定位 | 物模型是**前置约束**：先定义物模型，协议编解码实现 DeviceMessageCodec 标准化 | 物模型是**后置约束**：在协议 Converter 中进行标准转换，由使用者决定 |
| 核心理念 | 物模型驱动标准化解析，强调**管控** | 协议转换器驱动灵活适配，强调**灵活** |
| 规则编排 | 规则链 + 规则引擎 | 丰富的流程化编排工具 |
| 适用场景 | 对设备标准化和治理要求高的企业 | 需要快速接入多协议、灵活定制的场景 |

### 海量数据存储技术选型

| 场景 | 推荐存储 | 说明 |
|---|---|---|
| 时序数据（设备遥测） | TDengine | 超级表、连续查询、高压缩比；5000亿条时序数据场景首选 |
| 时序数据（替代方案） | InfluxDB、TimescaleDB | 社区生态好 / PG 扩展兼容 |
| OLTP（设备元数据、业务事务） | MySQL、TiDB、OceanBase | 关系型、分布式事务、高可用 |
| OLAP（运营分析、报表） | ClickHouse、Doris | 列存、聚合查询性能优 |
| 全文检索 / 日志 | Elasticsearch | 设备日志、告警检索、工单搜索 |
| 文档型（非标设备数据） | MongoDB | 灵活 Schema、适合异构数据暂存 |
| 大规模扫描 / 宽表 | HBase | 超大规模历史数据归档 |

选型原则：
- 时序数据优先 TDengine/InfluxDB，不要用 MySQL 存遥测数据
- OLAP 与 OLTP 分离：设备控制走 OLTP，运营分析走 OLAP
- 冷热分层：近期数据热存储（TDengine/ClickHouse），历史数据归档（HBase/对象存储）

### 解决的问题

1. 设备接入复用：多个业务共用统一设备平台
2. 跨设备联动：基于统一事件模型的规则引擎
3. 断网自治：边缘本地规则执行
4. 设备数据治理：统一校验、单位换算、数据质量
5. 多厂商兼容：不同厂商映射到同一物模型

### 新问题

1. **物模型设计困难**：过于简单丢特性，过于复杂难管理 → 建议分层（通用→产品→扩展）
2. **物模型 ≠ 业务模型**：不能把业务字段塞进物模型
3. **边云职责冲突**：需明确实时控制 vs 全局管理边界
4. **数据量爆炸**：10万设备×20属性×每分钟=28.8亿条/天 → 边缘聚合、变化上报、分层存储

## 海量时序存储深度对比（5000亿条场景）

### 存储引擎特性对比

| 特性 | TDengine | InfluxDB | TimescaleDB | ClickHouse | HBase |
|---|---|---|---|---|---|
| 类型 | 专用时序数据库 | 专用时序数据库 | PG 扩展（时序超表） | 列存 OLAP 数据库 | 宽表 NoSQL |
| 数据模型 | 超级表（一个设备一条子表） | Measurement + Tags + Fields | 超表（Hypertable）+ PG 表 | MergeTree 系列引擎 | Region + Column Family |
| 写入模式 | 批量追加，单条也可 | 批量 Line Protocol | SQL INSERT / COPY | 批量 INSERT（建议万级批次） | 批量 Put |
| 压缩比 | 极高（列存+差分+游程编码） | 较高（列存） | 依赖 PG TOAST + 原生压缩 | 极高（列存+LZ4/ZSTD） | 中等（Snappy/LZ4） |
| 查询语言 | SQL（部分兼容） | InfluxQL / Flux | 标准 SQL（PG 全兼容） | SQL（丰富聚合函数） | 需配合 Phoenix 或 Hive |
| 降采样/预聚合 | 连续查询（Continuous Query） | 任务（Task） | 连续聚合（Continuous Aggregate） | 物化视图（Materialized View） | 无原生支持 |
| 集群 | 开源支持 | 企业版才支持 | PG 生态（Citus/Patroni） | 原生分布式 | 原生分布式（HDFS） |
| 生态 | 国产、IoT 行业适配好 | Grafana/Telegraf 生态完善 | PG 生态（插件丰富） | 通用 OLAP 生态 | Hadoop 生态 |
| 适合写入频率 | 高频实时写入 | 高频实时写入 | 中高频实时写入 | 批量写入为主（不适合高频单行） | 批量写入 |
| 适合查询模式 | 时间范围聚合、最新值 | 时间范围聚合、最新值 | 复杂 JOIN + 时间聚合 | 大范围聚合分析、报表 | 大范围扫描、归档查询 |
| 延迟 | 毫秒级（单表） | 毫秒级 | 毫秒级 | 秒级（大查询） | 百毫秒~秒级 |

### 5000亿条场景分层存储建议

```
热数据（近7~30天）：TDengine 超级表
  ↓ 降采样/连续查询
温数据（近1年聚合）：ClickHouse MergeTree
  ↓ 生命周期迁移
冷数据（1年以上归档）：HBase + 对象存储（Parquet/ORC）
```

| 层 | 存储 | 原因 |
|---|---|---|
| 热时序（实时遥测） | TDengine | 超级表模型匹配设备层级、高压缩比、连续查询、IoT 原生 |
| 温时序（聚合分析） | ClickHouse | 列存 OLAP、聚合查询极快、物化视图预计算 |
| 冷归档（历史保留） | HBase + 对象存储 | 超大规模存储、低成本、写多读少 |
| 替代热时序 | InfluxDB | 社区生态好、Grafana 集成方便、适合非国产优先项目 |
| 替代热时序 | TimescaleDB | 已有 PG 栈团队、SQL 全兼容、适合不想引入新数据库的项目 |

### 选型注意事项

1. **TDengine**：超级表设计要求一个设备一条子表，设备数千万时子表数量需评估；开源版集群能力有限
2. **InfluxDB**：开源版不支持集群，企业版付费；Flux 语法学习成本高，社区正在回归 SQL
3. **TimescaleDB**：本质是 PG 扩展，超大规模时序场景需评估 PG 单机瓶颈；依赖 Citus 做分布式
4. **ClickHouse**：不适合高频单行写入（必须批量），时序场景建议搭配 Kafka + 批量消费写入
5. **HBase**：查询灵活性差，不适合实时分析；更适合作为冷归档层配合 Hive/Spark 做离线分析

## 第三阶段：以 AI 和"感、认、行"平台为基础的 AIOT

### "感认行"三层

- **感（全域感知）**：多模态采集（传感器、视频、音频、用户行为、工单文本），形成统一状态
- **认（状态理解与智能决策）**：故障诊断、意图识别、异常检测、根因分析、趋势预测、策略生成
- **行（执行与闭环）**：设备控制、工单创建、OTA、策略执行、结果验证

### 闭环

```
感知 → 归一化 → 认知 → 决策 → 执行 → 验证 → 学习
```

### 技术理念转变

1. 从数据采集 → 状态理解
2. 从规则驱动 → 规则 + 模型驱动
3. 从单设备控制 → 系统级优化
4. 从被动告警 → 预测性运维
5. 从人机交互 → 自然语言 + 智能代理

### 物理 AI 与具身智能

- **物理 AI（Physical AI）**：AI 对物理规律、空间环境、设备约束和动作结果的理解
- **具身智能（Embodied Intelligence）**：智能体通过传感器和执行器在真实环境中持续感知、规划和行动
- 物联场景载体：机器人、自动驾驶车辆、智能产线、无人仓储、能源系统
- 具身智能 ≠ 接入大模型，需要：多模态感知融合、物理世界模型、安全执行约束、持续学习闭环

### 本体论与动态本体

- **本体论**：对实物构建本体，不断充实语义，构筑其所在图谱世界（企业数字版高德地图）
- **静态本体**：知识图谱——设备类型、空间关系、组织架构、业务规则
- **动态本体**：实时状态 + 历史事件 + 运行规律 + 能力反馈 → 本体持续自我迭代和自我更新

#### 元元模型→元模型→模型→实例 四层结构

```
元元模型：基本属性、规则、行为（测点、时间、计算规则）
  ↓
元模型：基础模型（物模型）
  ↓
模型：本体类（产品）
  ↓
实例：本体对象（设备）
```

#### 能力与数据双飞轮

- **数据飞轮**：采集 → 提炼 → 验证 → 资产化 → 重复迭代
- **能力飞轮**：工具能力（规则库、决策树、工作流、模板库、低代码包、知识库、脚本）→ 现场执行 → 结果反馈 → 能力评估 → 增量优化（联邦学习 + 增量优化）
- 双飞轮突破产品边界思维：能力飞轮形成工具和反哺能力对数据进行反馈

### 物联机理仿真（AIOT 最终目标）

```
边端感知 → 云端接入 → 模型底座（机理打造/数据建模）→ 数字孪生 → 仿真推演
```

#### 三种模型职责区分

| 模型 | 职责 | 回答的问题 |
|---|---|---|
| 物模型 | 设备能采什么、能做什么 | What（能力契约） |
| 机理模型 | 设备为什么这样运行（热力学、运动方程、运行约束） | Why（物理知识底座） |
| 数据模型 | 从运行数据中能学习什么 | What-if（数据驱动预测） |

- **数字孪生**：物理世界的虚实映射（如汽车-人-高速），不仅镜像状态，还支持推演
- **仿真推演**：基于模型对事物的动态推演（如人驾驶汽车在高速上行驶，人本身对驾驶影响，周围环境对驾驶的影响）

#### 仿真流程

```
真实设备数据 → 校准机理模型和数据模型 → 数字孪生状态
  → 候选策略仿真 → 风险/成本/收益评估 → 执行与结果反馈
```

#### 仿真应用场景

- 设备参数调整前验证
- 生产线改造和产能规划
- 能源调度和峰值削减
- 车辆路径和驾驶策略
- 故障注入和应急演练
- AI 策略上线前的离线评估

最终目标：通过动态推演计算能力，减少人为因素影响，达到生产力提升。

### 必须补齐的能力

1. **物模型 → 状态模型**：从"设备能做什么"到"当前环境和设备处于什么状态"
2. **事件中心**：统一设备事件、环境事件、用户事件、AI推理事件、策略执行事件
3. **知识库 + 知识图谱**：产品知识、故障码、维修手册、设备拓扑、空间关系
4. **AI 可调用工具体系**：查询状态、读取物模型、执行设备服务、创建工单（受控调用，非直接操作）
5. **"AI 决策、规则兜底"机制**：AI建议 → 规则校验 → 权限校验 → 安全边界 → 执行 → 验证

### AI 控制安全

- **不建议自动执行**：工业安全联锁、高压设备控制、核心产线停机、OTA 全量升级、涉及人身安全的设备动作
- **适合自动执行**：非关键设备温度调节、普通照明控制、数据采集频率调整、非核心服务重启、告警通知、工单创建

## 三阶段核心对比

| 对比项 | 业务 IOT | 物模型+边云协同 | AIOT |
|---|---|---|---|
| 核心对象 | 业务功能 | 设备能力和业务能力 | 环境状态和业务目标 |
| 建设方式 | 一个业务一套系统 | 统一设备平台承载多个业务 | AI 平台驱动多系统协同 |
| 设备接入 | 业务服务直接接入 | 独立接入层统一接入 | 多模态、全域感知 |
| 数据模型 | 业务自定义 | 统一物模型 | 物模型+状态模型+知识模型 |
| 控制方式 | 云端指令 | 云边协同控制 | AI决策+规则约束+自动执行 |
| 规则能力 | 硬编码 | 规则引擎 | 规则+模型+智能代理 |
| 边缘能力 | 较弱 | 本地规则+协议转换 | 边缘AI+本地自治 |
| 数据价值 | 支撑单一业务 | 数据共享和平台复用 | 预测、推理和决策 |
| 运营方式 | 人工监控 | 平台化运营 | 自主运营和预测运营 |
| 典型问题 | 重复建设、烟囱 | 平台复杂、模型治理 | 幻觉、误控、安全责任 |
| 架构模式 | 单体/简单微服务 | 微服务+平台化 | 微服务+AI服务+事件驱动 |

## 迁移建议

### 第一阶段 → 第二阶段

1. 盘点设备和业务（厂商、协议、接入方式、数据字段）
2. 建立统一设备身份（tenantId/productId/deviceId/gatewayId/locationId/protocol）
3. 设计核心物模型（先选高复用设备：空调、灯光、电表、温湿度、门锁、网关）
4. 建设协议适配层
5. 迁移业务调用方式（业务→Device Service API→物模型平台→设备）
6. 逐步引入边缘能力（优先迁移低时延控制、断网必需逻辑、高频采集）

### 第二阶段 → 第三阶段

1. 补充数据和状态基础（设备影子、空间关系、设备拓扑、用户行为、工单）
2. 优先做辅助型 AI（故障问答、运维助手、日志摘要、告警聚合、能耗分析）
3. 再做建议型 AI（由人工确认再执行）
4. 最后做自动执行型 AI（仅限非关键场景）

### 第二阶段 → 第三阶段判断标准

| 能力 | 第二阶段 | 第三阶段 |
|---|---|---|
| 设备管理 | 知道设备是否在线 | 理解设备为什么异常 |
| 数据处理 | 存储和查询 | 推断状态和趋势 |
| 告警 | 超阈值告警 | 预测故障和根因分析 |
| 控制 | 执行明确指令 | 根据目标自动生成策略 |
| 运维 | 人工查看告警 | 自动推荐和创建工单 |
| 规则 | 固定条件触发 | AI建议+规则约束 |
| 边缘 | 协议转换和缓存 | 本地推理和自治闭环 |
