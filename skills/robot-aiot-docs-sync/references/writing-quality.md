# Module 5: 中文文档质量与一致性收口

本模用于在所有目标文档生成完成后做统一收口。

## 5.1 中文技术写作基线

1. 中文为主，技术名词保留英文原文，如 `README`、`API`、`Spring Boot`、`Redis`
2. 中英文之间加空格，中文与数字之间加空格
3. 中文语境优先全角标点；代码、命令、路径、协议和英文原句保持半角
4. 技术术语首次出现时，必要时补充中英对照，如“消息队列（Message Queue）”
5. 避免过度翻译行业通用术语，避免把 `Controller`、`Service`、`Redis` 强行翻成不自然中文

## 5.2 文风要求

1. 避免“强大”“优雅”“现代化”“企业级”这类空泛营销语
2. 避免 AI 腔、机翻味、被动语态和欧化长句
3. 一句话只表达一层意思；长句拆短句，长段拆列表
4. 优先给出真实命令、真实路径、真实文件名、真实模块名
5. 信息不足时写 `TODO: 待补充`，不要编造能力、指标和案例

## 5.3 五类文档的收口重点

### `AGENTS.md`

1. 面向 Agent，句子直接、约束明确
2. 命令、路径、入口和规则优先使用列表，不写宣传式介绍
3. 项目约束不得被通用模板覆盖

### `README.md`

1. 首屏需要满足 30 秒价值判断：这是什么、适合谁、怎么开始
2. 安装和快速开始命令必须能直接复制
3. 示例优先短而真实，不堆砌无效口号

### `CHANGELOG.md`

1. 每条变更尽量对应可追溯提交、Issue、PR 或 CVE
2. 条目短句化，避免把实现细节写成大段流水账
3. 分类标题使用项目现有风格，没有则使用稳定默认风格

### `docs/project-map.md`

1. 目录树不超过 3 层
2. 每个关键目录只给一句职责说明
3. 不把所有文件都罗列成噪音清单

### `docs/architecture.md`

1. 先给系统概览，再给模块关系和数据流
2. Mermaid 图服务于说明，不堆砌复杂节点
3. FAQ、限制、扩展点只写可证实内容

## 5.4 最终检查清单

### 排版

1. 中英文之间是否有空格
2. 中文与数字之间是否有空格
3. 中文语境是否使用全角标点
4. 代码块是否标注语言
5. 链接是否可点击且文案自然

### 术语

1. 同一术语前后是否一致
2. 首次出现的重要术语是否需要中英对照
3. 是否出现过度翻译或直译痕迹

### 内容

1. 是否每个结论都能在代码、配置、文档或 Git 历史中找到依据
2. 是否保留了真实命令、真实路径和真实入口
3. 是否仍有需要人工补充的内容，并已明确标成 `TODO: 待补充`
4. 是否存在空泛描述、重复段落或 AI 腔
