# Robot AIoT Commit

为本项目生成短、准、可审查的提交说明。核心目标不是写花哨 commit，而是让 reviewer 一眼看懂：

1. 这是修复、功能、优化、文档还是杂项
2. 这次改动解决了什么业务或工程问题
3. 分支对应的 JIRA 标识是什么
4. 具体 diff 涉及了哪些关键修改

## 提交类型

本项目统一使用以下大写类型：

1. `FIX`：问题修复
2. `FEAT`：新功能
3. `ENH`：优化提升
4. `DOC`：文档等修改
5. `CHORE`：编译脚本、版本号、依赖、工具链等修改

选择规则：

1. 引入新能力、对外新增功能时用 `FEAT`
2. 修复错误行为、缺陷、异常、兼容性问题时用 `FIX`
3. 不新增对外功能，但改善性能、稳定性、结构、体验时用 `ENH`
4. 仅文档、说明、示例、注释等改动时用 `DOC`
5. 构建、脚本、配置、发版号、依赖升级等工程性调整时用 `CHORE`

若一次改动跨多类，按用户最关心的主目标选一个主类型，不混写多个类型。

## 输出格式

默认输出三行，严格控制长度：

```text
<TYPE>: <业务修改总结>
JIRA: <branch-last-segment>
DIFF: <具体修改代码总结>
```

长度限制：

1. 第一行 `<业务修改总结>` 不超过 100 个字符
2. 第三行 `<具体修改代码总结>` 不超过 500 个字符
3. 所有内容优先中文，保留必要英文术语、模块名、类名、命令名

写法要求：

1. 第一行写业务或工程结果，不写“修改代码”“调整一些内容”这类空话
2. 第三行基于真实 diff，总结关键文件、核心动作、影响点和边界
3. 不重复堆砌文件列表；只保留 reviewer 真正需要的改动摘要
4. 不写 AI 生成说明，不写无意义客套话

## JIRA 提取规则

从当前 Git 分支提取 JIRA 标识。

标准规则：

1. 优先按 `/` 分段
2. 若分支是三段结构，取最后一段作为 JIRA
3. 若不是三段结构，仍取最后一段，并在结果中沿用原值
4. 若当前不在 Git 分支、无法获取分支名，明确标记为 `JIRA: [待补充]`

示例：

1. `feature/robot/AIOT-123` -> `JIRA: AIOT-123`
2. `bugfix/order/OMS-998` -> `JIRA: OMS-998`
3. `hotfix/HF-001` -> `JIRA: HF-001`

## 工作流

### 1. 读取状态

先读取并确认：

1. 当前分支名
2. staged 与 unstaged diff
3. 是否存在无关改动

仅当用户明确要求 commit 时，才进入暂存和提交动作。只生成说明时保持只读。

### 2. 判断主类型

根据真实 diff 判断主类型：

1. 新增业务能力 -> `FEAT`
2. 修复错误或回归 -> `FIX`
3. 优化、重构、性能、稳定性提升 -> `ENH`
4. 文档或说明更新 -> `DOC`
5. 构建、脚本、版本、依赖调整 -> `CHORE`

当 `FIX` 与 `ENH` 同时存在时，优先看用户收益：

1. 主要是恢复正确行为，用 `FIX`
2. 主要是提升性能、结构或可维护性，用 `ENH`

### 3. 生成第一行

第一行格式：

```text
<TYPE>: <业务修改总结>
```

生成原则：

1. 用动宾短语，直接说结果，例如“优化技能同步模块的差异处理”
2. 先写业务或工程价值，再写对象
3. 控制在 100 字符内
4. 若用户已有明确总结，优先沿用并压缩润色

### 4. 生成 JIRA 行

第二行固定格式：

```text
JIRA: <branch-last-segment>
```

不要自行杜撰工单号。提取失败就写 `[待补充]`。

### 5. 生成 DIFF 行

第三行固定格式：

```text
DIFF: <具体修改代码总结>
```

生成原则：

1. 必须基于实际 diff，不凭想象补内容
2. 控制在 500 字符内
3. 总结关键改动，不抄大段 diff
4. 优先包含：改了什么、影响哪里、是否补充约束或流程

推荐句式：

1. `DIFF: 更新 A 与 B，补充 C 规则，调整 D 阶段顺序，并明确 E 的校验边界。`
2. `DIFF: 在 X 模块新增 Y 文件，重写 Z 流程说明，同步修正发布前检查和异常降级逻辑。`

### 6. 输出或提交

1. 若用户只要提交文案，直接输出三行结果
2. 若用户明确要求执行 commit，先复核待提交文件范围，再使用这三行作为提交信息
3. 不得把无关改动混入本次提交
4. 不得默认 push；push 需要单独授权

## 与其他 commit skill 的关系

本 skill 吸收以下能力，但以本项目格式为准：

1. `caveman-commit`：保留“短、准、去废话”的压缩表达
2. `chinese-commit-conventions`：保留中文表达、动宾短语和可读性约束
3. `git-commit`：保留按真实 diff 判断类型与范围的思路
4. `git-workflow`：保留只在用户授权时执行 Git 动作、且不混入无关改动的边界

冲突处理：

1. 不使用 `feat(scope): subject` 这种 Conventional Commits 输出作为最终格式
2. 最终格式统一回落到本 skill 的三行模板
3. 若外部仓库强制 conventional commit，再单独提示用户当前项目规范与外部规范可能冲突

## 示例

### 示例 1：优化类提交

```text
ENH: 优化 robot-aiot-adr-confluence 的验证链接入与发布前校验说明
JIRA: AIOT-245
DIFF: 更新 adr-confluence 主流程与 generation-and-review、confluence-publish 两份引用文档，新增按需 verify-chain 核查阶段，明确触发条件、可跳过场景以及发布前必须记录已核查或跳过原因。
```

### 示例 2：修复类提交

```text
FIX: 修复技能同步文档中 rsync 误删风险描述不一致的问题
JIRA: OPS-118
DIFF: 修正 self-skill-sync 主说明与模块文档中的同步规则，去除可能导致误解的删除式表述，统一强调仅新增和覆盖、禁止 --delete，并补充模块边界说明。
```

### 示例 3：文档类提交

```text
DOC: 更新 skills-overview 生成规则为仅扫描全局技能目录
JIRA: DOC-009
DIFF: 重写 docs/skills-overview 的生成口径，移除项目侧技能索引内容，保留 ~/.agents/skills 下 skill 名称、路径和说明，并同步修正文档描述与扫描范围定义。
```

## 守则

1. 先看 diff，再写总结；禁止空泛概括
2. 优先写“为什么值得提交”，其次才是“改了哪些文件”
3. 长度超限时，先压缩形容词和重复背景，不删关键事实
4. 若改动不足以形成单一逻辑提交，应先提醒用户拆分提交
5. 只在用户明确要求时执行 `git add`、`git commit`、`git push`
