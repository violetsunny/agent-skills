# Retro

目标不是重复流水账，而是把一次工作的经验沉淀成后续可执行的改进项。

## 什么时候用

满足以下任一项时使用：

1. 用户明确要求复盘、回顾、retrospective、postmortem
2. 一次开发、排障、交付或协作刚结束，需要总结得失
3. 同类问题可能再次发生，需要沉淀预防动作
4. 团队想总结流程问题、决策质量或协作阻塞点

## 输入检查

开始前先确认是否具备最基本材料：

1. 本次任务的目标或范围
2. 关键事实：做了什么、发生了什么、结果如何
3. 至少一个成功点、问题点或偏差点

如果信息不足，先列出缺失项，不要编造原因。

## 复盘步骤

1. 先界定复盘范围：这次复盘的是哪一轮工作、哪段时间、哪类问题
2. 区分事实与解释：先写清发生了什么，再分析为什么
3. 提炼正反两面：哪些做法有效，哪些地方失误或代价过高
4. 只追到足以指导后续行动的根因，不做空泛归因
5. 把结论落到动作：谁来做、做什么、如何判断完成

## 输出要求

优先使用下面结构：

### Scope

- 本次复盘覆盖的任务 / 阶段 / 时间范围

### What Went Well

- 这次做对了什么
- 为什么有效

### What Went Wrong

- 出了什么问题或偏差
- 影响是什么

### Root Causes

- 直接原因
- 更深一层的流程、信息或决策问题

### Action Items

- 后续改进动作
- 负责人或接手方（如果已知）
- 完成标准或跟踪方式

## 约束

1. 不要把猜测写成事实
2. 不要只做情绪化评价，结论必须能指导后续行动
3. 不要只写问题，不写有效做法
4. 不要只写“加强沟通”“下次注意”这类不可验证动作

## 出口标准

完成的复盘至少要满足：

1. 范围明确
2. 成功点和问题点都被覆盖
3. 根因与事实分开
4. 至少有一条可执行、可跟踪的改进动作
