## 🔒 铁律（不可违反！）

> **每次读文档前，先默念铁律。铁律是底线，流程是纪律。**

### 铁律1：不得跳过任何阶段
即使经验库有记录、即使参数看起来明确、即使"感觉"能跳过——也必须完成每个阶段。
每个阶段必须 read 对应文档 + 产出对应存档文件。

### 铁律2：API模式优先
必须经过**三轮深入分析**（含重新分析二次录制数据）都不行，才能咨询用户是否转UI。
禁止轻易说"API不行"。

### 铁律3：二次录制是必经阶段
不得提出"跳过二次录制"的建议，不得以"参数已明确"或"节省时间"为由询问用户是否跳过。

### 铁律4：请求体用模板替换法
从录制数据提取完整模板，只替换动态字段。禁止凭理解重构请求体。

### 铁律5：中断后必须恢复检查点
中断/出错恢复后，必须先读取最近的存档文件，确认当前阶段，重述铁律，才能继续。

## 十一阶段流程

### 阶段零：环境检查（自动）
**执行：** `node scripts/check-env.js`

检查项：
- Node.js 版本（>= 18）
- npm 依赖是否完整（缺失则自动 `npm install`）
- Chrome 浏览器是否存在

> ⚠️ **每次执行录制前必须运行环境检查**，确保依赖完整。如缺失会自动安装。

### 阶段一：录制
**读：** [01-录制指南.md](references/01-录制指南.md)

启动 record.ts（PTY模式），用户在浏览器中操作，录完用 `.done` 文件触发保存。
输出：`recording.json` + `recording-bodies.jsonl` + `api-list.md` + `downloaded-files/`

#### ⚠️ 结束录制强制规则（不可违反！）

1. **启动后立即poll输出**，提取 `Output  :` 后面的完整路径，记为 `DONE_DIR`
2. **用户说"录完了"时，创建 `.done` 文件**：`New-Item -Path "<DONE_DIR>\.done" -ItemType File -Force`
3. 🚫 **禁止使用stdin写入**：不要用 `process(action=write, data="done\n")`，PTY模式下readline无法正确接收
4. 🚫 **禁止猜测路径**：必须从录制器输出中提取，不要自己拼接时间戳

### 阶段二：追问
**读：** [02-追问指南.md](references/02-追问指南.md)

趁用户记忆新鲜，追问业务逻辑（默认值、循环逻辑、输出要求等）。
核心原则：能自己查到的不问用户（参数编码自动匹配、文件格式自动识别）。

### 阶段三：流量清洗与分类
**读：** [03-流量清洗与分类.md](references/03-流量清洗与分类.md)

从录制数据中筛出有效业务请求，按四类分类（页面初始化/动作触发/状态同步/校验）。
📁 存档：`analysis/step1-traffic-classify.md`

### 阶段四：链路梳理与依赖分析
**读：** [04-链路梳理.md](references/04-链路梳理.md)

理清接口之间的调用顺序和数据依赖（串行/并行/路由跳转），追溯 export→download 关联。
📁 存档：`analysis/step2-chain-analysis.md`

> 📖 如需了解 recording.json 的数据结构（包括大响应体优化机制），按需查阅 [12-录制数据格式.md](references/12-录制数据格式.md)

### 阶段五：接口拆解与参数识别
**读：** [05-接口拆解.md](references/05-接口拆解.md)

逐个拆解核心接口的5个部分（基础信息/请求头/Query/Body/响应），识别动态参数4级难度。

> ⚠️ **强制完整提取：** 所有关键接口的请求体和响应体，必须从录制数据中完整提取原始JSON，禁止省略任何字段。字段分类表的行数必须等于原始JSON的字段总数。

📁 存档：`analysis/step3-api-breakdown.md`

### 阶段六：二次录制与样本对比
**读：** [06-二次录制与对比.md](references/06-二次录制与对比.md)

引导用户做第二次录制，六层逐项对比（URL/Query/Headers/Body/响应/DOM），确认常量vs变量。
📁 存档：`analysis/step4-comparison.md`
> ⚠️ **此阶段为必经阶段，不可跳过。** 二次录制数据保存到 `analysis/comparison/` 目录，不覆盖原始录制数据。
> 
> 🚫 **禁止行为：** AI不得提出"跳过二次录制"的建议，不得以"参数已明确"或"节省时间"为由询问用户是否跳过。必须直接引导用户做第二次录制。

### 阶段七：调用模式决策
**读：** [07-调用模式决策.md](references/07-调用模式决策.md)

根据分析结果选择模式：A接口直调（推荐）/ B页面模拟 / C混合模式。
两轮深入分析都不行才转UI模式。
📁 存档：`analysis/step5-mode-decision.md`

### 阶段八：确认
**读：** [08-确认模板.md](references/08-确认模板.md)

按模板格式展示业务理解，让用户确认。用户未确认前禁止进入下一阶段。

### 阶段九：生成脚本
**读：** [09-脚本生成规则.md](references/09-脚本生成规则.md)

生成 `run-api.ts`（API模式）+ `run-ui.ts`（UI兜底）。
强制：CDP连接、凭据参数化、入参必传、表头校验、**TypeScript类型规范（1.4节）**、**请求体模板替换（1.5节）**。

### 阶段十：测试
**读：** [10-测试指南.md](references/10-测试指南.md)

运行脚本，修复错误，最多5轮。测试的是脚本，不是AI操作。

### 阶段十一：完成
**读：** [11-完成指南.md](references/11-完成指南.md)

**⚠️ 必须按 11-完成指南.md 中的展示模板输出，禁止自由发挥！**

流程：
1. 读取 run-api.ts 提取实际参数
2. 按模板格式展示使用指南（含分隔线、固定标题）
3. 询问"脚本是否 OK？"
4. 用户确认 OK 后更新网站交互经验库

## 阶段性存档机制

分析阶段（三~七）的每步产出独立存档文件，保存在任务文件夹的 `analysis/` 子目录：

```
<任务文件夹>/
├── recording.json
├── recording-bodies.jsonl
├── api-list.md
├── task-meta.json
├── analysis/
│   ├── step1-traffic-classify.md    ← 阶段三产出
│   ├── step2-chain-analysis.md      ← 阶段四产出
│   ├── step3-api-breakdown.md       ← 阶段五产出
│   ├── comparison/                  ← 阶段六：第二次录制数据（隔离存放）
│   │   ├── recording.json           ← 第二次录制（不覆盖原始数据）
│   │   └── recording-bodies.jsonl
│   ├── step4-comparison.md          ← 阶段六：对比报告
│   └── step5-mode-decision.md       ← 阶段七产出
├── run-api.ts
├── run-ui.ts
└── downloaded-files/
```

**存档的作用：**
- 每个阶段的分析结论有据可查
- 下一阶段开始时读上一阶段存档，确保上下文不丢
- 如果中途会话重置，可以从存档恢复

## 核心原则速查

| 原则 | 说明 |
|------|------|
| **接口直调优先** | API模式更稳定、更快、更可靠，**三轮**深入分析不行才转UI |
| **CDP 连接强制** | 生成的脚本必须 `connectOverCDP()`，禁止 `launch()` |
| **浏览器内 fetch** | API 模式用 `page.evaluate(fetch)` 调接口，自动带认证 |
| **凭据参数化** | `--username`/`--password` 参数传入，禁止硬编码 |
| **入参必传** | output-dir/username/password 全部必传，不设默认值 |
| **表头校验** | 生成文件的表头必须和录制时下载的文件完全一致 |
| **链路必须理清** | 链路没理清，直接复刻请求必失败 |
| **关联必须追溯** | export→download 之间的关联机制必须追溯清楚 |
| **二次录制对比** | **必经阶段**，用两次录制对比确认固定/动态参数 |
| **录制阶段安静** | 不 poll 终端，录完后才汇报 |
| **.done 路径从输出获取** | 录制器启动时输出 `Output  : <路径>`，`.done` 必须放在该路径下 |
