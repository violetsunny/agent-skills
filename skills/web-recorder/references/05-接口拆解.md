## ⚠️ 强制完整提取规则（最高优先级）

### 核心要求

**所有关键接口的请求体和响应体，必须从录制数据中完整提取原始JSON，禁止省略任何字段。**

### 为什么？

漏传字段是脚本失败的常见原因。即使某个字段"看起来不重要"，只要原始请求里有，就必须传。

### 执行步骤

1. **提取原始JSON**
   - 从 recording.json 中找到对应请求的 `postData`（请求体）和 `response.body`（响应体）
   - 完整复制到文档，不要手动精简

2. **统计字段数量**
   - 递归统计所有字段（包括嵌套对象、数组内的子字段）
   - 在文档中记录这个数量

3. **逐字段分析**
   - 为每个字段标注分类（FIXED/DYNAMIC/SESSION/RELATIONAL）
   - 嵌套对象要展开到最内层（如 `array[0].subField`）

4. **数量对比校验**
   - 文档中的字段数量必须等于原始JSON的字段数量
   - 不一致 = 有遗漏，必须补全

### 校验脚本（建议执行）

```bash
# 统计请求体字段数
node -e "
const fs = require('fs');
const data = JSON.parse(fs.readFileSync('recording.json', 'utf8'));
const req = data.requests.find(r => r.id === 'req_xxx');
const body = JSON.parse(req.postData);
function count(obj, prefix='') {
  let count = 0;
  for (const key in obj) {
    count++;
    if (typeof obj[key] === 'object' && obj[key] !== null) {
      if (Array.isArray(obj[key])) {
        obj[key].forEach((item, i) => count += count(item, prefix+key+'['+i+'].'));
      } else {
        count += count(obj[key], prefix+key+'.');
      }
    }
  }
  return count;
}
console.log('字段总数:', count(body));
"
```

## 二、标准化拆解（5个部分）

对每个核心接口，逐项拆解：

### Part 1：请求基础信息

| 项目 | 内容 |
|------|------|
| URL | 完整 URL（含 query string） |
| Method | GET/POST/PUT/DELETE |
| Content-Type | application/json / form-urlencoded / multipart |
| 编码格式 | UTF-8 / GBK（少见） |

### Part 2：请求头（Headers）

按功能分组：

| 分组 | 示例 | 处理方式 |
|------|------|----------|
| **身份类** | Authorization、X-SCP-TOKEN、Cookie | 从浏览器 session 获取 |
| **跨域类** | Origin、Referer | 浏览器自动带 |
| **客户端标识** | X-Requested-With、X-Client-Version | 固定值 |
| **内容标识** | Content-Type、Accept | 固定值 |
| **风控校验** | x-csrf-token、x-xsrf-token | 从页面/cookie 获取 |

> ⚠️ **重点**：找出所有非标准 headers（排除 accept/sec-*/user-agent/cookie 等浏览器标准 headers），这些很可能是认证相关的。

**认证线索分析方法：**
1. 扫描 `authClues`（录制器收集的认证线索）
2. 找出高频非标准 headers（30%以上请求都有的）
3. 追溯 header 来源（sessionStorage? localStorage? 页面全局变量?）
4. 在浏览器中验证：手动带这些 headers 调 API，确认成功

### Part 3：URL Query 参数

| 参数名 | 值 | 类型 | 说明 |
|--------|-----|------|------|
| pageId | 9e78d6e6-xxx | 固定 | 页面ID |
| timestamp | 1718000000000 | 动态 | 时间戳 |
| token | abc123 | 动态 | 从上一个接口获取 |

### Part 4：请求体 Body

#### 4.1 原始请求体（强制完整复制）

**从 recording.json 提取完整的 postData，原样粘贴：**

```json
// 原始请求体（完整JSON，禁止省略）
{
  // ... 完整复制
}
```

**字段统计：**
- 顶层字段数：X 个
- 嵌套对象字段数：X 个（列出路径，如 `config.nested.field`）
- 数组元素字段数：X 个字段 × N 个元素 = XX 个
- **总计：X 个字段**

#### 4.2 字段分类表

**必须列出所有字段，禁止省略：**

| 字段路径 | 值示例 | 分类 | 说明 |
|----------|--------|------|------|
| field1 | "xxx" | FIXED | 说明 |
| field2.nested | 123 | DYNAMIC | 说明 |
| array[0].subField | "yyy" | FIXED | 说明 |
| ... | ... | ... | **所有字段** |

**字段分类标准：**

| 类型 | 含义 | 脚本处理 |
|------|------|----------|
| FIXED | 每次值相同 | 硬编码 |
| DYNAMIC | 每次不同 | 转为 CLI 参数 `--参数名` |
| SESSION | token/cookie/userId | 从 session 管理器注入 |
| RELATIONAL | 从其他 API 获取 | 脚本中自动查询 |

**⚠️ 校验：** 表中行数必须等于上面的字段总数。不一致 = 有遗漏！

#### 4.3 请求体模板代码（供阶段九直接使用）

```typescript
// 将此常量复制到 run-api.ts 中
const REQUEST_TEMPLATE_接口名 = `完整JSON字符串`;
```

**用途：** 阶段九生成脚本时，直接复制此模板，只替换动态字段，禁止手动构造。

### Part 5：响应体 Response

#### 5.1 原始响应体（强制完整复制）

**从 recording.json 提取完整的 responseBody：**

```json
// 原始响应体（完整JSON，禁止省略）
{
  // ... 完整复制
}
```

**字段统计：**
- 总计：X 个字段

#### 5.2 关键字段提取

| 项目 | 内容 |
|------|------|
| 成功标识 | `success: true` / `code: 200` / `status: "ok"` |
| 关键出参 | 后续接口需要的字段（id、token、url 等），标注完整路径 |
| 异常码 | `401=登录过期`、`403=无权限`、`500=服务端错误` |
| 数据路径 | `data.list` / `data.value.values`（数据在 JSON 中的位置） |

**⚠️ 关键出参必须标注完整路径**，如 `data.msg` 中的 requestId，脚本需要精确提取。

## 三、动态参数识别（4级难度）

### 等级1：简单动态参数 ⭐

直接可得，不需要复杂计算：

| 参数类型 | 来源 | 生成方式 |
|----------|------|----------|
| 时间戳 | 当前时间 | `Date.now()` |
| 随机串 | 随机生成 | `Math.random().toString(36)` |
| 页面上下文 | URL/页面元素 | 从页面提取 |
| 用户输入 | 用户指定 | CLI 参数 |

### 等级2：简单拼接/哈希 ⭐⭐

明文组合后做简单加密：

```
例：sign = md5(appKey + timestamp + secret)
例：token = btoa(username + ":" + password)
```

**分析方法：** 在浏览器中搜索参数名，找到赋值逻辑

### 等级3：JS全局加密函数 ⭐⭐⭐

前端有统一的加密函数，需要找到并复用：

```
例：所有请求的 body 都经过 encrypt(JSON.stringify(data))
例：请求头 sign 由 window.cryptoSign(params) 生成
```

**分析方法：**
1. 在浏览器 DevTools 中搜索加密关键词（encrypt/sign/md5/sha）
2. 找到全局函数后，在脚本中通过 `page.evaluate()` 调用

### 等级4：强混淆/环境校验 ⭐⭐⭐⭐

代码高度混淆，或校验浏览器环境（WebDriver 检测、Canvas 指纹等）

**处理方式：** 放弃接口直调，改用页面模拟操作（见阶段七）

## 四、frontend-generate 类型专项分析

当下载类型为 `frontend-generate` 时（前端 JS 生成文件，不是后端返回文件流），需要额外分析：

### 识别特征（3个同时满足）
1. 有 download 事件
2. 无文件流响应（没有 Content-Type: octet-stream 的响应）
3. 有大数据量 JSON 响应（bodyLength > 50KB，在下载事件前 1-5 秒）

### 需要提取的信息

| 信息 | 说明 |
|------|------|
| 数据源 API | 返回业务数据的接口（不是 export/auditlog） |
| 响应数据结构 | 数据在 JSON 中的路径（如 data.value.values） |
| 列定义路径 | 列名在 JSON 中的路径（如 data.value.columns） |
| 分页参数 | 录制时的分页值 + 全量值（如 topN: 20→30000） |
| 单元格格式 | 如 `{v: '值'}` 或直接字符串 |
| 表头 | 从 `downloadedFiles[0].headers` 读取（录制时自动提取） |

### 脚本生成注意
- 不要调 export API（只记录日志，不返回数据）
- 用 `page.evaluate(fetch)` 在浏览器内调数据源 API（自动带认证）
- 分页参数必须改为全量值
- 在 Node.js 端用 ExcelJS 生成文件

## 五、选择器质量评估

解析 actions 中每个操作的 `selectorStrategy` 字段，评估稳定性：

| 等级 | 策略 | 说明 |
|------|------|------|
| S | stable-id | 稳定ID，最可靠 |
| A | placeholder/text/sibling/parent+attrs | 属性组合，较可靠 |
| B | stable-classes/nth-of-type | 需验证稳定性 |
| C/D | fallback | 不稳定，需人工处理 |

> 完整策略表见 `archive/选择器策略表.md`（遇到 C/D 级选择器需要详细修复建议时按需查阅）
