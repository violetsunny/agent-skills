# 阶段十：测试

> 运行生成的脚本，确保能正确执行，最多 5 轮修复

---

## 一、核心原则

### 测试的是脚本，不是 AI 操作

```bash
# ✅ 有效测试：执行脚本文件
npx ts-node run-api.ts

# ❌ 无效测试：AI 直接操作浏览器
browser open → browser fill → browser click
```

**判断标准：**
- 脚本退出码 = 0 → 成功
- 脚本退出码 ≠ 0 → 失败（即使 AI 手动操作能成功也不算通过）

---

## 二、测试步骤

### 2.0 环境检查（前置）

```bash
# 检查 Playwright 依赖
npx playwright install --dry-run

# 检查浏览器连接
openclaw browser status
```

如果依赖未安装 → 告知用户，不要直接用 AI 操作替代。

### 2.1 第一轮：dry-run 预览

```bash
npx ts-node run-api.ts --dry-run
```

检查：参数解析、默认值、API URL 格式。

### 2.2 第二轮：实际运行

```bash
npx ts-node run-api.ts --output-dir "xxx" --username xxx --password xxx
```

检查：脚本退出码、输出是否符合预期、文件是否保存到正确位置。

### 2.3 失败 → 修复 → 重复

| 路径 | 做法 | 适用场景 |
|------|------|----------|
| **修改脚本** | 分析错误 → 修改脚本 → 重新运行 | 选择性问题、API参数错误 |
| **AI 辅助** | AI 直接操作验证逻辑 | 需要验证页面状态时 |

**重要：** AI 辅助验证后，必须修改脚本，不能只靠 AI 手动操作。

## 三、常见错误诊断

### 3.1 认证失败（401/403）

使用录制阶段收集的 `authClues` 自动诊断：

| 失败类型 | 诊断方向 | 修复方式 |
|----------|----------|----------|
| API 返回 401 | 自定义 header 未正确传递 | 检查页面是否完全加载？header 值是否正确获取？ |
| API 返回 403 | URL 认证参数已过期 | 检查 URL 中的认证参数（如 accessTicket） |
| API 返回 200 但 success=false | 认证信息不完整 | 检查是否需要同时传递多个 header |
| 页面跳转到登录页 | 登录态已过期 | 重新执行登录流程 |

### 3.2 选择器失败

| 错误信息 | 原因 | 修复 |
|----------|------|------|
| strict mode violation | 选择器匹配多个元素 | 增加更具体的限定条件 |
| waiting for selector timeout | 元素不存在或不可见 | 检查前置步骤是否完成 |

**根据 selectorStrategy 判断修复优先级：**

| 策略值 | 修复难度 | 修复方式 |
|--------|----------|----------|
| stable-id | 低 | 重新录制获取新 ID |
| placeholder/text | 低 | 更新文本值 |
| sibling-* | 中 | 检查兄弟关系是否还存在 |
| nth-of-type | 高 | 换用文本或属性定位 |
| fallback | 最高 | 需要全新选择器策略 |

### 3.3 表头不一致

**排查步骤（强制）：**
1. 获取脚本中的 EXPECTED_HEADERS 和 actualHeaders
2. 逐列对比，找出不一致的地方
3. 定位原因（API 字段名映射错误？列顺序错误？多了/少了列？）
4. 修改脚本中的 COLUMN_NAMES 映射（以 downloadedFiles[0].headers 为准）
5. 重新测试

**禁止行为：**
- ❌ 直接把错误告诉用户说"表头不一致，请检查"
- ❌ 不排查根因就盲目修改
- ❌ 修改 EXPECTED_HEADERS 来"修复"问题（应该修改脚本的数据映射）

### 3.4 数据不完整

当某个 API 返回的数据和预期不符，检查 `recording.json` 中对应响应的 `bodySaved` 字段：
- `bodySaved: false` → 完整响应在 `recording-bodies.jsonl` 中
- 按 requestId 搜索：`Select-String -Path "recording-bodies.jsonl" -Pattern "req_0042"`

### 3.5 请求体结构错误

**识别特征：**
- API 返回 200 但 `success: false`
- 错误信息包含 `NullPointerException`、`IllegalArgumentException` 等后端异常
- 错误堆栈指向参数解析相关的方法（如 `processPreSql`、`parseRequest`）

**排查步骤（强制）：**

1. **打印脚本中的完整请求体**
   ```typescript
   console.log('请求体:', JSON.stringify(body, null, 2));
   ```

2. **从录制数据中提取原始请求体**
   ```bash
   node -e "
   const fs = require('fs');
   const data = JSON.parse(fs.readFileSync('recording.json', 'utf8'));
   const req = data.requests.find(r => r.id === 'req_xxx');
   console.log('原始请求体:', req.postData);
   "
   ```

3. **逐字段对比**
   - 嵌套层级是否一致（如 `cubeId` 在 config 同级 vs 内部）
   - 字段顺序是否一致
   - 固定字段的值是否一致（特别是布尔值、数字）
   - 动态字段是否只改了预期的那些

4. **修复方法**
   - 使用"模板替换法"：从录制数据提取完整模板，只替换动态字段
   - 禁止凭理解手动构造完整请求体

**常见错误模式：**

| 错误 | 现象 | 原因 |
|------|------|------|
| 嵌套位置错误 | 后端找不到字段，返回 null | 把 A 层的字段放到了 B 层 |
| 字段顺序错误 | 某些 API 对顺序敏感 | 手动构造时顺序和录制数据不同 |
| 布尔值错误 | `needCount: true` vs `false` | 凭理解修改，没有对比录制数据 |
| 遗漏字段 | 后端报参数缺失 | 省略了"看起来不重要"的字段 |
