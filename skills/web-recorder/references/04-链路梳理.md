# 阶段四：链路梳理与依赖分析

> 搞清楚接口之间的调用顺序和数据依赖，这是脚本能不能跑通的关键

---

## 一、目标

理清所有业务接口之间的依赖关系，画出完整的调用链路图。

**前置条件：** 阶段三的 `analysis/step1-traffic-classify.md` 已完成
**存档位置：** `analysis/step2-chain-analysis.md`

> ⚠️ **关键原则：链路没理清，直接复刻请求必失败。** 很多脚本测试时报错，根因就是跳过了这一步。

---

## 二、三种依赖模型

### 模型1：串行依赖（最常见）

上一个接口的响应 → 下一个接口的入参

```
接口A：获取 token → 返回 tokenId
接口B：用 tokenId 查询数据 → 返回 dataList
接口C：用 dataList 中的 id 提交导出 → 返回 taskId
```

**识别方法：**
- 接口B的请求体/URL参数中，出现了接口A响应体中的某个字段值
- 时间上 A 一定在 B 之前

### 模型2：并行请求

多个接口同时发起，互不依赖

```
页面加载时同时请求：
  ├── 字典数据（下拉框选项）
  ├── 用户信息（页面头部显示）
  └── 列表数据（表格内容）
```

**识别方法：**
- 多个请求在相近时间（<500ms）发出
- 入参中没有来自其他请求的字段
- 通常是页面初始化类的请求

### 模型3：路由/页面跳转依赖

SPA 路由鉴权 → 页面数据加载

```
路由跳转 /page/A → /page/B
  ├── 先触发鉴权请求（带 ticket/token）
  ├── 鉴权通过后触发页面B的数据请求
  └── 如果鉴权失败，后续请求都不会发出
```

**识别方法：**
- URL 发生明显变化（路径不同）
- 新页面的第一个请求通常带认证参数
- 有 302 重定向或 SPA 路由变化

## 三、分析方法

### Step 1：逐个打开响应体

对阶段三识别的每个核心 API：
1. 读取完整响应体（从 recording.json 或 recording-bodies.jsonl）
2. 提取响应中的关键字段（id、token、code、url 等）

### Step 2：对比后续请求

拿着上一步提取的字段值，在后续请求的 URL 参数和请求体中搜索：
- 找到了 → 存在串行依赖，记录依赖关系
- 没找到 → 可能是并行或无依赖

### Step 3：画链路图

```
链路图示例：

[页面初始化]
  dict1(GET) ──→ 返回字典数据
  dict2(GET) ──→ 返回字典数据
  userInfo(GET) ──→ 返回用户信息

[查询流程]
  queryConfig(GET) ──→ 返回配置
       ↓
  queryData(POST) ──→ 返回列表数据
       ↓                ↑ configId 来自 queryConfig
  queryDetail(POST) ──→ 返回详情
                         ↑ itemId 来自 queryData

[导出流程]
  exportSubmit(POST) ──→ 返回 taskId
       ↓
  exportStatus(GET) ──→ 返回 status（轮询）
       ↓
  exportDownload(GET) ──→ 返回文件流
       ↑                   ↑ taskId 来自 exportSubmit
  或 messageNotice(GET) ──→ 返回 downloadUrl
       ↑                    ↑ 消息通知模式
```

### Step 4：关联追溯（export → download 必须追溯清楚）

如果存在导出/下载操作，必须搞清楚 export 和 download 之间的关联机制：

1. **读取 downloadChains**（录制器自动检测的）
2. **分析中间请求**：export 和 download 之间有哪些请求？
3. **识别桥接字段**：连接 export 和 download 的关键数据（taskId/downloadUrl/fileCode）
4. **验证关联唯一性**：桥接字段能否唯一定位到正确的文件

**常见关联模式：**

| 模式 | 中间请求特征 | 桥接字段 | 可靠性 |
|------|------------|---------|--------|
| 消息通知 | GET /userMsg/... | downloadUrl/fileName | ⭐⭐ 靠标题+时间过滤 |
| taskId轮询 | GET /status?taskId=xxx | status/downloadUrl | ⭐⭐⭐⭐ taskId唯一 |
| 文件列表 | GET /file/list | files[].name | ⭐⭐ 靠时间差 |
| 直接返回 | 无中间请求 | export响应直接返回文件 | ⭐⭐⭐⭐⭐ |

## 四、存档格式

```markdown
# 链路梳理报告

## 依赖关系总览

### 串行依赖
- dict1 → queryData（configId）
- queryData → exportSubmit（itemId）
- exportSubmit → exportStatus（taskId）
- exportStatus → exportDownload（taskId）

### 并行请求
- dict1、dict2、userInfo 三个请求并行（页面初始化）

### 路由依赖
- /page/A → /page/B 需要鉴权请求通过

## 链路图
（ASCII 图）

## 关联追溯
- export → download 关联方式：taskId 轮询
- 桥接字段：taskId
- 轮询间隔：2s
- 超时时间：30s

## 关键发现
- （列出分析过程中发现的重要信息）
```
