# 阶段三：流量清洗与分类

> 从录制数据中筛出有效业务请求，按功能分类，为后续链路梳理做准备

---

## 一、目标

录制数据里混杂了各种请求（业务API、轮询、埋点、心跳等），这一步要把它们分门别类整理清楚。

**存档位置：** `analysis/step1-traffic-classify.md`

---

## 二、执行步骤

### Step 0：读取接口清单（强制前置）

**录制完成后已自动生成 `api-list.md`，直接读取此文件获取完整接口列表。**

```
读取 api-list.md：
1. 获取所有业务API的完整列表（不会漏）
2. 查看每个API的Body完整性标记（✅/📋/❓）
3. 标记为📋的API，需要时用脚本从 recording-bodies.jsonl 提取完整响应
```

> ⚠️ **禁止用 read 工具直接读 recording.json 提取接口列表**（文件可能几百KB，read 工具有 50KB 限制，会漏接口）。

### Step 1：二次过滤确认

录制器已经做了大部分过滤（静态资源、路过式hover等），这里做二次确认：

**需要过滤掉的：**
- 心跳/轮询请求（同一个URL反复出现，间隔固定）
- 埋点/监控请求（URL含 analytics/tracker/beacon/log 等关键词）
- 广告/推荐请求（非业务相关的外部域名）
- OPTIONS 预检请求（CORS 自动发起的）

**怎么判断：**
```
1. 按 URL 分组统计请求数量
2. 出现 3 次以上且间隔固定的 → 大概率是轮询/心跳
3. URL 含 analytics/tracker/beacon → 埋点
4. method = OPTIONS → CORS 预检
```

### Step 2：按操作时序排序

把过滤后的请求按时间排序，和用户的操作步骤对应起来：

```
用户操作时间线：
  0s    → 打开页面
  3s    → 页面加载完成
  8s    → 选择筛选条件
  12s   → 点击查询
  15s   → 结果返回
  20s   → 点击导出
  25s   → 下载完成

对应的请求分组：
  [前置请求] 0-3s：页面初始化时触发的请求
  [主业务请求] 8-15s：查询/提交操作触发的请求
  [后置请求] 20-25s：导出/下载触发的请求
```

### Step 3：四类请求分类

对每个请求打标签：

| 类别 | 特征 | 处理方式 | 举例 |
|------|------|----------|------|
| **页面初始化类** | 进入页面就触发，加载字典/下拉/配置 | 脚本启动时预加载 | 字典查询、菜单加载、权限查询 |
| **动作触发类** | 点击/输入后触发，核心业务接口 | 脚本的核心逻辑 | 查询、提交、导出 |
| **状态同步类** | 心跳/推送/轮询 | 可忽略 | 在线状态、消息轮询 |
| **校验类** | 验证码/滑块/风控 | 需要特殊处理 | 图形验证码、短信验证 |

### Step 4：识别核心 API

提取所有发往应用域名的 POST/PUT/PATCH 请求（含有效 body），这些通常是动作触发类的核心接口：

- 请求 URL、Method、Headers、Body
- 响应 Status、Body（或 bodySummary）
- 请求时序（前置 → 主操作 → 后续）

> 💡 如果某个 API 的响应数据不完整（只有 bodySummary），去 `recording-bodies.jsonl` 中按 requestId 找完整响应。

---

## 三、查阅网站交互经验库（优先！）

分析前先检查 `references/site-experience/` 目录是否有相同域名的经验文件：

1. **提取入口域名**：从 recording.json 的 `recording.finalUrl` 字段提取（如 gsrm.midea.com）
2. **匹配经验文件**：文件名格式 `<系统名>-<域名>.md`
3. **有经验** → 读取并对比匹配度，可复用鉴权方式、接口模式等，但**必须用录制数据验证**
4. **无经验或差异大** → 按正常流程分析

---

## 四、存档格式

```markdown
# 流量清洗与分类报告

## 过滤统计
- 录制总请求数：XX
- 过滤掉：XX（轮询XX + 埋点XX + OPTIONS XX）
- 有效业务请求：XX

## 请求分类

### 页面初始化类
| # | URL | Method | 作用 | 触发时机 |
|---|-----|--------|------|----------|
| 1 | /api/dict/xxx | GET | 加载字典 | 页面加载 |

### 动作触发类（核心）
| # | URL | Method | 作用 | 触发操作 |
|---|-----|--------|------|----------|
| 1 | /api/query | POST | 查询数据 | 点击"查询" |
| 2 | /api/export | POST | 导出 | 点击"导出" |

### 状态同步类（可忽略）
| # | URL | 间隔 | 说明 |
|---|-----|------|------|
| 1 | /api/heartbeat | 30s | 心跳 |

### 校验类
（无 / 有：描述）

## 核心 API 列表
（动作触发类的详细信息）
```

## 五、校验通过标准

进入阶段四之前，必须确认：

- [ ] 所有请求都已分类（无遗漏，每个请求都打了标签）
- [ ] 核心API列表不为空（至少有1个动作触发类请求）
- [ ] 轮询/心跳请求已标记为"可忽略"
- [ ] 经验库已查阅（如有相同域名的经验文件）
- [ ] 存档文件已保存到 `analysis/step1-traffic-classify.md`
