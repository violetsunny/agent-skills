# 阶段六：二次录制与样本对比

> 两次录制 = 两组同操作不同时刻的样本，相同 = 常量，不同 = 变量

---

## 🔒 铁律提醒

> **铁律3：二次录制是必经阶段** — 不得提出"跳过"的建议，不得以"参数已明确"或"节省时间"为由询问用户是否跳过。
> 
> **必须直接引导用户做第二次录制，不问"要不要做"。**

---

## 一、核心原理

同一个操作做两次，对比两次的数据：
- **两次都一样的** → 常量（硬编码）
- **两次不同的** → 变量（需要动态生成或暴露为参数）

这是最可靠的参数识别方法——不需要猜，直接看数据说话。

**前置条件：** 阶段五的 `analysis/step3-api-breakdown.md` 已完成（至少有初步分析）
**存档位置：** `analysis/step4-comparison.md` + `analysis/comparison/` 目录

> ⚠️ **数据隔离：** 第二次录制的数据必须保存到 `analysis/comparison/` 目录，**不能覆盖原始 recording.json**。

---

## 二、适用场景

| 场景 | 说明 |
|------|------|
| 分不清固定/动态 | 某个参数两次录制值不同 → 动态；相同 → 固定 |
| 看不懂 sign/加密 | 对比两次的 sign 值，如果不同说明含动态因素 |
| 请求头不确定必填 | 两次对比，每次都有的 header → 必填 |
| 接口依赖不确定 | 两次录制中某个值是否来自上一个接口 |

## 三、执行步骤

### Step 1：引导用户做第二次录制

```
我需要你做第二次录用来对比数据。

请完全重复刚才的操作（一模一样的步骤），我会自动对比两次的数据。

⚠️ 注意事项：
1. 操作必须完全一致（点同样的按钮、填同样的内容）
2. 和第一次间隔 10-30 秒（不要太短，让时间戳等参数产生变化）
3. 不要混入额外操作（比如中途看消息、切换页面）
```

**启动第二次录制（数据隔离）：**

```bash
# 第二次录制：使用 --output 指定子目录，避免覆盖原始数据
npx ts-node scripts/record.ts --name "my-task" --app-url "https://..." --output "D:\Users\xubx4\.openclaw\rpa\tasks\my-task_20260604_1546\analysis\comparison"
```

> ⚠️ **关键：** 第二次录制的 `--output` 指向 `analysis/comparison/` 子目录，这样新的 recording.json 会保存在那里，不会覆盖原始的 recording.json。

#### ⚠️ 结束录制规则（同阶段一）

**启动后立即poll输出**，提取 `Output  :` 后面的完整路径，记为 `DONE_DIR`。

用户说"录完了"时，创建 `.done` 文件：
```powershell
New-Item -Path "<DONE_DIR>\.done" -ItemType File -Force
```

🚫 **禁止使用stdin写入**（`process(action=write, data="done\n")`），PTY模式下readline无法正确接收。

**录制完成后，目录结构：**

### Step 2：读取两次录制数据

- 第一次：`recording.json`（或 `recording-bodies.jsonl`）
- 第二次：`analysis/comparison/recording.json`（或 `analysis/comparison/recording-bodies.jsonl`）

> 💡 两次录制数据分别保存在不同位置，方便对比，不会互相覆盖。

### Step 3：六层逐项对比

#### 第1层：基础请求信息

| 对比项 | 第一次 | 第二次 | 结论 |
|--------|--------|--------|------|
| URL | /api/query?page=1 | /api/query?page=1 | ✅ 相同=固定 |
| Method | POST | POST | ✅ 相同 |
| Content-Type | application/json | application/json | ✅ 相同 |

#### 第2层：URL Query 参数

| 参数 | 第一次 | 第二次 | 结论 |
|------|--------|--------|------|
| timestamp | 1718000001 | 1718000035 | 🔄 不同=动态（时间戳） |
| pageId | abc-123 | abc-123 | ✅ 相同=固定 |

#### 第3层：请求头（⚠️ 重灾区）

> 很多认证问题出在请求头上，这层对比最重要！

| Header | 第一次 | 第二次 | 结论 |
|--------|--------|--------|------|
| X-SCP-TOKEN | eyJhbG... | eyJhbG... | 🔄 不同=动态（但每次都需要） |
| X-Requested-With | XMLHttpRequest | XMLHttpRequest | ✅ 相同=固定 |
| x-csrf-token | abc123 | def456 | 🔄 不同=动态（每次从cookie获取） |

**判断规则：**
- 两次都有（值不同）→ 必填，值从 session 动态获取
- 两次都有（值相同）→ 必填，固定值
- 只有一次有 → 可能是可选的，或条件触发的

#### 第4层：请求体 Body/FormData

> ⚠️ **必须对比所有字段，禁止只对比"看起来重要"的字段。**

| 字段路径 | 第一次 | 第二次 | 结论 |
|----------|--------|--------|------|
| buCode | "100909" | "100909" | ✅ 固定 |
| sign | "a1b2c3" | "d4e5f6" | 🔄 动态（需要找生成逻辑） |
| pageSize | 20 | 20 | ✅ 固定 |
| array[0].subField | "xxx" | "xxx" | ✅ 固定 |
| ... | ... | ... | **所有字段** |

**⚠️ 校验：** 
- 对比表的行数必须等于阶段五中统计的字段总数
- 如果有字段只在一个样本中出现 → 可能是条件触发的，需要进一步分析

#### 第5层：响应体 + 接口链路

| 对比项 | 第一次 | 第二次 | 结论 |
|--------|--------|--------|------|
| 响应结构 | 相同 | 相同 | ✅ 结构稳定 |
| 数据内容 | 不同（正常） | 不同 | 数据随时间变化 |
| 接口顺序 | A→B→C | A→B→C | ✅ 链路一致 |

#### 第6层：DOM/元素定位

| 对比项 | 第一次 | 第二次 | 结论 |
|--------|--------|--------|------|
| 选择器策略 | stable-id | stable-id | ✅ 稳定 |
| 元素位置 | 相同 | 相同 | ✅ 无变化 |

## 四、不同场景的提问话术

### 场景1：分不清固定/动态

```
"对比两次录制的请求体，哪些字段值变了？
 变了的 → 动态参数（需要暴露为 CLI 参数或动态生成）
 没变的 → 固定参数（硬编码）"
```

### 场景2：看不懂 sign/加密

```
"对比两次的 sign 值：
  不同 → 含动态因素（时间戳？随机数？请求内容哈希？）
  相同 → 纯静态签名（不太可能，除非是固定 token）
  
  进一步分析：
  - 如果 sign 长度固定 → 可能是 hash（md5/sha）
  - 如果 sign 长度不固定 → 可能是 base64 编码
  - 在浏览器中搜索 'sign' 关键词，找生成逻辑"
```

### 场景3：请求头不确定必填

```
"对比两次的请求头：
  两次都有的 header → 必填
  只有一次有的 → 可选或条件触发
  值每次都不同 → 从 session/cookie 动态获取
  值每次都相同 → 固定值"
```

### 场景4：接口依赖不确定

```
"对比两次录制中接口B的入参：
  如果某个参数值 = 接口A响应中的某个字段 → 有依赖
  如果两次都是相同的固定值 → 无依赖
  如果两次值不同且找不到来源 → 可能从页面/cookie获取"
```

## 五、关键避坑

| 坑 | 说明 | 怎么避 |
|----|------|--------|
| 操作不一致 | 两次操作不完全一样，对比结果不可靠 | 强调"完全重复" |
| 间隔太短 | 时间戳等参数来不及变化 | 间隔 10-30 秒 |
| 混入额外操作 | 中途看了消息/切了页面，多出无关请求 | 提醒不要做额外操作 |
| 只看 body 忽略请求头 | 认证问题 80% 出在请求头上 | 六层都要对比，第3层重点 |

---

## 六、进阶：三次录制

如果两次对比后仍有疑问，可以做第三次录制：

| 目的 | 怎么做 |
|------|--------|
| 验证跨分钟变化 | 等 1 分钟以上再录一次（看分钟级时间戳参数） |
| 验证业务入参影响 | 改一个筛选条件再录（看哪些参数跟着变） |
| 验证认证过期 | 等较长时间再录（看 token 是否刷新） |
